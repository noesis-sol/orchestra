# Setting a project up

What `orchestra init` does, in full, and the setup a spec run does without it. Back to the [README](../README.md).

## Set up a project

In the project's repository:

```
orchestra init --check-fast "scripts/ci-local.sh"
```

This creates `.orchestra/`, where everything `orchestra` owns in a project lives:

```
.orchestra/worker-prompt.md   committed: the worker prompt (from the built-in template)
.orchestra/settings.json      committed: the two checks and their time limits, how many tickets run at once, the MCP servers workers get (by name), an optional ticket limit, the issue types never dispatched, whether tickets are kept apart by footprint, whether conflicts go back to their workers, when failing workers hold the run, and the versions of orchestra's templates the worker prompt and the verifier came from
.orchestra/.gitignore         committed: ignores the three below
.orchestra/specs/             committed: the specs spec runs (orchestra --spec) copied in from outside the repository
.orchestra/orchestra.log      the event log
.orchestra/reports/           run reports
.orchestra/run/               per-ticket files in each worktree (the launch prompt and the standing rules, the worker's MCP servers, its hooks and what they report, and the whole output of a merge check that failed there, check.log); in the main checkout, the event stream, the workers the last run left behind (state.json), a spec's or a feature's breakdown's instructions (spec-prompt.md), each [answer talk](dashboard.md#the-answer-talk)'s files in a folder of its own, answer-<n> (its instructions, answer-prompt.md, and the questions it asks, questions.md, and questions-<n>.md for those queued into it), a feature's description (feature-request.md) and the epic its session filed (feature.json), and for a spec the change it updates the tree for (spec-update.md) and the root epic a refinement handed back (spec.json)
```

and the project's two checks, the runners, in `scripts/`:

```
scripts/check-fast.sh         committed: the merge check, run on every ticket before it merges
scripts/check-full.sh         committed: every check, check-fast.sh then the slower suites, run once at the end of a run
```

The run lock is not there but in the git directory, as `.git/orchestra.lock`, where `git clean` doesn't remove it during a run (see [Run](running.md#run)).

Run `init` from the main checkout, between runs. It refuses, with exit code 2 and the project as it was, in a linked worktree (`<path> is a linked worktree. Run this from the main checkout.`, as a run says), where what it writes would land on that worktree's branch, a worker's ticket's; and while a run holds the repository's lock, naming that run as a second run is told (`orchestra init: orchestra is already running in <repo> (pid 44497, since 14:02, main). …`): the runners and `.gitattributes` it rewrites would leave the run's tree dirty, which stops the run (`DIRTY_TREE`), and the run would take up the tickets it files. It looks for a run again once the form is answered, before it changes anything, and from then to its end holds the lock itself: a run started meanwhile is refused, as a second run is (`orchestra is already running in <repo> (orchestra init, pid 44497)`), rather than work on tickets `init` renames, in a tree it writes into.

First, `init` sets Beads up. Where `bd` isn't installed, it installs it: with Homebrew (`brew install beads`) where `brew` is on the `PATH`, as Beads recommends, otherwise, on macOS, Linux and FreeBSD, with the Beads install script (`curl -fsSL https://raw.githubusercontent.com/gastownhall/beads/main/scripts/install.sh | bash`), which checks what it downloads and falls back to `go install`. On Windows it installs nothing and says how: `irm https://raw.githubusercontent.com/gastownhall/beads/main/install.ps1 | iex` in PowerShell. In a terminal the form asks first, offering yes; `--install-beads` installs without asking and `--install-beads=false` declines. Without a terminal or either flag, `init` installs nothing and reports `bd` missing. The install may take up to 15 minutes, and Ctrl+C stops it. If `bd` lands in a folder that isn't on your `PATH` (the script uses `~/.local/bin` where it can't write to `/usr/local/bin`), `init` says where it is and how to add the folder. Then, in a repository without `.beads/`, `init` runs `bd init --non-interactive --role maintainer --init-if-missing`: no questions, the answers being "not contributing to someone else's repo" and auto-export off. Otherwise `bd init` does what it does when run by hand: it adds `.beads/`, `AGENTS.md`, `CLAUDE.md` and other agents' integration files, and points git's hooks at `.beads/hooks`. bd 1.3.0 also commits what it adds, along with anything already staged, so `init` runs it before staging anything of its own, then lists what `bd` committed and what is left to commit with `.orchestra/`. A failed install or `bd init` shows the command's error, and the **Next** box keeps the fix. Ctrl+C (or SIGTERM) after the form stops `init` with exit code 130 and `orchestra init: stopped`, below the steps it did: during the install or `bd init`, before anything of `.orchestra/` is written; once it has started writing `.orchestra/`, the runners and the settings, it writes them all first (`orchestra init: stopped once it had written the files above`), so that a setup half written isn't taken for one done; while it files the test work, with the tickets it didn't file named, for `orchestra init` run again to file.

In a terminal, `init` asks with a short form in two steps, one screen each, under a stepper showing the steps done, current and to come, such as **✓ Workers ──── ● Checks**; a question answered and left shows its choice ticked (✓). **Workers** asks whether to install Beads (where `bd` is missing, as above), how many **tickets to run at the same time** by default, and which **MCP servers workers get** (see [MCP servers for workers](workers.md#mcp-servers-for-workers)). Where the project keeps a `CHANGELOG.md` that `.gitattributes` doesn't merge by union yet, it also offers to add `CHANGELOG.md merge=union` there, so tickets that each add an entry at the same spot don't conflict (see [Several tickets at once](running.md#several-tickets-at-once)). **Checks** chooses the project's checks, as [Choosing the checks](#choosing-the-checks) says, and asks, where the repository has a lockfile and `settings.json` no setup command, the **setup command** (see [The checks](#the-checks)), and last the **ticket prefix** (see [The ticket prefix](#the-ticket-prefix)). It asks no time limit: `init` writes the defaults to `settings.json` where it has none, `check_fast_timeout` 30m and `check_full_timeout` 60m, and you change them by editing that file (see [The checks](#the-checks)); a value there is kept. Enter on a step's last question goes on to the next step, and Shift+Tab on its first goes back to the previous one, with its answers kept. Nothing is installed or written until the last step is submitted: Esc or Ctrl+C at any step ends `init` with the project as it was. A step whose every question a flag answers is skipped, and the one step left has its name alone as its header; with every question answered, there is no form. With `TERM=dumb`, the form asks its questions one after another as plain lines, each step's under a header such as **Step 1 of 2 · Workers**; Ctrl+D (the end of input) there ends `init` as Esc does. `--check-fast "<command>"` (or `--check`) and `--check-full "<command>"` (either answers the choice of checks, and there is then no scout), `--verifier` (or `--verifier=false`), `--check-fast-timeout 5m` (or `--check-timeout`), `--check-full-timeout 90m`, `--setup "<command>"` (or `--setup ""` for none), `--concurrent N` (or `-c N`), `--mcp a,b` (or `--mcp ""` for none), `--prefix name` and `--changelog-union` (or `--changelog-union=false`) answer those without asking, which is what a script, or an agent setting the project up for you, should use. Without a terminal it asks nothing, uses 1 at a time, leaves the MCP servers as they were (unset on a first run), and leaves `.gitattributes` alone. `init` then shows each step, whether `bd`, Beads, a terminal for the workers (`herdr`, `tmux` or `cmux`) and `claude` are there, and a **Next** box with only what's left, ending with the command to start a run and where to start it from: a Herdr pane, a cmux terminal or, with tmux, any terminal, as the machine has them. `init` also checks for `bd`, `.beads`, one of `herdr`, `tmux` and `cmux`, and `claude`, and says what's missing. It installs no terminal: with none, it says `install Herdr, tmux (brew install tmux, apt install tmux) or cmux`. tmux is the one to install for running anywhere; a run picks Herdr in a Herdr pane, cmux in a cmux terminal, tmux elsewhere ([Herdr, tmux or cmux](running.md#herdr-tmux-or-cmux)). It finds `cmux` on the `PATH`, as it is in a cmux terminal, or in the app, `/Applications/cmux.app/Contents/Resources/bin/cmux`. It never replaces an existing prompt unless you pass `--force`, and keeps existing settings unless its flags change them; where the prompt or the verifier it keeps is older than orchestra's templates, its step says which sections changed, and `orchestra init --update` takes them (see [Taking template changes](workers.md#taking-template-changes)). In a project set up by an earlier version, it moves `.claude/worker-prompt.md` into `.orchestra/` (staged with `git mv`); the old `.claude/orchestrate.log` and reports stay where they are, as history. Commit `.orchestra/` and the runners (and `.gitattributes`, if it changed, and whatever `bd init` left uncommitted; the **Next** box names them) afterwards: a ticket's worktree has only what is committed, and its merge check runs there.

## A spec run's setup

A [spec run](running.md#a-whole-app-from-a-spec), `orchestra --spec <file>`, builds an app from nothing, unattended, so it doesn't need `init` first:

```
mkdir shop && cd shop && git init && orchestra --spec ~/specs/shop.md
```

In a repository `init` hasn't set up (no `.orchestra/worker-prompt.md` or `.orchestra/settings.json`, nor a `.claude/worker-prompt.md` from before `init`), even one with no commit yet, the run sets it up itself, once it holds the run lock and before it commits the spec, rather than stop with `orchestra isn't set up in this repository yet`. It does what `init` does without a terminal, taking its defaults and declining what it offers. It first brings the base branch up to its upstream, as it does before it commits the spec: where that fast-forward brings in a setup, in a clone made before `orchestra init` was pushed, the run sets nothing up and runs with that setup's settings, saying `SPEC: the fetch brought in orchestra's setup: the repository is set up already`. Otherwise it sets up:

- **Beads**: `bd init` where the repository has no `.beads/`, as [above](#set-up-a-project). It never installs `bd`: without it the run doesn't start, `Required command not found: bd` (exit code 2).
- **The worker prompt** from the template, and `.orchestra/.gitignore`.
- **The runners** `scripts/check-fast.sh` and `scripts/check-full.sh`, checking nothing yet, or, where the project has a `scripts/check.sh`, calling it as `init` does: the breakdown's first ticket, the [environment setup](running.md#the-breakdown), scaffolds the project, wires its checks into them and sets `"setup"`.
- **`settings.json`** with the concurrency `-c` (or `ORCHESTRA_CONCURRENT`) gives, else 1, and `"mcp_servers": []`: workers get no MCP servers (the `START` line says `MCP servers: none`).

No test work is filed, no skill or verifier written, and `.gitattributes` is left alone. The run then commits what it wrote, the files whose `git status` the setup changed, with the spec, as `orchestra: set up for spec <name>`: the repository's first commit where it has none, on the branch `HEAD` names. bd 1.3 commits its own files first, as `bd init: initialize beads issue tracking`. It says:

```
orchestra init hasn't set this repository up: setting it up as init does without a terminal
setting Beads up here: bd init --non-interactive --role maintainer --init-if-missing
  - Beads: ran bd init (maintainer, not contributing to someone else's repo; auto-export off); bd committed .agents/, .beads/, …
  - worker prompt: wrote .orchestra/worker-prompt.md from the template
  - .gitignore: the log, reports and per-ticket files stay out of git
  - check-fast: wrote scripts/check-fast.sh: it checks nothing yet (--check-fast "<command>" gives it one)
  - check-full: wrote scripts/check-full.sh: it checks nothing yet (--check-full "<command>" gives it one)
  - settings: 1 at the same time · …
  - MCP servers: none: workers get no MCP servers (…)
committed the setup with the spec .orchestra/specs/shop.md as 4e6924256897 (6 files)
the spec .orchestra/specs/shop.md is committed already (sha256 bba415566a7b)
```

The log has `SPEC: setting up <repo>, which orchestra init hasn't, as init does without a terminal`, a `SPEC: setup: <step>: <detail>` line for each step, and `SPEC: committed the setup with the spec <path> as <commit> (6 files)`. Outside a git repository the run says `Not inside a git repository: cd into the project first, or for a new one, start it with: git init` (exit code 2). Uncommitted changes in the main checkout, besides the spec's own file, stop it with exit code 5 before anything is set up. A setup that fails leaves what it wrote uncommitted, for you to look at with `git status` (`orchestra init sets the repository up with you.`) and ends the run (`SPEC: not set up: <why>` in the log): `bd init` or the commit failing with exit code 4, anything else with 2. Ctrl+C stops it with nothing committed (exit code 130; `SPEC: stopped while setting the repository up`); once it has started writing the worker prompt, the runners and the settings, it writes them all first, so that the next run doesn't take a setup half written for one done. Run `orchestra init` afterwards, between runs, for what the setup leaves out: the scout, the checks you choose, the MCP servers workers get, the verifier.

## The ticket prefix

Ticket IDs read `<prefix>-<hash>`, such as `orchestra-74b2.31`, and name every branch (`wt/<id>`), worktree, tab, the dashboard's rows and the log's lines: a long folder name makes long IDs everywhere. **Checks** ends with **Ticket prefix**, prefilled with the prefix Beads has (`bd config get issue_prefix`) or, in a repository without `.beads/`, with the one `bd init` would use, the folder's name; Enter, or a field left empty, keeps it. A new prefix takes lowercase letters, digits and hyphens, starting with a letter, as `bd` requires; the form refuses another, as `--prefix` does (exit 2). Type it without the trailing hyphen `bd rename-prefix` wants (`orc`, not `orc-`; one typed is dropped). `--prefix name` sets it without asking; without a terminal or the flag, the prefix is kept and not shown.

- **A new Beads** gets it from `bd init --prefix <name>`, which `init` runs after the form (the summary: `ticket prefix  orc, for the new Beads`).
- **An existing Beads** whose prefix changes has every ticket renamed with `bd rename-prefix <name>-`, which rewrites each ticket's ID and every mention of one in the tickets' fields. The form first asks to confirm, naming how many tickets and an ID renamed (**Rename 12 tickets, orchestra-74b2.31 → orc-74b2.31?**), answered no unless you say yes; `--prefix` is the consent. The summary says `orc (was orchestra), 12 tickets renamed`, or that the prefix was kept.

Nothing outside Beads is renamed, so the rename is refused while something still names the old IDs: a ticket not closed that has a `wt/<id>` branch (and with it, its worktree), workers the last run left in `.orchestra/run/state.json`, which the next run carries on with, and tickets labelled `unmerged`, whose `unmerged_fork` names their branch. The form then says the prefix stays as it is for now and why, and refuses a new one; `--prefix` exits with code 2 and nothing changed (`orchestra init: --prefix: the tickets can't be renamed from orchestra to orc while …`). Finish those first (a run merges or sets aside its tickets), then run `init` again. `init` checks again once the form is answered, before it renames anything.

## The checks

A project has two checks, each a shell script `init` writes in `scripts/` and the project then owns:

- **`scripts/check-fast.sh`**, the merge check: orchestra runs it on every finished ticket before it merges, rebased onto work merged while it ran or not, and hands a ticket whose change breaks it back to its worker. Workers leave it to orchestra: they check only what their change touches, each suite on part of the project as the worker prompt says (see [Worker prompt](workers.md#worker-prompt)). `settings.json` names it as `check_fast`, with `check_fast_timeout` (default 30m; `--check-timeout` on a run overrides it).
- **`scripts/check-full.sh`**, everything: it runs `scripts/check-fast.sh` first, then the slower suites. orchestra runs it once at the end of a run that merged a ticket ([The full check](running.md#the-full-check)). `settings.json` names it as `check_full`, with `check_full_timeout` (default 60m; `--check-full-timeout` on a run overrides it).

A project whose workers check their own change with a command of its own, such as a script that checks only what the branch changed, can name it in `settings.json` as `check_own` (`"check_own": "scripts/check-own.sh"`; `init` writes none). orchestra never runs it, but a worker's standing rules name it as the check to run once with its whole output kept, `scripts/check-own.sh > .orchestra/run/worker-check.log 2>&1; echo "exit $?"`; without it they name `check_fast`. Like the other two checks' files, the files it names are left out of tickets' footprints.

A runner lists the suites' commands, one line each, run from the repository's root, each in a subshell, `(` and `)` on the lines around it, so that a command failing anywhere in a suite (`cd web && npm test`) fails the runner and its `cd` doesn't carry over to the next suite. Each is under a comment naming where the suite was found, after a line printing `SUITE: <its name>` (or its command), which names the suite a failing full check failed in. Each framework finds its own test files, so a new test in an existing suite needs no edit there; a new suite is a new line. A suite that can't run in two worktrees at once (a fixed port, a shared database) runs between `lock <name>` and `unlock`: checks running at once in several worktrees take turns on it. The lock is a directory in the temp directory, named for the repository and the suite and holding its holder's PID, taken over once that process is gone (macOS has no `flock`). A runner with no suites is just `exit 0`, with a comment saying it checks nothing yet; `check-full.sh` with no suites of its own runs `check-fast.sh`. An existing `scripts/check.sh` is never edited: `check-fast.sh` calls it as a suite, the line `scripts/check.sh`, and `init` without a check command finds it there.

A check that reruns a failed test, and passes when the rerun does, should say so with a line starting with `FLAKY:` for each such test, such as `FLAKY: ./internal/dispatch TestMerge`. The ticket merges, as the check passed, and orchestra warns of each `FLAKY:` line, naming the ticket, in the log, the dashboard, the event stream and the run report: a test that passes only on a rerun is a bug to fix. When the merge check fails, its whole output is kept in the ticket's worktree, in `.orchestra/run/check.log`, which the `CHECKS_FAILED` line names; the run report says what failed and whether in a directory the ticket's own commits change ([Organs](organs.md#organs)), and once another ticket merges, the ticket is rebased and checked once more ([Several tickets at once](running.md#several-tickets-at-once)). A full check that fails keeps its output in `.orchestra/run/check-full.log` and files a P2 ticket for the suite it failed in, named by the last `SUITE:` line ([The full check](running.md#the-full-check)).

`--check-fast "<command>"` writes `check-fast.sh` with that command (`""`: the runner that checks nothing), and `--check-full "<command>"` writes `check-full.sh` with it after `check-fast.sh`. A command that is just the runner (`scripts/check-fast.sh`, run by `sh` or `bash`, or by its absolute or `$PWD/` path) keeps the runner as it is. A runner never runs itself: a suite whose command runs `scripts/check-fast.sh` or `scripts/check-full.sh` anywhere in it, whether from a flag, the form or the scout, is left out, with a note saying so (`check-full.sh` runs `check-fast.sh` first already). Run again, `init` leaves a runner that `settings.json` already names as it is. Where it would write a runner that differs from the one there, it says so and keeps the one there, unless its flag was given or stage 2's question replaces it. A project set up before the runners keeps working: its `check` and `check_timeout` are read as `check_fast` and `check_fast_timeout`, and `init` writes its check command into `check-fast.sh` and the settings under the new names.

A ticket's new worktree has nothing installed in it, and a ticket rebased over another that bumped a dependency would be checked against the old dependencies. `"setup"` in `settings.json` is the command that installs them in a worktree, such as `"npm ci"`, `"pnpm install --frozen-lockfile"`, `"uv sync"` or `"bundle install"`. orchestra runs it in each ticket's new worktree before its worker starts, so every worker starts with the dependencies installed and its standing rules tell it not to install them again unless it changes a file the setup reads, and again in a reused worktree whose last setup failed or didn't finish, or whose dependency files changed since; a setup that fails there starts no worker (`SETUP_FAILED`), and the ticket waits in the queue. It runs it in a rebased ticket's worktree before `check_fast` when a dependency manifest or lockfile changed since the worktree's dependencies were last set up ([Several tickets at once](running.md#several-tickets-at-once)), and always in the full check's new worktree before `check_full` ([The full check](running.md#the-full-check)). In a ticket's worktree it may run as long as the merge check (`check_fast_timeout`), and before `check_full` within the full check's own time limit. It should install exactly what the lockfile says, without asking anything and without changing tracked files (a worktree left with changes to files it tracks can't be rebased: `DIRTY_WORKTREE`): a frozen or `ci` install rather than one that updates the lockfile. A spec's [environment setup ticket](running.md#the-breakdown) sets `"setup"` and `"setup_files"` for the tickets after it: a merge that changes them in the base's `settings.json` has the run use them from then on. `"setup_files"` lists the files the setup reads, which decide when it runs again, as globs matched against a file's name, or against its path from the repository's top when the glob has a slash (`"web/package-lock.json"`, `"apps/*/yarn.lock"`). Without it, they are the usual manifests and lockfiles: `package.json`, `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lock`, `bun.lockb`, `go.mod`, `go.sum`, `Cargo.toml`, `Cargo.lock`, `pyproject.toml`, `poetry.lock`, `uv.lock`, `Pipfile`, `Pipfile.lock`, `requirements*.txt`, `Gemfile`, `Gemfile.lock`, `composer.json`, `composer.lock`, `mix.exs`, `mix.lock`, `pubspec.yaml` and `pubspec.lock`. Where the repository's top has a lockfile and `settings.json` no `"setup"`, `init`'s **Checks** step offers the command for it, which you can change or empty: `npm ci` for `package-lock.json`, `pnpm install --frozen-lockfile` for `pnpm-lock.yaml`, `yarn install --frozen-lockfile` for `yarn.lock`, `uv sync` for `uv.lock`, `poetry install` for `poetry.lock` and `bundle install` for `Gemfile.lock`; one per ecosystem, joined with `&&` (`npm ci && bundle install`), the first in that list where an ecosystem has two. `--setup "<command>"` sets it without asking and `--setup ""` removes it; without either, `init` keeps a setup command that is there, and without a terminal it writes none and its summary names the flag. `"setup_files"` is for you to add by hand, as are the setup command of a lockfile in a subfolder and of an ecosystem not listed; commit `settings.json` afterwards.

```json
{
  "check_fast": "scripts/check-fast.sh",
  "setup": "npm ci",
  "setup_files": ["package-lock.json"]
}
```

## The machine's requirements

A project needs more of its machine than its dependencies: a language runtime, a package manager, a database or Docker running, a CLI the build calls, a permission granted. The setup installs a worktree's dependencies; `"requires"` in `settings.json` lists what the machine itself must have, each with a check, so that every new contributor's machine, and every run, finds out what is missing before a ticket fails on it:

```json
"requires": [
  {"name": "bun", "check": "bun --version", "install": "curl -fsSL https://bun.sh/install | bash"},
  {"name": "jq", "check": "command -v jq", "install": "brew install jq", "platforms": ["darwin"]},
  {"name": "docker", "check": "docker info", "manual": "Install and start Docker Desktop"}
]
```

Each entry has a `name` (letters, digits and `.` `_` `+` `-`), a `check`, a shell command run in the main checkout that exits 0 when the requirement is met, and either an `install`, a command that meets it, or `manual`, what a person must do instead: a GUI installer, a licence, a permission to grant, a service to start. `platforms` (`darwin`, `linux`) limits it to those systems; without it, it applies on both. An install runs without a terminal, its input empty, and never as root: one that runs `sudo` (or `su`, `doas`, `pkexec`) anywhere in it is refused as the settings load, a setup problem like any other, and goes in `manual` instead. So is an entry without a name, with the name of another, without a check, or with neither an install nor `manual` or both.

orchestra checks the list at each run's start, before its first ticket ([Run](running.md#run)), in `orchestra init` and with `orchestra requires`. It runs every check side by side, each within a minute; for a check that fails and has an install, it runs the install, one at a time, within the merge check's time limit (`check_fast_timeout`), its whole output kept in the main checkout's `.orchestra/run/requires-<name>.log`, then checks again. What is still missing stops a run before its first ticket with one line naming each with its manual step, or why its install failed and where its output is, exit code 2:

```
REQUIREMENTS_MISSING: docker (Install and start Docker Desktop); jq ('brew install jq' failed: exit status 1; its output is in <repo>/.orchestra/run/requires-jq.log); meet them (each entry of 'requires' in .orchestra/settings.json says how), then run again
```

`orchestra init` lists each requirement among what the machine needs, after `bd`, Beads, the terminal and `claude`: met, installed with its install, missing with what to do, or not checked on another system; a missing one is in its next steps, and `init` goes on with the rest. `orchestra requires` checks the list alone, as a run would, and prints each entry's state, a line each (`jq: met`, `bun: installed with '…'`, `docker: missing: Install and start Docker Desktop`), then the `REQUIREMENTS_MISSING` line when something is still missing, exit code 2 (0 once everything is met); `--no-install` checks without installing anything. A ticket that adds a tool adds its entry, committed with the ticket, and installs it with that entry's install, never by hand (the worker prompt and the workers' standing rules say so): a merge that changes the list in the base's `settings.json` has the run check it again before the next ticket starts ([Run](running.md#run)).

People read the README to set a machine up, and orchestra reads the list: written apart, they drift. So the README's section on what to install is the list itself, as Markdown: `orchestra requires --markdown` prints it (a `What to install` heading, then each entry with its check and its install, or `by hand:` and its manual step, and the systems it is limited to), between the lines `<!-- orchestra:requires -->` and `<!-- /orchestra:requires -->`, and `orchestra requires --readme` writes it into `README.md`, replacing what is between those lines or adding the section at the README's end, for you to commit; neither checks anything. `orchestra init` writes it into a `README.md` that has none, when the list has entries, and brings one that differs up to date, as a step to commit (`README: wrote README.md's section on what to install from the requires list, …`); it writes no `README.md` where there is none, and leaves alone one whose markers don't pair up, saying so. Each run's start says when the section differs from the list, or the README has none though the list has entries, and goes on without touching the main checkout: `README_STALE: README.md's section on what to install differs from the requires list in .orchestra/settings.json: orchestra requires --readme writes it, to commit`. A worker in a project with a `README.md` is told that a ticket that changes the list runs `orchestra requires --readme` and commits the section with the list.

## Choosing the checks

Stage 2 of the form starts with the scout, the one organ that reads the repository itself (with Read, Glob and Grep only, confined to it): it looks where projects say how they test (package manifests and their scripts, Makefiles and task runners, CI workflows, test configs and the project's own scripts) and lists each suite with its command, how to run it on part of the project where its tool allows it (`go test ./<package>/...`, `pytest <paths>`), which `init` writes into the worker prompt, where it was found, whether it is fast (unit tests, lint, type checks, a smoke e2e suite) or full, whether it can run in two worktrees at once, and what it needs (a service, a browser, credentials). An existing `scripts/check.sh` comes first, as a fast suite. It starts only when stage 2 is reached, under a spinner with the time it has taken; it may take up to 5 minutes, and Esc skips it. The scout uses `--organ-model`'s and `--organ-effort`'s variables, `ORGAN_MODEL` and `ORGAN_EFFORT` (else the settings' `organ_effort`; medium by default).

Then one of three choices, the one that fits what the scout found selected:

1. **Use them as they are**, selected when the scout found suites. Two checklists follow, each suite with its command, where it was found and what it needs: **On every merge (check-fast)**, every suite, those the scout calls fast ticked; and **At the end of a run (check-full)**, the other suites, all ticked. A suite ticked in both runs in `check-fast.sh` only, since `check-full.sh` runs that first. A suite that can't run in two worktrees at once takes turns (see [The checks](#the-checks)). Last, unticked, **Also file tickets for untested areas**.
2. **Create from scratch with the create-check-suite skill**, selected when the scout found none. The runners check nothing for now (`exit 0`); the skill sets the tests up in a ticket of their own (see [The test work init files](#the-test-work-init-files)).
3. **Manual**, selected when the scout failed (`claude` missing, an error, its time limit) or was skipped, with the reason shown: one line, the command `check-fast.sh` runs, pre-filled from the settings or an existing prompt. Empty writes a runner that checks nothing, or keeps a runner that is there as it is.

Where `init` runs again and a runner there differs from what the choice would write, stage 2 shows the commands that runner runs and asks whether to keep it (the default) or replace it; the same goes for a copy of the create-check-suite skill that differs from orchestra's, where the choice needs the skill. Without a terminal there is no scout and no stage 2: the flags decide.

### The test work init files

After writing its files, `init` files with `bd create` the work the choice calls for, each ticket labelled `orchestra-tests`, and its summary lists each ticket it filed:

- **Create from scratch**: an epic, *The project's tests*, and under it a P1 ticket labelled `solo`, *Set up the test harness and a first suite*, which asks a worker to use the create-check-suite skill for a harness and smoke tests added to the runners, both runners passing on the branch `init` ran on, `FEATURES.md`, and one P3 ticket per untested area under the epic. P1 and solo, it runs first and alone, so nothing merges while the runners still check nothing.
- **Use them as they are**: a P1 ticket labelled `solo`, *Make scripts/check-fast.sh and scripts/check-full.sh pass on main* (the branch `init` ran on): run them, fix what fails or skip it naming a bug ticket filed for it, and record how long each takes. With **Also file tickets for untested areas**, it goes under the epic, beside *Map the untested areas* (P2), which waits for it: the skill's `FEATURES.md` and one P3 ticket per untested area.
- **Manual**: nothing.

Run again, `init` files only what isn't open already: a ticket labelled `orchestra-tests` with the same title that isn't closed is kept (the summary says so) and serves as the parent or the ticket waited for. One that is closed is filed again. Where bd fails (Beads isn't set up, bd is missing), the summary says which tickets weren't filed and why; the files `init` wrote stand, and running it again files them.

## The create-check-suite skill

Where the project's tests are to be created from scratch, or its untested areas to be ticketed (stage 2's "Create from scratch", or "Use them as they are" with "Also file tickets for untested areas"), the tickets `init` files ask the workers to use the create-check-suite skill: it sets up a harness and deterministic suites in the project's own frameworks, wires them into the runners, maps the features in `FEATURES.md` and files a ticket for each untested area. orchestra carries the skill in its binary, and `init` writes it into the project's skill folder for the workers' agent, to be committed with the rest of its files, since a ticket's worktree has only what is committed:

```
.claude/skills/create-check-suite/   committed: for Claude Code workers (the default)
.agents/skills/create-check-suite/   committed: for Codex workers
```

`--agent codex` names the workers' agent, as on a run; without it `init` reads `AGENT_KIND`, else takes `claude`. For an agent whose skill folder orchestra doesn't know, it says so and installs nothing. Run again, it leaves a copy that is the same as its own. A copy that differs is kept, and `init` says so, unless replacing it is chosen; replacing it writes the skill's files over those there and leaves any file of the project's own in the folder. Without a terminal there is no stage 2, so no test work is filed and the skill isn't installed.

## The verifier

A worker runs the checks before it closes its ticket, but it grades work it wrote. Stage 2 ends by asking **Add a verification step for workers** (offered as yes), once the scout has said what the project is built with: its languages, frameworks, test frameworks and linters, which the question names. Yes writes `.claude/agents/verifier.md`, a Claude Code subagent with Read, Grep, Glob and Bash that checks a ticket's change against the ticket in a fresh context, seeing the ticket and the diff but not the reasoning behind them. It is told the stack, the commands `check-fast.sh` and `check-full.sh` run, and how to run each suite on what a change touches, the lines the worker prompt gives (the scout's command for part of the project, else the whole suite; a suite that can't run in two worktrees at once left to the merge check); it reads the ticket with `bd show`, the commits that name it, takes the worker's passing checks as they stand when the worker names the commit they passed at and the commands it ran there, that commit is `HEAD` and `git status --porcelain` is empty, quoting the output file the worker names, and runs only a suite they leave out that covers the change; otherwise it runs the suites on what the change touches itself. It leaves the whole suite to the merge check and the full check, as workers do. In a worker, whose settings raise Bash's default timeout to the merge check's limit (`check_fast_timeout`; see [Runs that share a machine](running.md#runs-that-share-a-machine)), it passes Bash no timeout, as one of its own would shorten that default, and Bash waits on each check in the foreground. Where Bash's description gives no default that long, it gives a check Bash's `timeout: 600000`, its maximum of 10 minutes, and runs one that can take longer, as the merge check may, in the background, its output and exit status in a file, waiting on it in the foreground with a loop of short waits (`until grep -q '^exit ' <file>; do sleep 10; done`), as Bash refuses a long `sleep` and the verifier has no Monitor. It checks each requirement has a test that would fail without the change and that nothing outside the ticket changed, checks again each finding of the earlier rounds on the same ticket that the worker gives it, saying in a line that starts `DISAGREES WITH ROUND <n>:` where it judges otherwise than one and why, changes nothing itself, and answers PASS or FAIL with each gap's `file:line` and evidence, leaving out style preferences. `init` also appends a **Verify** section to `.orchestra/worker-prompt.md`: before closing, once its checks pass, the worker runs the verifier in the foreground with the ticket's ID, the commit at which its checks passed, the commands it ran there, and the file their output is in where it kept one; it fixes the gaps that affect correctness or the ticket's requirements, and asks again, giving a later round the earlier rounds' verdicts and the gaps they raised (still nothing of its reasoning), so that each round doesn't start blind; where a round disagrees with an earlier one, it notes both rounds' findings on the ticket and asks the maintainer which holds rather than go round again; after three rounds that still fail, it notes the findings on the ticket and closes it only when it judges them outside the ticket's requirements, else defers it. Each ticket then costs a subagent's run too. Commit `.claude/agents/verifier.md` with the rest: a ticket's worktree has only what is committed.

`--verifier` adds it without asking, `--verifier=false` declines. Run again, `init` doesn't ask where the project has the verifier and a worker prompt that runs it; a `verifier.md` that is there is kept as it is (remove it for one written afresh), and the section isn't appended twice. So a verifier written before verifiers checked only what a change touches, which takes the worker's passing `check-fast.sh` or runs it itself, stays as it is: for the new one, run `orchestra init --update`, which rewrites the sections of the verifier and of the worker prompt's **Verify** section that changed (see [Taking template changes](workers.md#taking-template-changes)); or remove `.claude/agents/verifier.md` and the worker prompt's **Verify** section and run `orchestra init --verifier` again, or by hand, copy the last bullet of Its checks and step 3 of [`internal/project/verifier.md`](../internal/project/verifier.md) over the verifier's, writing under the bullet how to run each of your suites on part of the project, and the Verify section's first two bullets from `verifierSection` in [`internal/project/verifier.go`](../internal/project/verifier.go) over the worker prompt's. orchestra writes subagents for Claude Code workers only: with `--agent codex` it isn't offered. Without a terminal it isn't asked, and the summary says `--verifier` adds it.
