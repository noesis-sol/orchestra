# Workers

What a worker starts with, the worker prompt, the MCP servers workers get, the permission mode they start in, the tools they go without, their hooks and run files, workers in tmux and cmux, and other agent kinds. Back to the [README](../README.md).

## What a worker starts with

Each worker starts in a tab of its own (Herdr's, a tmux window or a cmux workspace) with:

- **A worktree of its own** under the worktree root, named with its ticket's ID, on the branch `wt/<id>`: cut from the branch the run merges into, or, for a ticket that comes back, the earlier attempt's worktree and branch, rebased onto that branch first (see [Several tickets at once](running.md#several-tickets-at-once)).
- **The project's dependencies installed.** With `"setup"` in `settings.json` (such as `"npm ci"`), orchestra runs it in a new worktree before the worker starts there, and in a reused one when its last setup failed or didn't finish, or a file it reads changed since; a setup that fails starts no worker (`SETUP_FAILED`, [Several tickets at once](running.md#several-tickets-at-once)). The worker's standing rules name the command, so that it doesn't install the dependencies again itself: `This worktree's dependencies are installed with 'npm ci'. Run it again only after changing a file it reads, such as a manifest or a lockfile.` Without `"setup"`, a worker installs what it needs itself.
- **The project's toolchain**, which is the machine's, not the worktree's: a spec's breakdown files an [environment setup ticket](running.md#the-breakdown) first, which installs the tools the spec needs and sets `"setup"`, and every other ticket waits for it. What the machine must have is the project's `"requires"` list ([The machine's requirements](setup.md#the-machines-requirements)), which each run checks before its first ticket; the worker's standing rules name it with the entries it has (`The project's requires list is "requires" in .orchestra/settings.json, which has jq, docker now.`), and, where its prompt doesn't say so already, that a ticket needing a tool, service or permission the list lacks adds an entry for it, commits it with the ticket and installs it with that entry's own install command, never by hand outside the list, a manual step being a question for the maintainer. In a project with a `README.md`, they add that a ticket that changes the list runs `orchestra requires --readme`, which writes the README's section on what to install from it, and commits that with the list.
- **Its prompt** (below): the standing rules in its system prompt, and a first message for this start.
- **The MCP servers** the project chose ([MCP servers for workers](#mcp-servers-for-workers)), the [permission mode](#permission-mode) and, for Claude workers, the hooks that report what it does (below).
- **For Claude workers, only the tools they use** ([Tools left out](#tools-left-out)): not Artifact, ListAgents, ReportFindings, ScheduleWakeup, SendFeedback or Workflow, and not Skill, with the listing of your skills, unless the project has skills of its own.

## Worker prompt

Each worker gets the prompt at `--prompt` / `WORKER_PROMPT` (default `.orchestra/worker-prompt.md`), with every `TICKET_ID` replaced by its ticket. In a `--ticket` run, orchestra adds a line asking the worker to file follow-ups that belong to the work as children of that ticket, so they join the run (not for the ticket's own worker, which runs last). A worker started on a branch an earlier attempt left work on (a ticket that comes back) is told what it left, commits `<base>` doesn't have (`git log <base>..HEAD`) or uncommitted changes (`git status`), and to build on them or revert them deliberately rather than start over. `orchestra init` writes it from [`internal/project/worker-prompt.md`](../internal/project/worker-prompt.md), which is built into the binary. Each rule prevents a way a run goes wrong:

- **Own worktree, never push, the orchestrator merges.** Workers can't disturb each other or the branch that finished tickets land on.
- **Commit with the ticket ID, closing only when the checks pass.** A ticket is merged only if a commit names it and its worktree is clean. One closed with no commits of its own and a clean worktree, as when tickets merged before it did what it was about, has nothing to merge: its worktree, branch and tab are removed as after a merge. So has one whose commits, taken together, change nothing (a commit and its revert), or whose rebase onto the branch drops them all, the branch having their changes already.
- **Don't add where every ticket adds.** New tests go in a new file named after the feature, new struct fields, constants and helpers next to the code they belong to, and a changelog entry as new lines (merged by union, above). Two tickets that each append at the end of the same file conflict when the second is rebased, though neither changed the other's lines.
- **Block follow-ups on the ticket they build on.** A follow-up that changes or builds on what its worker's ticket adds is filed `--deps blocked-by:<ticket>`, so it doesn't start from a base without that ticket's code; `bd` keeps one link per pair of tickets, so not `discovered-from` as well. One independent of the ticket's changes may stay `discovered-from`, which orchestra also holds until its source merges (see [Several tickets at once](running.md#several-tickets-at-once)).
- **Link follow-ups that overlap.** A follow-up that touches the same files or functions as another open ticket is linked to it (`--deps blocked-by:<id>` to wait for it, or `related:<id>`), and one that restructures code most tickets touch is labelled `solo`, so the two don't run side by side.
- **Check your own change; the merge check tests everything.** Before closing, a worker checks what its change touches: each suite on the modules or packages it changes and their tests, existing ones included, the slower suites too where they cover it, and lint and type checks on the files it changed. `orchestra init` writes into the prompt each suite the runners run, with how the scout said to run it on part of the project (`go test ./<package>/...`, `pytest <paths>`, `npx eslint <files>`), or its whole command where its tool can't (a slower one where the change touches what it covers); a suite that can't run in two worktrees at once is left to the merge check, which takes turns on it. Where `init` doesn't know the suites (runners kept as they are), the prompt says to run each command the runners list on part of the project where its tool allows it, and whole where it doesn't. The whole suite is orchestra's: its merge check, `scripts/check-fast.sh`, runs on every ticket before it merges and hands back a ticket whose change breaks something its worker didn't consider ([A failing check goes back to its worker too](running.md#several-tickets-at-once)), and the full check, `scripts/check-full.sh`, runs every suite once at the end of a run. Workers that ran the whole fast suite before closing spent about a third of their time on it, about twice a ticket, and slowed every other worker's checks. Where the project has test suites, a ticket that changes behaviour adds or updates tests in them; a new test framework is a ticket of its own.
- **Machine tools go in the requires list.** A ticket that needs a tool, service or permission of the machine that `"requires"` in `.orchestra/settings.json` doesn't have adds an entry for it (a name, a check, and an install without `sudo` or a manual step), commits it with the ticket, and installs it with that entry's own install command, never by hand outside the list; a manual step is asked of the maintainer as a question. Workers installed what they found missing by hand (Homebrew packages, Docker Desktop started), and the next machine had none of it.
- **Checks in the foreground.** A worker waiting on a background command looks idle, and an idle worker with its ticket still open stops the run (`PAUSED`).
- **Work unattended.** Nobody reads a worker's turns as they happen, so a turn that ends without a tool call ends its work. The prompt's last section, Working unattended, after Close, asks it not to end a turn with a summary announcing its next step, an offer to go on, a choice that doesn't block the rest, or a report because the turn has been long or a part is done, and to delete an invitation to redirect it or an offer to wait; it keeps the stops it wants to the Close section: DONE, a question, a wait for another ticket to merge, a deferral. It tells the worker that its context is compacted as it fills, so a long conversation is no reason to cut work short, and to keep the ticket's notes current. A Claude worker whose turn ends anyway with its ticket still in progress, without a question or a deferral, is told so and to continue, at most twice (`told it to continue (1 of 2)` in the log), as is one idle at its prompt after you refused a permission prompt it showed (see the hooks below); after that the 10-minute idle grace and `PAUSED` apply as before.
- **Wait for work not merged yet.** A ticket that needs another ticket's work, not on the worker's base yet, isn't built on that ticket's branch or a copy of its code. The worker leaves nothing committed or changed, links the other ticket as a blocker (`bd dep add <ticket> <other>`), reopens its ticket with a note (`bd update <ticket> --status open --append-notes "Waiting on <other> to merge: …"`) and stops. orchestra removes its worktree, branch and tab, says `WAITS_FOR_MERGE`, and starts it afresh once the other ticket merges (see [Several tickets at once](running.md#several-tickets-at-once)); a ticket stopped with commits of its own is deferred for review instead.
- **Stop only your own processes, by PID.** Workers run the same test binaries side by side, so a `pkill -f dispatch.test` from one ends another worker's check with `signal: terminated`.
- **Leave throwaway files; never `rm` a variable or a glob.** Claude Code's built-in safety check holds a removal whose target it can't resolve (`rm -f $S/*.mp4`, `rm -f $f`, `rm -f *`) for a person, whatever the settings allow, and a prompt left unanswered denies it, so the ticket waits on the maintainer for a cleanup it never needed. Workers and the verifier put throwaway files in a new folder of their scratchpad and leave them there, overwrite (`-y`, `>`) or write to a new name rather than delete first, and remove a file that must go by its literal absolute path; a worker tells the subagents it starts the same.
- **Close, and let the batch PR run CI.** A ticket whose change only CI can verify (a workflow, a platform the local checks don't cover) is closed once the local checks pass, with an "Awaits CI" note. The batch goes to the main branch through a pull request that runs every CI job, so each ticket needn't wait for its own.
- **Ask, don't wait.** A ticket that needs the maintainer's decision gets a question ticket labelled `human` that blocks it, and so does another ticket that needs one, a follow-up its worker files or one it names: the worker files the question blocking that ticket and linked to its own, where it was asked (`--deps 'blocks:<that ticket>,discovered-from:<its ticket>'`), so the answer talk shows both, and goes on with its own, since a decision left in its final message is read by nobody, and that ticket's worker makes it instead. Every question gives 2 to 4 options, each a short label and a one-line trade-off, one of them recommended, in its description and in its metadata, in the same order (`{"options": [{"label": …, "description": …}, …], "recommended": <its index, from 0>}`), so that they can be offered as choices. The orchestrator never hands a question to a worker; it shows the ticket as **? for you**, and the run goes on. A Claude worker that files its question but leaves its ticket in progress settles at the end of that turn (`A settled: Stop hook at 20:48:39, waiting on Q`), and orchestra reopens the ticket for it; without hooks, that waits out the 10-minute idle grace. Answer in the [answer talk](dashboard.md#the-answer-talk), which the dashboard opens beside itself (**a** goes to it), or with `orchestra answer` on any terminal; on the command line alone, `bd human respond <question> --response "…"` does it. The ticket then returns to the queue with its branch rebased onto the current one. If you answer in the worker's tab instead and it carries on, orchestra adopts that worker and merges its work, whether the ticket returns through `bd ready` or not: the worker claims it again, and `bd ready` lists only open tickets, so orchestra also reads each asked ticket every 30 seconds and before the run ends. One in progress again (while the run takes tickets) or closed (unless the run stops for a failure) is adopted at once, beside the running tickets even beyond `--concurrent`, since its worker is already at work, rather than waiting for a free slot: `ANSWERED: <id> was closed in tab <tab> after <question> (…), so its worker is adopted`. A worker still idle there once its question is answered is told so, and carries on with what it knows; one gone from its tab by then has its session resumed in a new tab (see the hooks below). An asked ticket its worker defers in its tab shows as deferred, and one in progress whose worker has gone from its tab has the worker's session resumed in a new tab (see the hooks below), or, without one, stops the run with `PAUSED` and a note on the ticket. As the run ends, an asked ticket left in progress, or closed but unmerged because the run stopped (`ASKED_UNMERGED`), is labelled `unmerged`, as a ticket left running is, and left for the next run, which merges a closed one. The log says `ANSWERED`, and the ticket's row goes back to working. Answering in the tab works between runs too: the next run carries each asked ticket over (see [Several tickets at once](running.md#several-tickets-at-once)), merges it if its worker closed it meanwhile, adopts the worker if it is at work on it again, and otherwise tells it, once the question is answered, to carry on.

A project set up before the prompt had **Leave throwaway files** keeps its prompt and verifier too: copy the bullet that starts `Put throwaway files` from [`internal/project/worker-prompt.md`](../internal/project/worker-prompt.md) after the one on `pkill`, and the one from [`internal/project/verifier.md`](../internal/project/verifier.md) into the Rules of `.claude/agents/verifier.md`.

A project set up before workers checked only their own change keeps its prompt, whose workers run `scripts/check-fast.sh`, the whole merge check, before they close: `orchestra init` never replaces it without `--force`, and `orchestra init --update` takes the new opening and Close (above). `orchestra init --force` writes the template afresh, with the new check section and, in a terminal, the suites chosen under **Use them as they are** with the scout's commands for part of the project; it drops changes of your own and the **Verify** section, which `init` then offers again. By hand, replace the bullets that start `Check your work with` and `When your change touches` with the template's two that start `Check your own change` and `Leave the whole suite`, writing under the first how to run each of your suites on part of the project, and in Close, `your checks pass` where it names the check.

A project set up before the prompt had **Block follow-ups on the ticket they build on** and **Wait for work not merged yet** keeps its prompt: `orchestra init` never replaces it without `--force`. To add them, copy from [`internal/project/worker-prompt.md`](../internal/project/worker-prompt.md) the three lines on a follow-up that builds on the ticket (after `Details go in the description.`), the Close bullet that starts `If the ticket needs work from another ticket`, and `a wait for another ticket to merge` among Working unattended's stops. `orchestra init --force` writes the whole template afresh instead, for a prompt with no changes of your own.

A Claude worker gets the prompt in two parts. Its standing rules, the worker prompt with the `--ticket` line, the line naming the setup command (above), the time-limit line, one on giving a check its time (its settings set Bash's default timeout to the merge check's limit, which the line names, so it runs every check in the foreground and passes Bash no timeout, as a shorter one moves the check to the background when it runs out, and never waits on a check in the background or with a long `sleep`, which Bash refuses; a worker whose settings can't be written is told instead to pass Bash's `timeout: 600000`, its maximum of 10 minutes, and to run a check that can take longer in the background, its exit status in its output file, waited on with Monitor) and one on the usage limit (commit what you have and stop, without deferring or closing the ticket for it, to carry on after the reset), go in its system prompt: orchestra writes them to `.orchestra/run/rules.md` in its worktree and starts it with `--append-system-prompt-file` on that file. Claude Code sends the system prompt with every request, so the rules survive when a long ticket's conversation is compacted, while the summary that replaces its early messages may lose instructions given there: never push, the Close section's DONE, question and deferral, checks in the foreground, working unattended. Its first message carries only what belongs to this start: its ticket, a pointer to the rules, and what an earlier attempt left. A worker whose session is resumed is given the rules again, as Claude Code keeps no system prompt with a session.

A ticket broken down from a spec ([A whole app from a spec](running.md#a-whole-app-from-a-spec)) carries the metadata `spec`, the committed spec's path, and its worker is pointed to it: its first message adds, before what an earlier attempt left, `<id> is part of the spec at <path>: read the sections of it that <id> cites before you start, and treat the spec as settled.`, and the message a resumed worker gets ends with the same sentence, `carry on` in place of `start`. A worker of another kind gets it in its prompt too. The standing rules are the same for every ticket. A `spec` that isn't a path on one line is left out. If the rules can't be written, or Herdr refuses the argument, the worker gets the whole prompt as its first message, as workers of other kinds always do.

Claude workers are started with a one-line instruction to read `.orchestra/run/prompt.md` in their worktree, where `orchestra` writes that first message (kept out of git through the repository's `info/exclude`, as are the rules, so they're ignored even on a branch cut before `.orchestra/.gitignore` was committed). Herdr can't pass line breaks to a worker, and a prompt pasted into the input box can go unsubmitted. `--prompt-at-launch=false` pastes it instead.

Claude workers also start with `--settings .orchestra/run/hooks.json`: hooks, for that worker only, that record each tool it uses in `.orchestra/run/activity.json`. Each hook is orchestra's own binary, the one that launched the worker, run by its absolute path as `orchestra hook <event> <folder> <process>`, the process being the Claude Code that runs the hook (the shell's `$PPID`): it reads the hook's input as JSON and writes the records from the same Go types orchestra reads them with. `orchestra hook` is missing from `orchestra -h`, and runs only with `ORCHESTRA_HOOK=1`, which the hook's command sets; typed by hand, it says what it is and does nothing. A worker keeps the binary it was launched with: after `orchestra update` replaces it, the worker's hooks run the new one, and a binary that is gone, as `go run`'s once orchestra exits, leaves the worker reporting nothing. Each hook costs a process of orchestra's per event, about 8 ms on macOS and less on Linux, where the shell one-liners before it took 1–5 ms and 11–28 ms: a few milliseconds a tool call, next to the seconds a model's turn takes. A hook that can't write its record (say, the worker removed `.orchestra/run/`) leaves it unwritten and exits 0, so it never blocks the worker. That is how the dashboard tells `testing` (the check command or a test runner), `editing`, `reading` and `subagent` (its Agent tool) apart from plain `working`, without reading the worker's screen. It is also how `orchestra` knows a worker has finished: Herdr can show a worker as idle while it is still starting up, so a Claude worker counts as settled only at its Stop hook, the end of its turn (or its `StopFailure`, for a turn an API error ended: see below). While its last hook was a tool use it is mid-turn, whatever Herdr says, for up to 10 minutes (a turn interrupted ends with no hook). Without hooks (another agent kind), or before its first one, an idle worker gets 3 minutes from its start to claim its ticket before it counts as settled with the ticket still open. The log says what decided it, such as `A settled: Stop hook at 20:48:39`. One settled by those 10 minutes after a tool use also says who recorded it: `that record was written at 09:24:02 by tool Bash, session <id>, main agent, transcript <path>`, or the subagent's ID and type in place of `main agent`. Claude Code forks agents at the end of a turn (a prompt suggestion, say) that run the worker's `PreToolUse` hook and are then refused the tool, so a tool use with no turn of its own can replace the Stop in `activity.json`. So the Stop hook, and each prompt that starts a turn (`UserPromptSubmit`), also write `.orchestra/run/turn.json`, which no tool use does: a worker whose last record is a `PreToolUse` written after a Stop no prompt has followed, with no subagent running, has ended its turn at that Stop, and the log names the record: `A settled: Stop hook at 09:24:00; then a PreToolUse record with no turn of its own, written at 09:24:02 by tool Read, …`.

The hooks record three more things Claude Code tells them, which orchestra would otherwise have to guess:

- **Permission prompts.** When Claude Code asks to allow a tool (its `PermissionRequest` hook, which runs only when a prompt is about to show, not for a tool the worker's settings allow), the hook records the tool and its input in `activity.json`, as before a tool use. Herdr may show a worker waiting on the prompt as idle, which used to wait out the 10-minute idle grace and stop with `PAUSED`. Now, while Herdr shows it idle, blocked or done after such a record, the dashboard shows `permission — waiting for you` in red (`■ allow?` in the tickets table), the log says once `PERMISSION_PROMPT: A's worker waits on a permission prompt for Bash (rm -rf build) in tab 3; allow or deny it there` (a Bash command with a removal Claude Code's built-in safety check holds for a person, an `rm` whose target is a variable or a glob or a home, root or working directory, is named by that removal wherever it is in the command, rather than by its first 80 characters: `for Bash (rm -f $S/*.mp4), a removal Claude Code's built-in safety check holds for a person, which no allow rule skips, in tab 3`), and the wait counts as a blocked worker's: after 4 minutes the run stops with `BLOCKED >4min: tab 3 (A) needs attention: its worker waits on a permission prompt`. A worker that asked a question and, answered in its tab, waits on such a prompt when the run takes its ticket up again is adopted as it is and waited on the same way, never told the answer is in or to carry on: the message's Enter would answer the dialog, allowing the tool (`A's worker in tab 3 waits on a permission prompt with the ticket in_progress; adopting it rather than telling it Q is answered`). Once you allow it, Herdr shows the worker working, and the dashboard what the tool does. Once you refuse it, which runs no hook either, the record stays; Claude Code's `idle_prompt` notification after it (`notice.json`, below), as the worker waits at its prompt for a while, says it was answered: the worker no longer waits on the prompt, and its turn has ended there, as at a Stop hook: an idle one whose ticket is still in progress is told to continue, at most twice, then settles after the 10-minute idle grace; one whose ticket waits on a question it asked settles at once (`A settled: idle at its prompt at 20:48:39 after a permission prompt for Bash refused, waiting on Q`). In tmux and cmux the hook's record shows the worker blocked, from the moment the prompt shows, for as long as its screen shows the dialog: Claude Code runs no hook as a prompt is allowed (its `PreToolUse` runs before it asks, its `PostToolUse` once the tool is done), so orchestra reads the bottom of the screen for the dialog's question (`Do you want to proceed?`) or first answer (`1. Yes`), and a worker whose dialog is gone works while its tool runs, however long.
- **Compactions.** Claude Code's `PreCompact` hook notes each compaction of the worker's context, with what triggered it (`auto`, or `manual` for `/compact`), and the log says `A's worker's context was compacted (auto)`.
- **Subagents.** `SubagentStart` and `SubagentStop` note each subagent's start and stop by its ID. A subagent's own tool uses are reported as the worker's, so the dashboard shows `testing`, `editing` or `reading` while it runs one, and `subagent` between its tools, where it showed plain `working`. A turn doesn't end while a subagent runs: a Stop hook with one running doesn't settle the worker or have it told to continue, as a subagent in the background works on after the turn that started it, and its answer starts the next. While one runs, its tool uses count as the worker's activity, so an idle worker waits 10 minutes after its subagent's last tool use rather than after its own turn's end. A subagent cut off by Esc (or a crash) runs no `SubagentStop`, nor its turn a Stop, so one started and not stopped counts as running only while hooks report: once none has reported anything (a note in `events`, a tool use of any agent) for 10 minutes, it counts as ended, and the worker reads idle and settles or is told to continue as without one. The worker's settings (`hooks.json`) also set `CLAUDE_CODE_FORK_SUBAGENT=0`: Claude Code's fork mode, on by default in an interactive session, runs every subagent in the background, so a worker told to wait on one (the [verifier](setup.md#the-verifier)) couldn't run it in the foreground. They give its environment its share of the machine's cores too, `ORCHESTRA_CORES` and `GOFLAGS=-p=<share>` ([Runs that share a machine](running.md#runs-that-share-a-machine)).

These notes go in `.orchestra/run/events`, one short JSON line each, apart from `activity.json`, which each tool use replaces; a new or resumed worker starts with none. A permission prompt's note keeps the tool, the first 80 characters of a Bash command and the removal in it that the safety check holds, if any. The permission prompts and compactions are also triage's evidence: a deferred ticket's triage reads, in a section of its own, `It waited on a permission prompt once, Claude Code asking to allow: Bash (ffprobe -v error in.mp4).` (a held removal is said apart: `a removal held by Claude Code's built-in safety check, …, which only a person can approve and no allow rule skips`) or `Its context was compacted twice (auto, auto): …`. They are the run report's too: orchestra reads each ticket's notes before its worktree is removed, or a new worker in it starts afresh, and the reviewer is given, for each ticket, how many permission prompts its workers in this run waited on (and for which tools) and how often their context was compacted, which it adds to the ticket's bullet; a command the workers kept asking for goes under **Needs you** with the allow rule that spares it (such as `Bash(ffprobe:*)`), and a removal the safety check held with the worker-prompt rule above instead, never an allow rule. Every one of these hooks, like the others, ignores its errors, reads all its input, prints nothing and exits 0: it never answers a prompt, blocks a compaction or keeps a subagent going.

Each JSON record the hooks write (`activity.json`, `turn.json`, `session.json`, `notice.json` and each line of `events`) starts with its format, `"v":1`. A worker keeps the hooks of the orchestra that launched it, so after an upgrade, or when another orchestra adopts a running worker, the records may be in another format than the one reading them: one with no `v`, written before records carried it, is read as format 1; one in a newer format is left unread rather than misread, and the log says so once for the worker: `<worktree>/.orchestra/run/activity.json is in hook record format 2, newer than this orchestra reads (1): the worker was launched by a newer orchestra, and its records are left unread`.

The events also note each session's start (`SessionStart`, with its source: `startup`, `resume`, `clear` or `compact`) and end (`SessionEnd`, with its reason: `clear`, `logout`, `prompt_input_exit`, `other`, …), and Claude Code's `Notification` hook writes the last notification (a permission prompt, a dialog asking for input, `idle_prompt` once the session has waited at its prompt for a while) to `.orchestra/run/notice.json`. From these records `orchestra` can tell what a Claude session is doing without reading its screen, for a terminal that can't read it as Herdr does: gone once a session ended after the last one started (not when it ended to be cleared, or to resume another session with `/resume`, which starts another); blocked on a permission prompt not yet answered, or a dialog; working while a subagent runs (one started and not stopped, until no hook has reported anything for 10 minutes), or from a prompt to its turn's Stop; idle after the Stop, after `idle_prompt` (an interrupted or refused turn ends without a Stop), or once a session started and no prompt since; unknown before any hook ran. The records are those of the Claude Code process whose `SessionStart` came first after the worker's start, which `.orchestra/run/process` names: an earlier worker left running in its tab beside the one started since in the same worktree (as one renamed, its tab not closed, when its deferred ticket is taken up again) reports through the same hooks, and what it reports, its `SessionEnd` included, is left out, as is the session it starts when it is cleared (`/clear`) or resumes another (`/resume`). A worker launched by an orchestra whose hooks name no process is told apart by its session instead: the one the last `SessionStart` named. A Claude session with no ticket can report the same way, its records apart in the main checkout's `.orchestra/run/probe-session/` (the environment probe's worker) or `.orchestra/run/interview-session/` (a feature talked through, or a spec refined, with you). Runs in Herdr keep reading the state from Herdr; runs in tmux read it this way ([Workers in tmux](#workers-in-tmux-and-cmux)).

A turn that ends on an API error runs Claude Code's `StopFailure` hook instead of its Stop, with the error's kind and what Claude Code says of it, which the hook writes to `activity.json` and `turn.json` as a Stop's record (a subagent's is left out: its failure comes back to the main agent). When that error is the account's usage limit (kind `rate_limit`, and words such as `You've hit your session limit · resets 7pm (Europe/Athens)`), the worker is `limited` until a prompt starts another turn, and orchestra reads when the limit resets from those words. A turn can also end normally at the limit, with a Stop hook, after Claude Code's note that a short grace allowance remains: the worker is then `limited` while its session's transcript last says Claude Code will continue by itself once the limit resets (`Usage limit reached · continuing automatically at 5:30am · esc to cancel`, the reset read from it), with no message, prompt or continue after it. Claude Code logs that notice, and the turn's end (its `stop_hook_summary` and `turn_duration` entries), only once the turn's Stop hooks have run, your own too: until the transcript logs the turn's end, for a minute at most, its Stop isn't yet the turn's end (tmux and cmux show the worker working), so a worker that deferred its ticket as it stopped isn't set aside a moment before the notice. Herdr has no such state: a Claude worker it shows idle, done or blocked is `limited` while its screen ends with those words, or with that line of Claude Code's. A limited worker isn't idle, so it is neither told to continue into the limit nor settled: the run holds for the limit, starting no new tickets, and a minute after it resets sends the worker Escape (which cancels Claude Code's own automatic continue, or dismisses its question about the limit) and tells it to carry on ([The usage limit](running.md#the-usage-limit)). Any other API error (a 500, a 529, a rate limit that isn't the account's) leaves the worker idle, its turn over as at a Stop hook: one whose ticket is still in progress is told to continue at once, and one done with its ticket settles there (`A settled: StopFailure hook (server_error) at 15:04:05`), also when a forked agent's `PreToolUse` record replaced it. A usage limit that Herdr shows idle, its words gone from the screen, ends no turn: the worker isn't told to continue, and waits out the 10-minute idle grace.

The hooks also record the worker's Claude Code session: as it starts (or is resumed, cleared or compacted), its `SessionStart` hook writes the hook's input, with `session_id` and `transcript_path`, to `.orchestra/run/session.json`. orchestra takes the session only while its transcript is there (`~/.claude/projects/<the worktree, encoded>/<session ID>.jsonl`, or under `CLAUDE_CONFIG_DIR`), named after a session ID that is a UUID, and a plain file. With it, two things work that need the session:

- **A worker gone from its tab is resumed.** A Claude worker gone from its tab while its ticket is still in progress (its tab closed, Claude Code quit or crashed, Herdr, the tmux server or cmux restarted) stopped the run with `PAUSED`. Now orchestra opens a new tab in the ticket's worktree and starts `claude --resume <session ID>` there, with the worker's settings, MCP servers and hooks, telling it to carry on: it has all it knew of the ticket. The log says `RESUMED: <id>'s worker is gone from tab <tab> with the ticket in progress; resuming its session <session ID> in a new tab (worktree <path>)`, the ticket gets a note, and the worker is watched and merged as any other, its ticket limit counted afresh. The old tab is left as it is. This happens once per ticket in a run: a worker gone again stops the run with `PAUSED: <id> still in_progress, its worker gone from tab <tab> (worktree <path>); its session <session ID> was resumed once in this run already: the next run resumes it again, or tells it to carry on should it be back in its tab`. The next run carries it over and resumes it, as it does a ticket waiting on a question whose worker is gone after taking it up again; should the worker be back in its tab and idle (one taken for gone as it lost its name, say), it is told to carry on (`<id> is yours again`) and adopted (`<id>, which the last run left running (PAUSED), is back and idle in tab <tab>, so its worker is adopted`), rather than left waiting for you as a worker that run left idle is. A ticket back through `bd ready` once its question is answered, its worker gone from its tab, has that session resumed the same way, told the answer is in and to claim the ticket again (`RESUMED: <id> is back, and its worker is gone from tab <tab>; …`), once in a run: the answer is to what that session asked. A ticket back from a deferral gets a new worker, told what the earlier attempt left on its branch: a deferral stops a worker (it gave up, orchestra set the ticket aside, or you stopped it), and the ticket may have changed since. Its earlier worker, idle or done in its tab, has that tab closed, the log naming its session's transcript ([Tickets set aside](running.md#tickets-set-aside)). This holds when the run takes no more tickets too (its limit reached, winding down): a resumed worker counts toward no limit. Without a session (no hooks, another agent kind, a transcript removed), such a worker stops the run with `PAUSED` as before, or, when the run takes no more tickets, is warned about (`WORKER_GONE: <id> is in progress after …, but its worker is gone from tab <tab> (worktree <path>), so it is no longer followed; …`), noted on the ticket and dropped, as the next run would only stop for it again; resume it by hand in its worktree with `claude --resume <session ID>`, or reopen the ticket. To stop a worker for good, defer its ticket (`bd defer <id>`) before closing its tab.
- **A worker that loses its name is named again.** orchestra follows a worker by the name the terminal gives its agent, and a program the worker runs can take that name from it: in Herdr, a Claude Code started in the worker's pane with the pane's `HERDR_*` variables (a live test of a Claude Code integration, say) reports itself through Herdr's hook as the pane's agent, and Herdr clears the worker's name while it goes on working. So a worker the terminal has no agent under its name for is looked for in its pane, while the terminal has its tab open and labelled with the ticket's ID: an unnamed agent of the worker's kind there is the worker, named again and followed on, rather than taken for gone and its session resumed beside it (`<id>'s worker lost its name in tab <tab>; named it <name> again`). Only with its tab closed or labelled otherwise, nothing in its pane, or another agent there (named, or of another kind) is the worker gone, and resumed as above; and only once the terminal has shown it so for 30 seconds, read every poll, as Herdr can lose sight of a worker for a moment as a Claude Code it ran in its pane ends. A name the terminal refuses is logged, and the worker taken for gone; a tab or pane the terminal can't say anything of is a status it can't read, waited through as any other.
- **Triage reads the transcript.** A deferred ticket's [triage](organs.md#organs) gets the end of the worker's transcript besides the end of its terminal: its last 40 messages, tool calls and tool results, one line each (a tool's error up to 800 characters, other results up to 200), at most 8,000 characters, read from the transcript's last 512 KB.

A worktree is its worker's to change, so `orchestra` reaches the files in its `.orchestra/run/` (and the environment probe's file in the main checkout's) through an `os.Root` at the checkout, which won't follow a symlink out of it. Nor will it write through a symlink in place of `.orchestra` or `.orchestra/run`, wherever it points: git's ignore rules for the folder match a directory, not a link, so the files (`mcp.json` holds the MCP servers' secrets) would be untracked where it points, for a worker to commit. A file `orchestra` writes there that is a symlink staying inside the worktree is replaced by the file, not written through. A worktree whose `.orchestra` or `.orchestra/run` is a symlink, or with a file `orchestra` writes there that is a symlink leading outside, is set aside without a worker: `RUN_FILES_OUTSIDE: its worktree's .orchestra/run is a symlink -> <id> deferred …` (`… points outside the worktree` for such a file), with a note on the ticket naming the link. Remove the link, then `bd undefer <id>`.

A ticket's ID names its worktree (a folder under the worktree root) and its branch, `wt/<id>`, and workers file tickets themselves, while Beads checks only an ID's prefix. A ready ticket whose ID isn't a plain name (one with a `/`, a `\` or `..`, or one git won't take in a branch name) is set aside before anything is made from it: `BAD_TICKET_ID: IDs with path characters can't be run: <id> -> deferred …`, with a note on the ticket, and the run goes on. Give it a plain ID with `bd rename <id> <new-id>`, then `bd undefer <new-id>`. `--ticket` with such an ID is a setup problem (exit code 2).

Workers of another agent kind (`--agent` / `AGENT_KIND`, any kind Herdr can start; in Herdr only, as [workers in tmux and cmux](#workers-in-tmux-and-cmux) are Claude Code) are dispatched, watched and merged the same way, but these features only work with `claude`:
- **Prompt at launch.** Workers of other kinds always get the prompt pasted.
- **Recovering a paste whose Enter didn't register.** `orchestra` only recognises Claude Code's `❯` input box, so it pastes the prompt once more instead of pressing Enter, and if the worker still doesn't start, defers the ticket (`PROMPT_FAILED`).
- **The latest action on the dashboard,** read from Claude Code's `⏺` and spinner lines, and `testing`, `editing`, `reading`, `subagent` or `permission`, from the hooks above; with them, the permission-prompt stop and the compaction lines in the log.

The [organs](organs.md#organs) run `claude` whatever the workers' agent kind.

### Taking template changes

`orchestra init` writes the worker prompt and the verifier from orchestra's templates once, and keeps them as they are from then on, so a change to the templates in a later orchestra doesn't reach a project by itself. `settings.json` records the version of each template the project's files came from (`"templates": {"worker_prompt": 4, "verifier": 3}`); a project set up before it recorded them has none, and orchestra looks in its files for the words each change brought instead. Where a template has changed since, every run says so under its `START` line, a line a file:

```
  templates: .orchestra/worker-prompt.md is older than orchestra's worker prompt template, which has since changed the opening (a worker checks its own change and leaves the whole suite to the merge check) and Close (a ticket closes once the worker's own checks pass): orchestra init --update rewrites those sections from the template, keeping the rest of the file, and shows the diff to commit
```

and `orchestra init` names those sections in the step of each file it keeps. `orchestra init --update` takes the changes: in each file, it rewrites from the template the sections the template changed, the opening (before the first `## ` heading) or a section under its heading (`## Close`, `## Verify`), adding one the file lacks, and keeps the rest as it is, sections of the project's own included. The worker prompt's **Verify** section is taken only where the prompt runs the verifier. It records the templates' versions now in `settings.json`, prints the diff of each file it rewrote, and leaves the commit to you, the **Next** box naming the files. A section it rewrites loses the project's own edits in it: read the diff, and carry them over before committing. It keeps the opening's lines on running each suite on part of the project, the bullets under `The suites, and how to run each on part of the project:`, and the verifier's under the last bullet of **Its checks**, as the file has them; a prompt without them gets the lines `init` writes where it doesn't know the suites, pointing at the commands the runners list, and `orchestra init --force` writes the whole prompt afresh, with the scout's commands, in a terminal. `--update` does nothing else of `init` and takes no other flag; like `init`, it runs from the main checkout, between runs. Once the versions are recorded, a section you word your own way is left alone until the template changes it again.

## Workers in tmux and cmux

In tmux and cmux ([Herdr, tmux or cmux](running.md#herdr-tmux-or-cmux)) nothing reads a worker's screen to say what it is doing, as Herdr does: its hooks say, from the records above, and the terminal whether its program is still running. So workers in tmux and cmux are Claude Code, always started with their hooks, and a worker is:

- **gone** when its session ended (`SessionEnd`); in tmux, when its pane is dead (Claude Code exited; its window stays open with its last screen) or back at a shell after a hook ran; in cmux, when no `claude` process is left in its terminal (`cmux top`), as after a crash or a kill that ran no hook;
- **blocked** on a permission prompt not yet answered, while its screen still shows the dialog (one allowed runs no hook until its tool is done), or while its screen shows a dialog that runs no hook: one Claude Code asks before a session starts, whether to trust the folder or to use the project's MCP servers. orchestra reads the bottom of the screen for those (`tmux capture-pane`, `cmux read-screen`) while the hooks say the worker is idle or haven't said yet;
- **working** from a prompt to its turn's Stop, or while a subagent runs;
- **idle** after the Stop, after `idle_prompt`, or once a session started with no prompt since;
- **unknown** before any hook ran, as it starts up, or on a screen showing none of those dialogs; unknown for 5 minutes stops the run (`UNKNOWN >5min`), as in Herdr.

orchestra keeps what it knows of each worker (its name, the ticket's ID, and where its hooks write) on the worker's pane, as tmux pane options, so a later run finds it there. Its prompt, when pasted, goes in as one bracketed paste, its lines arriving together, then Enter; Enter, when orchestra presses it for a paste that didn't submit, goes by `tmux send-keys`; its screen, for the dashboard's latest action and triage, is read with `tmux capture-pane`. The environment probe's worker and the feature interview report through their own hooks, to `.orchestra/run/probe-session/` and `.orchestra/run/interview-session/`.

In cmux, orchestra addresses each worker's workspace and terminal by their UUIDs and, as cmux keeps nothing on a terminal the way tmux keeps pane options, keeps what it knows of those it opened (each workspace's label; each terminal's worker, agent kind and where its hooks write) in `.orchestra/run/cmux.json`, so a later run finds them there and never closes a workspace it didn't open. From cmux 0.65.0 a prompt goes in as one bracketed paste (`cmux paste`), then Enter; an older cmux types what it is given, without bracketed paste, so there a prompt of several lines is written to `.orchestra/run/cmux-prompt-<terminal>.md` in the worker's worktree and the worker is pointed at it with `@`. Keys go by `cmux send-key`, with `--force` from 0.65.0, whose guard would refuse a key into Claude Code's dialogs, and its screen is read with `cmux read-screen`. cmux's own Claude Code hooks (its sidebar's notices) are off in the workers' terminals. See [Workers in cmux](running.md#workers-in-cmux).

## Permission mode

`"worker_permission_mode"` in `settings.json`, or `--worker-permission-mode <mode>` (`WORKER_PERMISSION_MODE`) for one run, starts Claude workers in that Claude Code permission mode:

- `default`: Claude Code asks before each tool your settings don't allow. Claude Code 2.1.301 calls it `manual`, which orchestra takes too; a run passes whichever of the two names the workers' `claude` lists, so one setting suits an older `claude` and a newer alike.
- `acceptEdits`: edits go ahead without asking; the rest asks as in `default`.
- `auto`: Claude Code's classifier decides, and a worker waits on a permission prompt only when it can't.

`bypassPermissions` and `plan` are setup problems (exit code 2), with why: a worker in `bypassPermissions` would run every command unchecked, where `auto` has Claude Code's classifier check them, and one in `plan` only plans, never changing a file. Without a mode, workers start in the one your Claude Code settings give, as before the setting existed; a [spec run](running.md#a-whole-app-from-a-spec) (`--spec`, `ORCHESTRA_SPEC`, or a spec chosen at the start) starts them in `auto`, as nobody is there to answer a prompt.

Claude workers get `--permission-mode <mode>` after `--no-chrome` (or `--chrome`) and `--effort`, when their session is resumed too, and the environment probe's worker after `--strict-mcp-config`; workers of another agent kind never get it. The `START` line adds the mode after the agent, `agent: claude, permission mode: auto`, or `, permission mode: not passed to codex workers` for another kind, and nothing without a mode. As the run begins, it reads `claude --help` once: where its `--permission-mode` choices don't list the mode, the run warns, `  PERMISSION_MODE: claude --help doesn't list the permission mode auto; workers start without it, in the mode Claude Code's settings give (claude update may bring it)`, or, when `claude --help` fails, `  PERMISSION_MODE: cannot read claude --help to tell whether it takes the permission mode auto (<error>); workers start without it, …`. A `claude` that doesn't know a mode refuses to start with it, so workers start without it rather than not at all.

## Tools left out

Claude Code describes each tool it offers in every request a worker makes, and these descriptions came to about 75,000 characters a call, half of them Artifact's, with a listing of the user's skills on top. No worker in 484 sessions called Artifact, ListAgents, ReportFindings, ScheduleWakeup, SendFeedback, Workflow or Skill. So Claude workers start with `--disallowedTools=Artifact,ListAgents,ReportFindings,ScheduleWakeup,SendFeedback,Workflow,Skill` after `--permission-mode`, when their session is resumed too, and so does the environment probe's worker: a denied tool isn't described to the model, and denying Skill drops the skill listing with it. Measured on Claude Code 2.1.303, a worker's first call opened with 11,926 tokens rather than 39,180.

They keep the rest, and any tool a later Claude Code adds: Bash, Read, Edit and Write; Agent, which runs the verifier; AskUserQuestion, how orchestra sees a worker ask; ToolSearch, which loads the tools of the project's MCP servers; and the deferred tools such as Monitor.

A project with skills of its own, anything in `.claude/skills` (as `orchestra init` installs the create-check-suite skill there) or `.claude/commands` (which Claude Code runs as skills), keeps Skill, as its workers reach those skills only through it; the listing then names your own skills too. So does a project that enables a plugin in its committed Claude settings, `enabledPlugins` in `.claude/settings.json` with an entry not set to `false`, as the plugin's skills come through Skill too; orchestra counts any enabled plugin as having skills. `--disable-slash-commands` would drop the project's skills with the rest, so orchestra doesn't use it. The run decides once, as it begins, from the main checkout: skills or plugins added during the run count from the next one. It says which: `  workers start without the tools they never use: Artifact, ListAgents, ReportFindings, ScheduleWakeup, SendFeedback, Workflow (Skill and the skill listing, as the project has no skills or plugins)`, or `(the project's skills kept)`.

The run passes the flag only when `claude --help`, which it reads once as it begins, lists `--disallowedTools`, so an older `claude` still starts; workers of another agent kind never get it.

## MCP servers for workers

A worker reads ticket text that orchestra can't fully trust: a ticket filed by someone else, a follow-up another worker wrote, text pasted from an issue or a web page. Whatever it reads can steer what it does with its tools, so give it only the MCP servers the project's work needs. Each server a worker doesn't need is something a misled worker could reach, and its tool descriptions cost input tokens in every request: choosing 1 server out of 10 saved about 17,000 per request in one measurement.

`orchestra init` asks which servers workers get, offering every server Claude Code defines for the repository on your machine, with its scope and transport, the current choice ticked (none on a first run); with no server to offer, it chooses none. `--mcp postgres,firecrawl` chooses without asking, and `--mcp ""` chooses none. `settings.json` keeps their names only:

```json
{ "mcp_servers": ["postgres", "firecrawl"] }
```

The definitions stay in Claude Code's own config, because they can hold API keys and tokens and differ from machine to machine. Each machine resolves the names the way Claude Code does, the first scope that defines a name winning:

1. **local**: `~/.claude.json`, under the repository's path (or its main checkout's, from a worktree): `claude mcp add <name> …`;
2. **project**: `.mcp.json` in the repository, committed and shared: `claude mcp add --scope project <name> …`;
3. **user**: `~/.claude.json`, for every repository: `claude mcp add --scope user <name> …`.

With `CLAUDE_CONFIG_DIR` set, `.claude.json` is read from there instead of your home folder.

**claude.ai connectors** (the servers Claude Code lists as `claude.ai …`) belong to your claude.ai account: Claude Code fetches them when it starts, and there is no definition on the machine that orchestra could hand a worker. `init` lists them as not available to workers and doesn't offer them. For a worker to use the same service, define an MCP server for it with `claude mcp add`.

When a run starts, it looks up each chosen name on this machine. A name that isn't defined here, or names a claude.ai connector, is a setup problem (exit code 2) naming the fix: `redis isn't defined on this machine (define it: claude mcp add redis …)`, or `… is a claude.ai connector, which workers can't get`, or choose the servers again with `orchestra init`. A worker is never started without a server its project chose. `init` itself only warns about such a name and saves it anyway, as a teammate may define it.

Each Claude worker then gets the chosen servers' definitions in `.orchestra/run/mcp.json` in its worktree (readable by you only, and out of git) and starts with `--mcp-config <that file> --strict-mcp-config`, so no definition appears on a command line and no other server loads. `"mcp_servers": []` starts workers with `--strict-mcp-config` alone: no MCP servers. The `START` line in the log says what workers get: `MCP servers: postgres, firecrawl`, `MCP servers: none`, or `MCP servers: all, not configured`. If Herdr refuses those arguments, the run stops with `START_FAILED` rather than start the worker with every server.

Without `"mcp_servers"`, workers load every MCP server Claude Code finds on the machine, as before this setting existed, and the run warns once, in the log and on the dashboard: `workers load every MCP server Claude Code finds on this machine; choose theirs with orchestra init`. Workers of another agent kind (`--agent`) don't get the setting; the log says so once. Organs never get any MCP server. The Claude Code sessions that break a spec down or talk a feature through get the servers Claude workers get, in `.orchestra/run/mcp.json` in the main checkout, and none (`--strict-mcp-config` alone) when the project chose none, hasn't chosen, or chose them for workers of another kind ([Talked through](running.md#talked-through)). They get Chrome as Claude workers do, `--no-chrome` or `--chrome` as the project chose, workers of another kind or not.
