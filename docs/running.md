# Running

Starting a run and its options, a whole app from a spec and the nightly recipe, several tickets at once, tickets set aside, the usage limit, and what happens when a run stops. Back to the [README](../README.md).

## Run

From the main checkout (not a worktree), in a Herdr pane or, with tmux installed, any terminal, on the branch finished tickets should land on:

```
git switch -c batch/$(date +%F)
orchestra
```

`orchestra` checks its setup first and lists every problem at once, with exit code 2. In a repository [`orchestra init`](setup.md#set-up-a-project) hasn't set up (no `.orchestra/settings.json`, which `init` writes with the worker prompt, nor a `.claude/worker-prompt.md` from before `init`), it says so first, `orchestra isn't set up in this repository yet. Run this first: orchestra init`, rather than list the worker prompt and Beads database `init` provides; problems `init` doesn't fix, such as a detached HEAD or no terminal for the workers, follow under `Also fix before a run:`. `orchestra --feature …` stops the same way before the feature is talked through; `orchestra --spec …` sets the repository up itself instead ([From an empty repository](#from-an-empty-repository)). A project with settings but no worker prompt is told `Worker prompt not found: .orchestra/worker-prompt.md. Recreate it with: orchestra init`.

One run at a time works on a repository: a second would race the first for the same tickets, worktrees and branch. Once its startup checks pass, a run holds a lock, `orchestra.lock` in the repository's git directory (`.git/orchestra.lock` in the main checkout; `git rev-parse --git-common-dir` names that directory from any worktree), until it exits after the run report. Nothing that empties `.orchestra/run/`, such as `git clean -fdX` or `-fdx`, removes it: `git clean` never touches the git directory. A second run in the same repository stops before changing anything, and a `--feature` request before it is talked through, with exit code 2: `orchestra is already running in <repo> (pid 44497, since 08:31, main, pane w2B:p60)`. The lock is an `flock`, which the system releases when orchestra exits however it exits, `kill -9` included, so there is never a stale lock to remove. The file says which run holds it, or held it last: its PID, start time, version, branch, `ticket`, `feature` (a feature described at the question too, once it is typed) or `spec` (the spec's path in the repository, for a [spec run](#a-whole-app-from-a-spec), one chosen at the question too) and `pane`, the Herdr or tmux pane, or cmux terminal, it runs in (`HERDR_PANE_ID`, `TMUX_PANE`, `CMUX_SURFACE_ID`; empty when it runs in none). `lsof .git/orchestra.lock` shows whether a run holds it. Runs in different repositories don't block each other. `orchestra init` holds the lock too while it changes the project, writing `"init": true` and its PID alone, so a run started meanwhile is refused (`orchestra is already running in <repo> (orchestra init, pid 44497)`). `orchestra plan --apply` warns when a run is going: a ticket the run has started keeps going whatever it now waits for.

In a terminal (its input and output both), `orchestra` then asks what the run should work on, once the startup checks have passed and it holds the lock, so that an answer is never followed by `orchestra cannot start`:

- **Current tickets**, selected to start with, runs the backlog as this page describes. The option says what there is to run: `Current tickets: N ready`, N what the run's own `bd ready` query finds (`0 ready` when the last run left workers to carry on with); with [nothing to run](#nothing-to-run), none ready (or every ready ticket held back) and none carried over, `Current tickets: none, all done` or `Current tickets: none ready (N open)`, N the tickets not closed, leaving out the `exclude_types`. It says only `Current tickets` when `bd` can't say. Picked with nothing to run, it shows why, as [below](#nothing-to-run).
- **Spec: build what a spec file describes** asks for the **Spec file**: a path typed or pasted, a relative one from the repository, `~` or `~/` for your home folder; a path in quotes, or a file dropped on the terminal with its spaces escaped by backslashes, works too. Tab completes folders and `.md`, `.markdown` and `.txt` files in the folder typed so far (hidden ones once a `.` is typed), and ↓ or Ctrl+N goes to the next completion. Ctrl+O browses instead, from the folder typed so far or else the repository, ten entries at a time, dotfiles hidden and other files greyed (`.md, .markdown and .txt files only`): ↑ and ↓ move, ← (h, Backspace) goes up a folder, Enter opens a folder or chooses a file, and Esc closes the browser without leaving the question. It won't go into a folder it can't read, and says `cannot open <folder>: <cause>` (on macOS, `~/Documents` or `~/Desktop` until the terminal has access to them). Enter goes on only once the path names a file of text with something in it, else says why: `no such file: <path>`, `<path> is a folder`, `<path> isn't a file` (a device or a pipe), `<path> is empty`, `<path> doesn't look like text`, `cannot read <path>: <cause>`. Then **Refine it with claude first?**: **Run it as it is**, selected, runs the spec as `orchestra --spec <file>` does, and **Refine it with claude first** as `orchestra --spec <file> --refine` does. orchestra prints `Spec: <absolute path>, run as it is` (or `, refined with claude first`), and the run goes on as a [spec run](#a-whole-app-from-a-spec): workers in the `auto` permission mode unless a mode is given, and the lock, the log and the start record naming the spec. A spec git ignores, or one inside `.git`, ends the run there with exit code 2: `orchestra cannot run that spec:`, then the problem, which says `(chosen at the start)` where `--spec`'s say `(--spec)`. With `TERM=dumb` it asks for the path as a line, with the same checks.
- **New feature** opens a field for the feature's description. Alt+Enter or Ctrl+J starts a new line, and Enter goes on; an empty description isn't taken. orchestra prints the description, then opens Claude Code in a pane to the right of its own to [talk it through](#talked-through) with you and file its tickets, and runs them as `--feature` does ([A feature from one request](#a-feature-from-one-request)).

Before its first ticket, once it knows there is something to run and has brought its branch up to its upstream (below), the run checks the project's [requirements](setup.md#the-machines-requirements), `"requires"` in `settings.json`: each check in the main checkout, and for one that fails, its install, then the check again. The log says what it found (`REQUIRES: git-lfs met; jq (installed with 'brew install jq') installed`), and what is still missing stops the run there, with no worker started and every ticket as it was, `REQUIREMENTS_MISSING: docker (Install and start Docker Desktop); meet it (each entry of 'requires' in .orchestra/settings.json says how), then run again`, exit code 2, rather than leave every ticket to fail on it one by one. A merge that changes the list in the base's `.orchestra/settings.json`, as a ticket that needs a new tool does, has the run check it again before the next ticket starts (`REQUIRES: <id>'s merge changed the requirements in .orchestra/settings.json on <base>: they are checked before the next ticket starts`); what is missing then stops the run the same way, once the running tickets finish. A list in the merged file that a run would refuse leaves the requirements as they were, with a warning (`SETTINGS_UNREAD: <id>'s merge changed the requirements in .orchestra/settings.json on <base>, but …`). Where `README.md`'s section on what to install differs from the list, or the README has none though the list has entries, the run's start says so and goes on, the README as it is: `README_STALE: README.md's section on what to install differs from the requires list in .orchestra/settings.json: orchestra requires --readme writes it, to commit` ([The machine's requirements](setup.md#the-machines-requirements)).

Before its first ticket too, once the main checkout is clean and on its branch, the run brings that branch up to its upstream, the branch it follows (`git branch -vv` names it), so that no ticket builds on a branch a push from another machine or a pull request merged on GitHub has left behind. It fetches the upstream's branch, asking for no credentials (`GIT_TERMINAL_PROMPT=0`), with ssh in batch mode (`-o BatchMode=yes` after the ssh command git would run, `GIT_SSH_COMMAND`, `core.sshCommand` or `ssh`), so that a key's passphrase or an unknown host key fails the fetch at once rather than waits on a prompt, and for at most a minute, and then:

- with the upstream ahead and the branch without commits of its own, fast-forwards the branch (`git merge --ff-only`): `BASE: fast-forwarded main to origin/main (3 commits)`;
- with both ahead of each other, starts on the branch as it is, with a warning: `BASE_DIVERGED: main is 2 ahead of and 3 behind origin/main; the run builds on main as it is`;
- with the branch ahead, or the two the same, does nothing.

A fetch that fails (offline, authentication, its time limit) is a warning, `BASE_UNFETCHED: could not fetch origin/main: <cause>; the run builds on main as it is`, and the run goes on; `BASE_NOT_FAST_FORWARDED` says the same of git failing to compare the two or to fast-forward. None of them stops a run, and the [event stream](events.md)'s `warn` record gives the word in its `detail`. A branch with no upstream, as in a new repository, is left as it is. A fast-forward that changes `"setup"`, `"setup_files"` or `"requires"` in `.orchestra/settings.json` has the run take them as committed, as a [merge](#several-tickets-at-once)'s does, though it read its settings before: `SETUP: the fast-forward to origin/main changed .orchestra/settings.json on main: the setup is 'npm ci' from now on`, and `REQUIRES: the fast-forward to origin/main changed the requirements in .orchestra/settings.json on main: …`, the new list then checked before the first ticket. Its check commands too, which a merge's count only from the next run: no ticket has started, so each is checked with the commands of the branch it builds on (`CHECKS: the fast-forward to origin/main changed .orchestra/settings.json on main: the merge check (check_fast) is 'scripts/check-fast.sh' from now on`). Its worker prompt too, `.orchestra/worker-prompt.md` (or one `--prompt` gives in the repository), for every ticket's worker, as their worktrees are made from that commit: `PROMPT: the fast-forward to origin/main changed .orchestra/worker-prompt.md on main: the run's workers get it as committed`; one git can't read, or without its `TICKET_ID` placeholder, leaves the prompt the run read as it opened, with a warning (`PROMPT_UNREAD: …`). A fast-forward git can't say the changes of, as when `git diff` passes its time limit, leaves the settings and the prompt as the run read them, with a warning for each: `SETTINGS_UNREAD: git could not say whether the fast-forward to origin/main changed .orchestra/settings.json on main: <why>; the setup, the requirements and the check commands stay as they were`, and `PROMPT_UNREAD: git could not say whether …`. The run never pushes, and never rewrites a commit. `--no-fetch` (or `ORCHESTRA_NO_FETCH=1`) skips all of it, for working offline. An [overnight](#overnight) run does all of it as its pre-flight's first check instead, so that its checks read the branch the run builds on, and doesn't fetch again as it starts; a [spec run](#a-whole-app-from-a-spec) does it before it commits its spec, or the spec's commit would leave the branch diverged from an upstream that moved.

Esc or Ctrl+C at the question, at any of its steps (Ctrl+D, the end of input, with `TERM=dumb`, where it asks with plain lines), exits with code 130, with nothing changed and no run recorded in `.orchestra/run/events.jsonl`. `--tickets` (or `ORCHESTRA_TICKETS=1`) skips the question and runs the current tickets; `--ticket`, `--feature`, `--spec`, [`--overnight`](#overnight) and `--plain` skip it too, and a run without a terminal, or with `DONE_SO_FAR` at `LIMIT`, never asks. Scripts and agents that start `orchestra` in a terminal, such as a Herdr pane or a tmux window, pass `--tickets`, or `--spec` or `--ticket`: the bare command would wait at the question, and `--feature` talks the feature through with you ([A feature from one request](#a-feature-from-one-request)).

### Herdr, tmux or cmux

Workers run in [Herdr](https://herdr.dev) tabs, [tmux](https://github.com/tmux/tmux) windows or [cmux](https://cmux.com) workspaces. `--terminal herdr`, `--terminal tmux`, `--terminal cmux` or `--terminal auto` (or `ORCHESTRA_TERMINAL`) chooses for a run, over `"terminal"` in `settings.json`, which chooses for the project; without either it is `auto`: the terminal `orchestra` runs in, the innermost first (Herdr in a Herdr pane, `HERDR_ENV=1`; tmux in tmux, `$TMUX`; cmux in a cmux terminal, `CMUX_WORKSPACE_ID`), else tmux when `tmux` is on the `PATH`. A terminal started from a pane of another copies that one's variables into its own panes, as tmux started from a Herdr pane has `HERDR_ENV=1` and `HERDR_PANE_ID` in its panes, even once that pane is closed: with Herdr's variables beside `$TMUX` or `CMUX_WORKSPACE_ID`, orchestra picks Herdr only when Herdr says `HERDR_PANE_ID` is the pane it runs in (orchestra's process group is the one in that pane's foreground, `herdr pane process-info`), and else tmux, or cmux. With none of these, the run doesn't start: `No terminal for the workers: run orchestra from a Herdr pane or a cmux terminal, or install tmux (brew install tmux, apt install tmux) to run it anywhere.` A choice of Herdr outside a Herdr pane, of tmux without `tmux` installed, or of cmux outside a cmux terminal, is a setup problem that says so. The `START` line names the choice, `terminal: Herdr, workspace: w2B`, `terminal: tmux, session: orchestra-kinieta` or `terminal: cmux, workspaces: one per ticket`.

- **Herdr.** Each worker gets a tab in the Herdr workspace `orchestra` runs in, or in the one `--workspace ID` names (`herdr workspace list` lists them). Herdr reads from each worker's screen whether it is idle, working or blocked, for any agent kind it can start (`--agent`).
- **tmux.** Each worker gets a window named with its ticket's ID, which keeps that name whatever Claude Code writes to its title (tmux 3.7, which refuses `.` and `:` in a window name, gets them as `_`, so a child ticket's window there is named `proj-abc_1`); notes and logs give its window and pane by tmux's IDs (`@3`, `%7`). Run inside tmux, `orchestra` opens the windows in its own session, beside its own window, and the dashboard's number keys go to them. Run outside tmux, it opens them in a detached session, `orchestra-<repository folder>` (with `.` and `:` made `_`, which tmux before 3.8 doesn't keep in a session name), starting the session, and the tmux server if none runs, when it opens the first window. `--workspace <session>` names another session, made the same way if tmux has none; tmux before 3.8 names one asked for with `.` or `:` with `_` in their place (3.2 to 3.6), or refuses the name (3.0, 3.1 and 3.7), and orchestra then uses the session so named. A `:` in `--workspace` is made `_` on every tmux, 3.8 included, since tmux reads `foo:bar` as session `foo`, window `bar`, and couldn't be told to attach to a session so named; only the session `orchestra` runs in keeps a `:`. A session's name may hold `.` or `#`, whether orchestra makes the session or runs in it; one with `.` is attached to as `tmux attach -t foo.bar:`, since tmux reads `foo.bar` as window `foo`, pane `bar`. When the windows aren't in the session `orchestra` runs in, the `START` block says how to see them, `to see the workers' tabs: tmux attach -t orchestra-kinieta` (`tmux switch-client -t …` from inside tmux), the dashboard says it above its hint, and a run that leaves workers in their windows says it again as it ends. A worker's window stays open when Claude Code exits, its screen there to read, until orchestra closes it.
- **cmux.** Each worker gets a workspace of its own in orchestra's window, named with its ticket's ID, which the sidebar lists with its branch; start `orchestra` from a cmux terminal. See [Workers in cmux](#workers-in-cmux).
- **Workers in tmux and cmux are Claude Code.** Neither can say what a program in a window is doing: the worker's [hooks](workers.md#workers-in-tmux-and-cmux) tell orchestra, and only Claude Code has them. `--agent` (or `AGENT_KIND`) other than `claude` with tmux or cmux is a setup problem: `Workers in tmux must be Claude Code …` (`Workers in cmux …`). The environment probe's worker and the sessions that talk a feature or a spec through with you report through hooks too.

`.orchestra/run/state.json` records which terminal each worker the last run left runs in. A run in another terminal can't reach those workers: it leaves them in the file for a run in theirs, and its `START` block says so, `kept for a run in Herdr, as this run in tmux can't reach their workers: <id> (left running: PAUSED)`. It doesn't start their tickets either, even once bd ready lists one again, as when the question its worker asked is answered: their workers may still be at work in those worktrees. The tickets they block wait as they would for a running one. A file written before workers could run in tmux names no terminal: its workers are Herdr's.

### Workers in cmux

[cmux](https://cmux.com), a macOS terminal for coding agents, can hold the workers: `"terminal": "cmux"` in `.orchestra/settings.json`, `--terminal cmux` or `ORCHESTRA_TERMINAL=cmux`, or left to `auto` from a cmux terminal (a Herdr pane, or tmux, inside it comes first). Start orchestra from a cmux terminal: cmux answers only programs started in its own terminals, so outside one choosing cmux is a setup problem saying so. orchestra finds the `cmux` command on the `PATH`, as in a cmux terminal, or else in `/Applications/cmux.app`.

Each worker gets a workspace of its own in orchestra's window, named with its ticket's ID and opened without taking the focus, so the sidebar lists the workers with their branches; `--workspace` has no use there and is a setup problem. The dashboard's 1–9 keys select a worker's workspace, and a feature [talked through](#talked-through) with you, or a spec refined, opens claude in a split to the right of orchestra's terminal. As under tmux, workers must be Claude Code: cmux can't say what an agent is doing, so a worker's hooks do, and a session killed or crashed without a word is gone once no `claude` process is left in its terminal; a dialog Claude Code shows before its session starts, such as whether to trust the folder, is read from the screen. From cmux 0.65.0 a prompt is pasted into the worker's input box with `cmux paste`, bracketed, so its lines arrive together; an older cmux types what it is given, with no bracketed paste, so there a prompt of several lines is written to `.orchestra/run/cmux-prompt-<terminal>.md` in the worker's worktree, and the worker is pointed at it with `@`. cmux 0.65.0 also refuses to type over a draft in an agent's prompt or into a dialog it has open, so orchestra passes `--force` with what it types and the keys it presses in its workers' terminals, as a key answering Claude Code's dialogs has to go through; it reads the version with `cmux version`. cmux's own hooks for Claude Code (its sidebar's notices) are off in the workers' terminals, where orchestra's hooks report instead. The adapter was written against cmux 0.64.22 and 0.65.0.

orchestra addresses cmux's workspaces and terminals by their UUIDs, never by short refs such as `workspace:2`, which older cmux numbered afresh on each start, and keeps those it opened in `.orchestra/run/cmux.json`. It closes only a workspace it opened that still has its ticket's name, never its own, and checks afterwards that cmux closed the right one. Quitting or restarting cmux ends the workers (cmux restores its layout, not the programs that ran in it): the next run finds their workspaces gone, or holding no claude, and resumes them from their sessions in new ones, as after a Herdr restart.

### Nothing to run

A run with nothing to run says so and exits 0, rather than open the dashboard only to end at once: no dashboard, no triage, no run report and no notification. It has nothing to run when its own `bd ready` query (in its scope, without questions and the `exclude_types`) finds nothing the run would start and `.orchestra/run/state.json` carries no worker over from the last run (with `--ticket`, none on a ticket in the scope); a worker to carry on with is something to run, and the run goes ahead. A ticket `bd ready` lists that the run would hold back is none to start: a parent whose subtickets aren't all closed and merged, which runs after them, or a ticket blocked by one closed but not merged (labelled `unmerged`, or with its branch `wt/<id>` not on the base: see [below](#several-tickets-at-once)), which waits for it to merge (`bd ready` counts a closed blocker as done), or a follow-up filed from one (`discovered-from`), which waits likewise (see [Several tickets at once](#several-tickets-at-once)). When `bd` can't show such a ticket's blockers, the run goes ahead. A run that asks checks once **Current tickets** is picked; the others (`--tickets`, `--ticket`, `--plain`, no terminal) check once the startup checks have passed and they hold the lock, a feature run once its epic is filed, and a spec run once its root epic is filed or found. On a terminal the message is a box, otherwise the same lines, plain, after the time:

- `✓ All done`: no ticket is left but those of the `exclude_types` (epics, never run), and none is closed but not merged. `Still open: <ids> (bd close <ids>)` follows when epics are still open: their subtickets merged before this run, which closes an epic only as it merges the last of them. A spec run says `✓ <path> is built (<root epic>)` instead: everything under the spec's root epic is merged.
- `○ Nothing ready to run`: tickets are left, but none can start. A line for each of what holds them: `N questions wait for your answer: orchestra answer`, `N tickets wait on other tickets: bd blocked`, `N tickets wait for their subtickets to merge`, `N tickets wait for their blockers to merge`, `N follow-ups wait for the tickets they were filed from to merge`, `N in progress · N deferred`, `N closed but not merged: bd list --label unmerged`. A ticket labelled `unmerged` whose branch is on the base already, merged by hand with a commit of its own naming the ticket, counts as merged, as the run itself would find it; the next run that gets as far as its loop removes the label.

With nothing ready, in either form, a deferred ticket whose blockers have all merged gets a line of its own, `Deferred: <id>: its blockers have merged (<blockers>); to run it: bd update <id> --status open`, followed by `its worktree has no commits of its own, safe to remove: git worktree remove <path> && git branch -d wt/<id>` when its worktree holds nothing, as the [`DEFERRED_FREE`](#several-tickets-at-once) line in a run's `START` block does; one deferred until a later date (`bd defer --until`) isn't listed until that date has come. When `bd` can't say which they are, the box goes without them and the log says why.

The [event stream](events.md) records the run's start, its done line, `READY_EMPTY after 0 tickets: everything is done` or `READY_EMPTY after 0 tickets: nothing ready`, and its end with code 0; the log has the done line too. When `bd` can't say, the run goes ahead, and the loop reports what it can't read (`READY_UNREADABLE`). A run whose `DONE_SO_FAR` has reached `LIMIT` ends `LIMIT_REACHED`, as before.

`--concurrent N` (or `-c N`, or `ORCHESTRA_CONCURRENT=N`) sets how many tickets run at the same time for this run, from 1 to 16, overriding `settings.json` (0 is a setup problem, not "unset"); see [Several tickets at once](#several-tickets-at-once). `--terminal` chooses Herdr, tmux or cmux, and `--workspace` the Herdr workspace or tmux session for the worker tabs (cmux has none: each worker gets a workspace): see [Herdr, tmux or cmux](#herdr-tmux-or-cmux). `orchestra -h` lists the flags. These pages write a long flag with two dashes and a one-letter shorthand (`-c`, `-v`, `-h`) with one, but a long flag takes one dash as well, as Go's flags do, so a script written either way keeps working. Most default to the environment variable `orchestrate.sh` used: `LIMIT` (none), `DONE_SO_FAR`, `AGENT_KIND` (claude), `WORKER_PROMPT` (`.orchestra/worker-prompt.md`), `NOTIFY`, and `WT_ROOT` (`<repo>-worktrees`); a relative `WORKER_PROMPT` or `WT_ROOT`, or their flags, is relative to the repository. The organs add `TRIAGE`, `REVIEW`, `ORGAN_MODEL` and `ORGAN_EFFORT`, and `PROMPT_AT_LAUNCH` controls how workers get their prompt.

A run has no ticket limit unless `--limit N` (or `LIMIT=N`) gives one: its `START` line says `limit: none`, its dispatch lines read `[12]`, the event stream's `dispatch` records leave `limit` out, and it ends `READY_EMPTY` once nothing is left to start. A limit given caps a run of any kind, `--spec` and `--feature` runs included, for a run meant to spend no more than so many tickets: it stops taking tickets after N dispatches, counting a ticket dispatched again and the `DONE_SO_FAR` (or `--done-so-far`) of earlier runs, its dispatch lines read `[12/40]`, and it ends `LIMIT_REACHED`.

The on-or-off variables, `NOTIFY`, `TRIAGE`, `REVIEW`, `PROMPT_AT_LAUNCH`, `ORCHESTRA_TICKETS`, `ORCHESTRA_OVERNIGHT`, `ORCHESTRA_REFINE`, `ORCHESTRA_NO_FETCH` and `ORCHESTRA_NO_UPDATE_CHECK`, all read their value the same way: `1`, `true`, `yes` or `on` turns the feature on, `0`, `false`, `no` or `off` turns it off, in any case, and unset leaves its default (on for the first four, off for the last five). `ORCHESTRA_REFINE` is a standing choice, as `ORCHESTRA_TICKETS` is: a run without a spec leaves it unused. Anything else is a setup problem (exit code 2) naming the variable, unless its flag, such as `--triage=false`, is given too.

`--worker-effort medium` (or `WORKER_EFFORT=medium`, or `"worker_effort": "medium"` in `settings.json`) starts Claude workers with `--effort medium`; any of `low`, `medium`, `high`, `xhigh` and `max` will do. Without it they run at `high`, and `orchestra init` says so. The session that refines a spec (`--spec --refine`) or talks a feature through (`--feature`, New feature) starts at the same effort, chosen the same way, so a talk-through runs at the level its tickets will. Measuring `high` against `medium` on real tickets (time to close, tokens, the check passing first time) may yet move the default.

`--worker-permission-mode auto` (or `WORKER_PERMISSION_MODE=auto`, or `"worker_permission_mode": "auto"` in `settings.json`) starts Claude workers in that Claude Code permission mode: `default` (`manual` in newer Claude Code), `acceptEdits` or `auto`. Without it they start in the mode your Claude Code settings give, but for a [spec run](#a-whole-app-from-a-spec), whose workers start in `auto`. See [Permission mode](workers.md#permission-mode).

`--ticket-limit 2h` (or `TICKET_LIMIT=2h`, or `"ticket_limit": "2h"` in `settings.json`) stops the run, like `PAUSED`, when a worker is still going that long after its ticket was dispatched (an [overnight](#overnight) run sets the ticket aside instead): a hung command or a stuck worker would otherwise hold its slot for good. The worker's prompt says how long it has, as agents pace themselves to a stated budget. The ticket gets a note, and its tab and worktree are left open. The time a worker waits on the account's [usage limit](#the-usage-limit) doesn't count. `0` turns a limit from `settings.json` off for a run. Without a limit, a worker still going after 2 hours is logged once (`LONG_RUNNING`), and the run keeps waiting. Whatever the limit, a worker whose status the terminal can't tell (`unknown`) for 5 minutes stops the run (`UNKNOWN >5min`), as one blocked on a dialog for 4 does. A project not yet set up with `orchestra init` keeps working from `.claude/worker-prompt.md`, `.claude/orchestrate.log` and `.claude/orchestrate-reports/`.

Every `bd`, `git`, `herdr`, `tmux` and `cmux` command orchestra runs has a time limit: 30 seconds for a read or a Herdr, tmux or cmux call, 2 minutes for a git write (worktree, rebase, merge, branch) or a `bd` update; Herdr's own waits keep their timeouts, with 30 seconds to spare. A command still running then is stopped and fails with `<command>: timed out after 30s`, reported like any failure of it (`STATUS_UNREADABLE`, `TERMINAL_FAILED`, `GIT_FAILED`, …). A git question that fails is never read as its answer, as no commit, no change or not on the base: one a finished ticket's merge turns on (the ticket's own commits, uncommitted changes in its worktree, whether its branch is on top of the base or changes anything, where a branch is) is asked again, three times in all, and then stops the run with `GIT_FAILED: git can't tell <what>: <git's error>; stopping before merging wt/<id>; …`, the ticket left unmerged and labelled, its branch as its worker left it, for you to merge by hand or the next run to carry on with once git answers. Ctrl+C stops the commands in flight too, and the run ends once its workers have returned; a merge already under way, and the notes after it, finish first, so one Ctrl+C never leaves the repository half merged. Nothing is rebased after it, though: a finished ticket still waiting for its turn to merge takes none, and one whose rebase stops on conflicts as Ctrl+C comes has the rebase aborted rather than handed back to its worker, which could no longer be told; the next run carries it over and merges it.

Pressing Ctrl+C again meanwhile quits rather than wait, so that a shutdown that hangs can be left without `kill -9`. With nothing under way that Ctrl+C doesn't cut short, orchestra quits at once with exit code 130, logging and printing `INTERRUPTED: quit at once with Ctrl+C, leaving <id> (tab <tab>) running with its tab and worktree open`, without triage or the report. With a merge or a worktree setup under way, the second Ctrl+C says so, `<id>'s merge is under way; press Ctrl+C again to abandon it (the repository may be left half merged)`, and skips triage and the report, as it always did; a third quits, the line adding `abandoned <id>'s merge: git may still finish it, so check git status before starting another run`. The commands under way run in their own process groups, so they carry on after orchestra has gone: a `git` command may still finish, or hold git's lock files for a while, though a new run can take orchestra's own lock at once. The workers left running aren't labelled `unmerged` as they are after a stop, which would wait on `bd`, but they are saved for the next run to carry on with, as after a stop: those at work as left running, `INTERRUPTED` (see [Exit codes](#exit-codes)). SIGTERM and SIGHUP (closing the terminal or pane) count as Ctrl+C does, so a supervisor's second SIGTERM quits too. During triage and the report, Ctrl+C skips them, and the one after it quits.

Epics are never dispatched: their children are the work. `"exclude_types"` in `settings.json` lists the issue types a run leaves out of `bd ready`, for a project with other container or non-work types, for example `["epic", "decision", "milestone"]`; without it, only `epic` is left out, and `[]` dispatches every type.

Parents run last. A ticket with subtickets (`bd create --parent <id>`) that aren't all closed and merged waits for them, logged once as `<id> waits: its subtickets are not all closed and merged`: its worker couldn't close it before they are, and its work builds on theirs. An epic is never dispatched, so orchestra closes it itself once a run merges the last of its subtickets: when none is left open, running, or closed but not merged (labelled `unmerged`), it runs `bd close <id>` with the reason `All 3 subtickets are merged; closed by orchestra after <last id>`, and logs `closed epic <id>: all 3 subtickets are merged`. An epic that was itself the last open subticket of another epic closes that one too, and so on up. Should `bd close` fail, the log carries `bd`'s error and `all 3 subtickets are merged, but bd could not close <id>: <error>; close it with: bd close <id>`, and the run goes on. An epic whose subtickets were all merged before the run started isn't closed, as orchestra didn't see the last one merge: [nothing to run](#nothing-to-run) lists it under `Still open`.

A run that has nothing ready but tickets waiting on questions, open questions in its scope (issues labelled `human`: with `--ticket`, one that blocks the ticket or one under it, or is under it itself), doesn't end when it can put them to you: on the dashboard, with orchestra in a pane, it goes on to its loop, which opens the answer talk on them beside the dashboard without taking the keyboard focus, whatever `"questions"` says, and logs `nothing ready but the questions <question> (holding <ids>), …: the answer talk is open beside the dashboard, and the run takes up each ticket an answer frees`. A run whose queue runs dry with nothing running does the same. Meanwhile the run reads `bd` every 5 seconds and takes up each ticket an answer frees as soon as it is ready, without waiting for the talk to end, and carries on as a normal run. A talk you close with questions left open ends the run as before, its last line naming them and the tickets they hold: `READY_EMPTY after 3 tickets; QUESTIONS_OPEN: <question> (holding <ids>): answer with orchestra answer, then run again`. A question put to you in a talk now over, however the run was waiting as it ended, isn't put again in the same run: a talk that opens by itself leaves it out, while the **a** key's talk and `orchestra answer` ask it again. One asked since is put, as is one that came in as a talk was ending, before claude was given it. The talk also says how many of the scope's tickets are deferred, and under which parent (`35 deferred under tutti-kkb`): they aren't questions, and it releases them (`bd undefer`) only when you ask. With `--plain`, without a terminal, with orchestra in no pane, and in an [overnight](#overnight) run, whose full check and report shouldn't wait for the morning, no talk opens: at the start the box says `N questions wait for your answer: orchestra answer`, and mid-run the log says `nothing ready but the questions …: answer with orchestra answer, then run again` and the run ends with the same `QUESTIONS_OPEN` part.

### One ticket and its subtickets

```
orchestra --ticket CalendarView-bl0
```

`--ticket <id>` (or `ORCHESTRA_TICKET=<id>`) runs that ticket and its descendants (children, grandchildren, …) and nothing else: the queue is `bd ready --parent <id>` plus the ticket itself, with the usual filters, holds and priority order, each parent after its children. A ticket without subtickets is a run of one. An unknown ticket, a closed one or a question (label `human`) is a setup problem. The START line and the dashboard's title line show the scope (`· ticket <id>`), and so does the run report.

Workers are told to file follow-ups that belong to the work as children of `<id>`, and those join the run; anything filed otherwise waits for a later run, and the log and the run report list it. `--limit`, `--concurrent` and the rest apply as usual. The run ends as any other, with `READY_EMPTY`, `LIMIT_REACHED` or `DRAINED`, followed by whether the scope is finished:

- `SCOPE_DONE: <id> and its 3 subtickets are merged`, or for an epic, which the run closes as its last subticket merges, `SCOPE_DONE: <id>'s 3 subtickets are merged; orchestra closed <id>` (`…; close it with: bd close <id>` should `bd close` have failed);
- `SCOPE_OPEN: <id>: 2 of its 5 subtickets not done: <id>.2 (blocked by other-7 outside the scope), <id>.4 (waiting on your answer to <question>)`, naming why each isn't: set aside in this run, its setup failed (`its setup failed; the whole output is in <path>`), deferred, closed but not merged, waiting for its own subtickets, not started.

Both exit with 0.

With nothing under `<id>` ready from the start (or only tickets the run would hold back), and no worker carried over on a ticket in the scope, the run has [nothing to run](#nothing-to-run): it shows `○ Nothing under <id> is ready to run`, then each ticket not done with why, as `SCOPE_OPEN` gives it, and its done line ends with the `SCOPE_OPEN` part (`READY_EMPTY after 0 tickets: nothing ready; SCOPE_OPEN: …`). An epic whose subtickets are all merged is `✓ All done`, with `Still open: <id> (bd close <id>)`.

### A feature from one request

```
orchestra --feature "Add a --json flag to the list command"
```

A feature goes from a request to a finished run with you there to talk it through, in one of two ways: typed at the start, as **New feature** ([Run](#run)), or given with `--feature "<request>"`, which skips the question. Either way Claude Code [talks it through](#talked-through) with you and files the tickets you agree on, as `--spec <file> --refine` breaks a spec down ([Refined with you](#refined-with-you)), and the run starts on them without asking. A feature always needs you at a terminal: there is no unattended feature run. Scripts and agents write the request to a file, with whatever it leaves open settled, and run `orchestra --spec <file>`, which breaks it down with nobody there ([A whole app from a spec](#a-whole-app-from-a-spec)).

The feature is filed in Beads as an epic and its tickets, and run as `--ticket <epic>` would run it, with the other flags as given (`-c`, `--plain`, the effort flags, …) and a spec run's defaults:

- **Workers in Claude Code's `auto` permission mode**, unless `--worker-permission-mode`, `WORKER_PERMISSION_MODE` or `"worker_permission_mode"` gives another ([Permission mode](workers.md#permission-mode)).

The START line and the dashboard's title show `· feature <epic>`, with a line under the START line naming the request, as do the log and the run lock (`feature`); the run report gets the request as evidence. Nothing is left to run after it: the run starts on the epic as soon as it is filed and checked.

The session starts after the usual startup checks (repository, `bd`, the terminal, settings, MCP servers), and once the main checkout is found clean, so that nothing is filed for a run that couldn't start. `--feature` with `--spec`, `--ticket` (or `ORCHESTRA_TICKET`) or `--tickets`, an empty request, and `DONE_SO_FAR` at a `LIMIT` given, which would file the feature and run none of it, are setup problems (exit code 2). `--refine` with `--feature` changes nothing, as a feature is always talked through. `--yes`, which once filed a feature planned without you, is gone: given, it is a setup problem saying `--yes is gone: --feature always talks the feature through with you; orchestra --spec <file> runs a request written to a file unattended.`

#### Talked through

orchestra splits its pane, Herdr's or tmux's, or its cmux terminal, and starts an interactive Claude Code session in the new pane, to the right of orchestra's, in the main checkout, with the keyboard focus: `claude --append-system-prompt-file .orchestra/run/spec-prompt.md --strict-mcp-config -- "Here is the feature I'd like to talk through (feature run 20261017T093005Z): @.orchestra/run/feature-request.md"`, the feature run being the time the run started, in UTC. The instructions are the spec breakdown's, in their feature mode. Herdr types the command into the pane's shell, which takes no argument with line breaks, so the description, every line of it, goes in `.orchestra/run/feature-request.md`, which the `@` attaches to Claude's first message; tmux runs the same command, with Claude's hooks added, and cmux too, its split taking the keyboard focus. The file holds the description between an opening and a closing `<pasted_content id="<random>">` tag, the ID drawn afresh for each session: a description is often pasted from an issue or a web page, and the instructions say that text inside the tags may carry instructions you didn't write, which Claude follows only where your own message asks it to. orchestra's pane stays in view, saying `Talking the feature through with claude in the pane on the right, which closes once the feature is filed. Type /exit there to leave without filing; Ctrl+C here stops.`, and waits for the session to end. On a terminal, without `--plain`, a line under it, updated in place each second as Herdr reports Claude (in tmux and cmux, as Claude's hooks report it, to `.orchestra/run/interview-session/`), says whether Claude is working, waiting for you or waiting for a permission answer (a permission prompt, or the question whether to trust the folder), and how long the session has run; once the feature is filed it names the epic: `Filed <epic>: <title> (N tickets)`. The interview's method, in the instructions appended to Claude Code's own system prompt so that its tools and sub-agents work, adapts Matt Pocock's [grilling skill](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md) (MIT License; see [the notices](../THIRD_PARTY_NOTICES.md)). It is your own session, not a worker or an organ: your Claude Code setup applies, the project's `CLAUDE.md` included, but not every MCP server you have. It gets the ones the project's workers get ([MCP servers for workers](workers.md#mcp-servers-for-workers)), their definitions in `.orchestra/run/mcp.json` in the main checkout, with `--mcp-config .orchestra/run/mcp.json --strict-mcp-config`; with none chosen, or none chosen yet, or workers of another agent, `--strict-mcp-config` alone, no MCP servers at all. It gets Chrome as workers do, too, after those: `--no-chrome` when the project chose its servers without `claude-in-chrome`, `--chrome` when it chose it, whatever its workers' agent, and neither when it hasn't chosen; Claude Code turns Chrome on by itself, past `--strict-mcp-config`, once it is set up. Each server's tool definitions would otherwise go with every request the session makes: a headless breakdown on a machine with 12 servers, the claude.ai connectors among them, carried 259 tools, about 200,000 of the 227,000 tokens of its first request, and never called one. Workers of another agent (`--agent`) don't change that: a feature is talked through with Claude Code, as a spec is broken down.

1. Claude reads the description, the README and `CLAUDE.md` (or `AGENTS.md`), and the code the feature is likely to touch, and checks `bd list --status open` for tickets that already cover part of it. Then it interviews you in rounds. A round asks every question that can be asked yet, numbered, each with Claude's recommended answer; a question that depends on an answer still open waits for a later round. Claude looks facts up in the repository itself, with a sub-agent only for a wide search, rather than ask you; the decisions are yours. When nothing is left open, it sums up what you agreed and waits for you to confirm it.
2. It sums up what it will file, the epic, any child epics (only where the feature has separable parts) and how many tickets each gets, and the decisions settled, and asks you to go ahead. Nothing is filed until you agree.
3. It files the tree itself, with `bd`, laid out as a spec's breakdown lays it out ([The breakdown](#the-breakdown)), with the same rules for tickets that run side by side, but without a spec's metadata: the epic, whose description holds your description in full and, under `Decisions`, the decisions settled, as workers have no spec to read; each ticket under it, citing those decisions, with its acceptance criteria, its files as `files` metadata (which [footprints](#several-tickets-at-once) read), a blocks link to each ticket it builds on, and the `solo` label where it restructures code most tickets touch. Every issue it files carries the feature run as `feature_run` metadata. It checks the tree (`bd show`, `bd list --parent`, `bd dep cycles`). Last, it writes the epic's ID to `.orchestra/run/feature.json` (`{"epic":"<id>"}`), the one file it writes, and tells you that the feature is filed and that the run starts next.
4. Once `feature.json` names the epic and Claude's turn is over (Herdr, or in tmux and cmux its hooks, report it idle, or done), orchestra closes Claude's pane, which ends Claude Code, and its own pane has the keyboard focus again: you don't type `/exit`. A `feature.json` written while Claude is still working, or waiting on a permission answer, leaves the pane open until that turn ends.
5. orchestra checks the epic as bd has it, as it checks a spec's tree but for what depends on a spec's metadata. An epic `bd` can't show, or an issue that isn't an epic, ends the run with exit code 2: `orchestra won't run what the interview handed back: <why>`. It warns of what else is amiss, on standard error (`warning: …`) and in the log (`FEATURE warning: …`), running the epic all the same: open tickets under it without `files` metadata, whose files orchestra then guesses, or without acceptance criteria, and blocks cycles holding one of them. Then it says `filed the feature as <epic>, <title> (N tickets)` (`(1 epic, 3 tickets)` with child epics) and starts the run on the epic, without asking.

To end the session without filing, type `/exit` in Claude's pane, or close the pane: orchestra closes it if it is still open, and says that nothing was filed (below).

Claude only reads and files tickets: it doesn't edit files, commit or push. Ctrl+C in Claude's pane is Claude Code's, which interrupts or clears with it. Ctrl+C in orchestra's pane, SIGTERM or SIGHUP close the session's pane, which ends Claude Code, and stop orchestra (exit code 130): `orchestra: stopped before the run started.`, then, if an epic was handed back, `The interview filed <epic>; start the run on it with: orchestra --ticket <epic>`.

When Herdr, tmux or cmux can't split the pane or start Claude Code in it, or Claude Code doesn't show in the new pane within a minute, orchestra closes any pane it made, says why in one line (`orchestra couldn't open the interview in a pane beside its own, so claude takes this terminal: <why>`), and hands its own terminal to the session instead, as `claude --append-system-prompt-file .orchestra/run/spec-prompt.md --strict-mcp-config -- "Here is the feature I'd like to talk through (feature run <run>): @.orchestra/run/feature-request.md"`, saying `Talking the feature through with claude, which files it as tickets once you agree. Type /exit to come back.` and waiting for it to end. orchestra can't end that session by itself, so the instructions there have Claude, once the feature is filed, tell you to type `/exit` to come back; the run then starts. There Ctrl+C is Claude Code's, not orchestra's; SIGTERM and SIGHUP still stop orchestra (exit code 130), the session with it. Ctrl+Z suspends orchestra with the session, as the shell suspends any program, and `fg` brings both back. orchestra run outside tmux, its workers in a detached session, has no pane of its own to split: the session gets its terminal this way from the start, without that line. With no pane and no terminal (its input or output not one, as under cron), there is nobody to talk to: the run ends with exit code 2 and nothing filed, `orchestra couldn't talk the feature through: talking the feature through needs you at a terminal, and orchestra's input or output isn't one: orchestra --spec <file> breaks a request written to a file down unattended`.

orchestra removes an earlier `.orchestra/run/feature.json` before the session. When the session leaves none, having filed nothing under its feature run, orchestra says `No feature was filed; nothing to run.` and exits with 0. When it filed issues all the same (you left it before it handed the epic back), orchestra lists them, under `The interview ended without handing the feature back. It filed N epics and M tickets:`, followed by `Start the run on it with: orchestra --ticket <epic>`, and exits with 0 without running them; `bd list --metadata-field feature_run=<run> --all` lists them again. A stop before the hand-back names that epic too. A `feature.json` it can't read, or that names no epic, is taken as none, after saying why (`orchestra can't read the epic the interview handed back: …`). Without `claude` on the `PATH` there is no session: `orchestra can't talk the feature through: it needs Claude Code, and …` (exit code 2). The log has `FEATURE interview: <request>`, then `FEATURE interview filed epic <epic> (N tickets): <request>`, `FEATURE interview filed nothing`, `FEATURE interview handed nothing back; it filed <N epics and M tickets> under <epic>` or `FEATURE not talked through: <why>`.

### A whole app from a spec

```
orchestra --spec ~/specs/shop.md
```

`--spec <file>` (or `ORCHESTRA_SPEC=<file>`) builds what a spec describes, a feature or a whole app written down in a Markdown or plain-text file, with nobody there: it commits the spec, has Claude break it down into Beads tickets, and runs them, asking nothing on the way. The run is that of `--ticket <root epic>`, the epic the breakdown files for the spec, with what a night alone needs:

- **Workers in Claude Code's `auto` permission mode**, unless `--worker-permission-mode`, `WORKER_PERMISSION_MODE` or `"worker_permission_mode"` gives another: its classifier decides, and a worker waits on a permission prompt only when it can't ([Permission mode](workers.md#permission-mode)).
- **A ticket's worker is told of the spec**: its first message says the ticket is part of the spec at its path, to read the sections the ticket cites, and to treat the spec as settled ([Worker prompt](workers.md#worker-prompt)).

Like every run, it [waits out the usage limit](#the-usage-limit) rather than end. The `START` line names the spec, `… on build/shop · spec .orchestra/specs/shop.md (done so far: 0, limit: none, …)`, with a line under it, `  spec: epic shop-a1b, broken down from: .orchestra/specs/shop.md`; so do the dashboard's title line, the run lock (`spec`) and the event stream's `start` record (`spec`, with `scope` the root epic). `--refine` (or `ORCHESTRA_REFINE=1`) breaks the spec down with you instead ([Refined with you](#refined-with-you)).

Problems with the spec are setup problems, listed with the rest (exit code 2): `Spec not found: <file> (--spec).`; `The spec <file> (--spec) is empty: write what to build in it first.`; `The spec <file> (--spec) isn't text: give a Markdown or plain-text file, in UTF-8.`; `Cannot read the spec <file> (--spec): <why>.`; a spec in the repository's `.git` folder; and one where git ignores it, as workers only see committed files: `git ignores <path>, where the spec (--spec) is kept, and workers only see committed files: move the spec, or stop ignoring that path (git check-ignore -v <path> says where).` (`ORCHESTRA_SPEC` in place of `--spec` when the variable gave it). So are `--spec` with `--feature`, `--ticket` (or `ORCHESTRA_TICKET`) or `--tickets`, `--refine` without a spec, and `DONE_SO_FAR` at a `LIMIT` given, which would break the spec down and run none of it.

Workers see only what is committed, so once the startup checks have passed and the run holds its lock, orchestra commits the spec before anything is broken down: a file in the repository where it is (`docs/shop-spec.md`), one outside it as a copy in `.orchestra/specs/<its name>` (over the copy an earlier run made there). That path in the repository names the spec from one run to the next. A copy is named after its file alone, so its commits record where it came from (`Spec-Source: ~/specs/shop.md`), and a spec from another folder with the same file name doesn't start, exit code 2, as it would take the other's copy and update its tickets for the whole of itself: `The spec <file> (--spec) has the name of another: .orchestra/specs/shop.md holds the copy of another spec, ~/specs/shop.md, …`. Give it another file name, which its copy takes, or, if it is that spec moved, copy it over `.orchestra/specs/shop.md` and give `--spec` that path. A copy whose commits record no source, made before orchestra recorded them, is taken by the next spec of its name. orchestra commits that path alone, on the branch checked out, as `orchestra: add spec <name>`, or `orchestra: update spec <name>` once it has changed, with its SHA-256 in the message (`committed the spec <path> (sha256 <12 hex>)`); a spec committed already as it is stays as it is (`the spec <path> is committed already (sha256 <12 hex>)`). The main checkout must have nothing uncommitted besides the spec itself: anything else stops the run with exit code 5 before anything is committed (`orchestra cannot start: uncommitted changes in <repo>. …`). Every ticket broken down from the spec cites it, so the spec is left out of their [footprints](#several-tickets-at-once) unless a ticket's `files` metadata lists it. The log has `SPEC: committed <path> (sha256 <12 hex>)` or `SPEC: <path> is committed already (sha256 …, commit …)`. Before it commits anything (the spec, or the [setup](setup.md) of a repository `init` hasn't set up), the run brings its branch up to its upstream, as a run [does](#run) before its first ticket, and doesn't fetch again as its loop starts: `BASE: fast-forwarded main to origin/main (3 commits)`, or a warning (`warning: BASE_DIVERGED: …`) where the branch stays as it is.

#### The breakdown

Without `--refine` the spec is taken as complete and final, the end result of refinement, and nobody is asked anything. orchestra runs `claude -p` in the main checkout, with your own Claude Code setup (your settings, the project's `CLAUDE.md`) but only the MCP servers workers get, as a feature's session ([Talked through](#talked-through)), its instructions appended to Claude Code's system prompt from `.orchestra/run/spec-prompt.md`, and a first message naming the spec: its path, SHA-256 and commit, and how long the session may take. Its tools are Read, Glob, Grep, Agent and Bash; Bash runs only `bd` and read-only `git` (`git log`, `git show`, `git diff`, `git grep`, …), Edit, Write and NotebookEdit are denied, and it starts with `--permission-mode dontAsk` (and `--permission-prompts none` where `claude --help` lists it), so anything else is denied without asking. It reads the spec, the README, `CLAUDE.md` or `AGENTS.md` and the code there is, and breaks the spec down into:

- a **root epic** for the spec, whose description sums the spec up;
- **child epics** where the spec has separable parts, nested as deep as it needs and no deeper;
- **tickets**, each one worker's session of work: a description citing the spec's sections by heading (§ "Sign-up") rather than restating them, acceptance criteria, a type, a priority, the files it changes as `files` metadata (the new ones included, a new folder as `web/src/`), a blocks link to each ticket it builds on, and the label `solo` where it restructures code most tickets touch.
- an **environment setup ticket**, filed first, when the spec needs a tool the repository doesn't have (a language runtime, a package manager, a database, a CLI the build calls) or the repository has no code yet: one ticket for all of the project's basic setup, P0 and `solo`, with a blocks link from every other ticket, so every other ticket waits for it. Its worker writes the project's [requirements](setup.md#the-machines-requirements), an entry in `"requires"` in `settings.json` for each tool, service and permission the tickets after it need: a check (the tool's version command, checking the version pinned in the ecosystem's own committed file: `mise.toml` or `.tool-versions`, `rust-toolchain.toml`, `.nvmrc`, `go.mod`'s `toolchain` line, `.python-version`), and an install with a user-level package manager or the tool's own installer (Homebrew, mise, rustup, the Bun or uv installer), never with `sudo`, or a manual step where only a person can meet it (`sudo`, a GUI installer, a licence, a permission). It installs nothing outside the list: it runs `orchestra requires`, which installs what the entries can, as every later run checks the list and installs what a machine lacks; a requirement still missing that only a person can meet, it asks you about with a question, so the run waits for your answer rather than build on a guess. Where there is no code yet, it scaffolds the project: the stack's generators (`create-next-app`, `cargo new`, `bun init`, …) run non-interactively at pinned versions, then the layout, the build, a first test and the lint, wired into the two checks `settings.json` names. It installs the dependencies and sets `setup` in `settings.json` to the command that installs them in a fresh worktree (`bun install --frozen-lockfile`, `npm ci`, `uv sync --frozen`, …), with `setup_files` where the default list misses the project's lockfile: the run runs `setup` in each new worktree [before its worker starts](#several-tickets-at-once), so no later ticket installs the dependencies itself. Last, it writes what to install, with the versions, into the repository's `CLAUDE.md` or `AGENTS.md` and README. A spec that adds a tool to a repository with code, such as Postgres to an existing app, gets the ticket without the scaffold; one that needs no new tool, in a repository with code, gets none.
- **spikes**, right after the environment setup ticket, for the facts the spec marks unverified (`[VERIFY]`, "to verify", "check that", an open question about an outside API, library or tool) that tickets rest on: a short ticket for a fact, or for a few related ones, with the label `spike` and P1, whose worker checks it against the library's source, its documentation or a minimal program, changes nothing in the repository, and says what it found in its close reason. The tickets that rest on the fact wait for its spike, so a wrong fact stops them before they are built on it, rather than each failing late, one after another. A spike that finds a fact false asks you about it with a question blocking those tickets, rather than change the spec; they wait for your answer. A fact nothing rests on gets no spike, nor does one the repository settles.

It files two of them itself, with `bd`: the root epic, and the environment setup ticket where there is one, so that the run can start on that ticket early (below). The rest it gives in its answer (`--json-schema`), each issue with a key of its own, its parent, type, priority, title, description, acceptance criteria, labels, files, and the issues it waits for, each by its key or the ID of an issue filed already. orchestra files them with `bd`: each issue after its parent and the issues it waits for, with the spec's metadata and its links to them, so that `bd` failing part way leaves every issue filed with all its links. A session that filed every issue itself took a turn for each `bd create`, each turn reading the whole session's context again: on one spec, 46 of its 56 turns and most of its 21 minutes. An answer orchestra can't file as given (a key used twice, a key or ID that names no issue, a cycle among the parents, the blocks links or the two together, such as an epic waiting for a ticket under it) has none of it filed, and ends the run as a breakdown that didn't finish does (below): `orchestra couldn't break the spec down: its answer can't be filed: its blocks links make a cycle: a → b → a`. `bd` failing part way says how far it got: `orchestra couldn't break the spec down: orchestra filed 12 of its answer's 40 issues, then couldn't file <key> (<title>): <why>`. An update of the tree ([Carrying on across nights](#carrying-on-across-nights)) still files what it changes with `bd` itself.

Every issue carries the metadata `spec`, the spec's path; the root epic also `spec_sha256` and `spec_commit`, the version of the spec it was filed for, which orchestra sets last of all, once everything is filed ([Carrying on across nights](#carrying-on-across-nights)). Where the spec leaves a choice open, the breakdown takes the most conservative reading consistent with it, the smallest, plainest and most reversible, and writes the assumption down where it will be read: in the description of each ticket that depends on it (`Assumed: …`), and in its answer, each naming those tickets, which orchestra writes under `Assumptions` in the root epic's notes for you to read in the morning. It files no question: nobody would answer it.

It may take 60 minutes (`"spec_timeout"` in `settings.json`, or `--spec-timeout 90m` or `ORCHESTRA_SPEC_TIMEOUT` for one run), at effort `high` (`"spec_effort"`, or `--spec-effort` or `ORCHESTRA_SPEC_EFFORT`: `low`, `medium`, `high`, `xhigh` or `max`). On a terminal a spinner counts what it files, `⣾ Breaking the spec down with Claude… 4 epics · 23 tickets · 6:12 (Ctrl+C stops)`, and ends `◆ Spec broken down: 5 epics, 31 tickets (14m2s)`. Plain output gets `breaking the spec down with claude… (ctrl+c stops)`, a line for each epic filed, `SPEC: filed epic <id>: <title>`, and every minute `SPEC: breaking the spec down: 4 epics and 23 tickets filed so far (6m)`. It ends `broke the spec down into <root> (5 epics, 31 tickets)`, the root epic among the epics, followed by the assumptions, `Assumed where the spec leaves a choice open:` and a line each. The log has `SPEC: breaking <path> down with claude (effort high, time limit 1h)`, each epic filed, what the session cost (`SPEC: breakdown $4.1234 in 212 turns, 14m2s, session <id>`, or `SPEC: claude session <id> gave no result (…)`), what orchestra filed from its answer (`SPEC: filing the 34 issues of the breakdown's answer under <root>`, then `SPEC: filed 34 issues from the breakdown's answer (4s)`), `SPEC: broken down into <root> (5 epics, 31 tickets)` and a `SPEC: assumed: …` line each.

Then orchestra checks the tree the breakdown filed, as bd has it. The root epic it named must be an epic and carry no other spec's metadata, else the run doesn't start: `orchestra won't run what the spec's breakdown filed: <why>`, with what it filed (below), exit code 2. orchestra sets the root epic's `spec`, `spec_sha256` and `spec_commit` where the breakdown left them out or wrong, and warns of what else is amiss, on standard error (`warning: …`) and in the log (`SPEC: warning: …`), running the tree all the same: issues carrying the spec's metadata outside the root epic, which the run leaves out; issues under it without the metadata, whose workers aren't told of the spec; open tickets without `files` metadata, whose files orchestra then guesses, or without acceptance criteria; and blocks cycles holding one of the spec's issues (`a blocks cycle: a → b → a; none of them can start until it is broken (bd dep remove)`). Then the run starts on the root epic, without asking.

The environment setup ticket doesn't wait for the whole breakdown, as nothing else can start before it merges: once the breakdown has filed the root epic and then, as its first ticket, that one (`solo`, P0, open), the run starts on it alone while the breakdown files the rest: `SPEC: the run starts on <id>, the environment ticket, while the breakdown files the rest of <root>` (on a terminal `◆ Starting on <id>, the environment ticket, while the breakdown files the rest`), then the `START` line. The tickets filed after it, ready or not, join the run only once the breakdown is over and the checks above have passed (`  the rest of <root> is filed: its tickets join the run`), as ready tickets do; a run whose environment ticket is done before then waits for them (`  waiting for the rest of <root> to be filed`) rather than end. On a terminal the run's lines show above the breakdown's spinner until it is over, then the dashboard opens with them; plain output has both as they come. A breakdown that fails or is stopped after that ends the run as below, exit code 2 or 130, with the loop stopped as Ctrl+C stops it: `INTERRUPTED: stopped because the spec's breakdown failed while <id> (tab …) were running; their tabs and worktrees are left open`, the environment ticket's worker left in its tab for the next run to carry over. One that changes the environment ticket after the run started on it gets a warning: `the breakdown changed <id> after the run started on it: a worker started on it before then works from it as it was (bd show <id>)`. With no environment ticket filed first, with `--refine`, for an update of the tree and for a breakdown carried on, the run starts once the breakdown is over.

A session that fails, runs out of time or names no root epic ends the run with exit code 2: `orchestra couldn't break the spec down: <why>` (or `orchestra: the spec's breakdown named no root epic, so there is nothing to run.`, with `It says: <why>` when it gave a reason), then what it filed for the spec, up to 20 issues (`It filed 3 epics and 12 tickets for <path>, under <root>:`, an issue a line, then `… and 9 more: bd list --metadata-field spec=<path> --all`), and `Run it again to carry on: orchestra --spec <file>`. Ctrl+C stops it, exit code 130 (`orchestra: stopped while the spec was broken down, with <root> filed.`, and the same last line). What was filed stays filed, and the next run carries on from it.

#### Refined with you

`--refine` (or `ORCHESTRA_REFINE=1`) is for a spec with decisions still open: you break it down with Claude in an interactive Claude Code session in the main checkout, which takes the spec as mostly settled and asks only where it leaves open a decision that changes what gets built, and that neither the spec nor the repository answers; often there is none. The session opens as a feature's [talked through](#talked-through) does, with the same instructions in their spec mode: in a pane split off orchestra's, to its right (Herdr, tmux or cmux), or on orchestra's own terminal when orchestra runs in no pane or the split fails (`orchestra couldn't open the refinement in a pane beside its own, so claude takes this terminal: <why>`). Its first message is `Break the spec at <path> down into Beads tickets with me (sha256 <hex>, commit <hash>).`

1. Claude asks in rounds, as when it talks a feature through: numbered questions, each with its recommended answer. A choice that changes nothing you or a later ticket would notice it takes without asking, writing `Assumed:` in the tickets that depend on it.
2. Once nothing is left open, it sums up the root epic and each child epic, what each covers and how many tickets it gets, and the decisions settled, and asks you to go ahead. It files nothing until you agree.
3. It files the whole tree itself, with `bd`, laid out as the headless breakdown lays it out, with the decisions settled with you under `Decisions` in the root epic's description (no `Assumptions` notes, and no assumptions printed), and writes the root epic's ID to `.orchestra/run/spec.json` (`{"epic":"<id>"}`), the one file it writes. Then it says the run starts next.
4. Once `spec.json` names the epic and Claude's turn is over, orchestra closes the pane, checks the tree as above, and starts the run on it without asking.

orchestra's pane says meanwhile `Breaking the spec down with claude in the pane on the right, which asks you only what the spec leaves open and closes once the tickets are filed. Type /exit there to leave without filing more; Ctrl+C here stops.`, and on a terminal, without `--plain`, a line under it: whether Claude is working, waiting for you or waiting for a permission answer, the time so far, and `· 3 epics, 18 tickets filed`, counted from bd by the spec's metadata every 5 seconds. On orchestra's own terminal it says `Breaking the spec down with claude, which asks you only what the spec leaves open and files the tickets once you agree. Type /exit to come back.`, and Claude tells you to type `/exit` once the tickets are filed: orchestra can't end that session by itself.

`/exit`, or closing the pane, before the root epic is handed back files nothing more and ends the run: with nothing filed for the spec, `The refinement filed nothing; nothing to run.` and exit code 0; with issues filed, `orchestra: the refinement ended without handing back a root epic, so there is nothing to run.`, what was filed as above, and `Run it again to carry on: orchestra --spec <file> --refine`, exit code 2. Without a terminal, and outside any pane, there is nobody to ask: once the spec is committed, the run stops with `orchestra couldn't break the spec down: refining the spec needs you at a terminal, …` (exit code 2). A nightly job runs without `--refine`: a spec refined by day carries on at night without it, as below. The log has `SPEC: refining <path> with claude and you`, and `SPEC: the refinement ended with nothing filed for <path>` or `SPEC: the refinement ended without handing back a root epic`.

#### Carrying on across nights

Run again, the same command carries on rather than break the spec down again. Once the spec is committed, orchestra looks for its root epic, which an earlier run filed: the epic whose `spec` metadata is the spec's path and whose parent doesn't carry it (`bd list --metadata-field spec=<path> --all` lists all the spec's issues). Its `spec_sha256` and `spec_commit` name the version of the spec its tree was filed for:

- **The spec unchanged**, the same SHA-256, and the root epic open: no breakdown, and `--refine` asks nothing. The run is scoped to the root epic and carries on with what is left, carrying over the workers the last run left, as any run does: `the spec <path> is unchanged; carrying on with <root>`.
- **Unchanged, and the root epic closed**, as orchestra closes it once the last of its tickets merges: there is [nothing to run](#nothing-to-run): `✓ <path> is built (<root>)`, exit code 0. The log says `SPEC: <path> is unchanged, and <root> is closed`.
- **The spec changed**: the new version is committed (`orchestra: update spec <name>`), and the breakdown, headless or with `--refine`, updates the tree for the change: `the spec <path> changed since <root> was filed: updating its tickets`. orchestra writes `.orchestra/run/spec-update.md` for it: the change, as `git diff` of the spec from the root epic's `spec_commit` to the new commit, and the tree under the root epic, open and closed, an issue a line. The breakdown's first message names the root epic, the version it was filed for and that file. It files only what the change needs, under the same root epic (a new child epic for a new part), with an environment setup ticket first, as above but without the scaffold, for a change that needs a tool the repository doesn't have (or updates the tree's own, while it is still open), and spikes after it for the unverified facts the change adds; never changes a closed issue (what changes a closed ticket's work is a new ticket); defers each open ticket the change makes obsolete with a note naming the change, moving or removing the blocks links that waited on it; updates the open tickets the change alters; and leaves those in progress alone, filing a ticket blocked by one where the change alters it. It notes on the root epic what changed and what it filed, updated and deferred, with its assumptions (headless) or the decisions settled (with `--refine`), and sets `spec_sha256` and `spec_commit` to the new version last of all. orchestra then checks the tree and says `updated <root> for the spec's change (6 epics, 40 tickets)`, counting the whole tree, and the run starts on it. An update that names another root epic ends the run with exit code 2 (`it named <other> as the root epic, not <root>, whose tree it was to update`); one stopped says `orchestra: stopped while <root>'s tree was updated for the spec's change.`, and one that didn't finish lists the tree, `The spec's tree has 6 epics and 40 tickets for <path>, under <root>:`. Where git can't give the diff, as for a root epic with no `spec_commit`, the file says why, and the breakdown compares the spec as it is with the tree (`SPEC: no diff of the change: <why>` in the log).
- **No `spec_sha256`**: the breakdown that filed the root epic didn't finish (stopped, out of time, failed). It runs again as for a new spec, filing only what is missing under that root epic: `the breakdown that filed <root> didn't finish: carrying it on`.

So the nightly command stays the same; to change what gets built, change the spec by day (a spec in the repository may be left uncommitted: the run commits it). Two root epics for one spec, one filed by hand say, are a setup problem, exit code 2: `The spec <path> has two root epics, <a> and <b>: epics carrying its metadata (spec) whose parent doesn't. A spec run carries on with one, so keep one: put the other under it (bd update <b> --parent <a>), or take the spec's metadata off it (bd update <b> --unset-metadata spec).` When bd can't list the spec's issues, the run stops with exit code 4: `orchestra can't look for the spec's root epic, which an earlier run filed: …`.

#### From an empty repository

```
mkdir shop && cd shop && git init && orchestra --spec ~/specs/shop.md
```

A spec run starts from nothing. In a repository `orchestra init` hasn't set up (no `.orchestra/settings.json`, which `init` writes with the worker prompt, nor a `.claude/worker-prompt.md` from before `init`), even one with no commit yet, it sets the repository up itself, as `init` does without a terminal, and commits that with the spec, rather than stop with `orchestra isn't set up in this repository yet`: see [A spec run's setup](setup.md#a-spec-runs-setup). The breakdown's first ticket, the [environment setup](#the-breakdown), then lists the toolchain in `"requires"` and installs it with the list's own commands, scaffolds the project and its checks, installs the dependencies and sets `setup`. Outside a git repository the run says `Not inside a git repository: cd into the project first, or for a new one, start it with: git init` (exit code 2).

#### Every night

A spec run needs nobody, so a scheduler can start it each night: cron, or launchd on macOS. Started by one, `orchestra` has no terminal: it prints plain lines, never asks, and runs its workers in tmux, in a detached session named after the repository's folder (`orchestra-shop`), which you can attach to in the morning. It needs what a run always needs: the main checkout clean, on the branch you want the work on, and no other run there (a run still going when the next starts is left alone, and the new one exits 2).

Once, by day, put the main checkout on the branch the nights build on:

```
cd ~/code/shop
git switch -c build/shop
```

If the spec leaves decisions open, break it down by day too, while you are there to answer: `orchestra --spec ~/specs/shop.md --refine`. The run starts on the tickets as soon as they are filed (press **s** in the dashboard to stop it after its first tickets), and the nights carry it on. Otherwise the first night breaks the spec down by itself.

Then write the job's script. A scheduler gives a job little of your shell's environment, so the script takes your `PATH`, where `orchestra`, `tmux`, `git`, `bd` and `claude` are found (and the workers' tools: they run with orchestra's `PATH`), and `HOME`, as they are in the shell you write it from: the `$`s are expanded as it is written. `--terminal tmux` overrides a `"terminal"` in `settings.json`, as a job runs in no Herdr pane or cmux terminal.

```
cat > ~/shop-nightly.sh <<EOF
#!/bin/sh
# orchestra's nightly run on the shop spec: written with the PATH and HOME of the shell that wrote it
export PATH="$PATH" HOME="$HOME"
cd "$HOME/code/shop" || exit 1
exec orchestra --spec "$HOME/specs/shop.md" --terminal tmux
EOF
chmod +x ~/shop-nightly.sh
```

With cron, `crontab -e` and a line to start it at 22:00, its output (setup problems included, which come before the log opens) appended to a file:

```
0 22 * * * $HOME/shop-nightly.sh >> $HOME/shop-nightly.log 2>&1
```

On macOS, a launchd agent does the same, and also starts a job the Mac slept through once it wakes; `caffeinate -i` keeps the Mac awake while the run goes:

```
mkdir -p ~/Library/LaunchAgents
cat > ~/Library/LaunchAgents/local.orchestra.shop.plist <<EOF
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key><string>local.orchestra.shop</string>
  <key>ProgramArguments</key>
  <array><string>/usr/bin/caffeinate</string><string>-i</string><string>$HOME/shop-nightly.sh</string></array>
  <key>StartCalendarInterval</key>
  <dict><key>Hour</key><integer>22</integer><key>Minute</key><integer>0</integer></dict>
  <key>StandardOutPath</key><string>$HOME/shop-nightly.log</string>
  <key>StandardErrorPath</key><string>$HOME/shop-nightly.log</string>
</dict>
</plist>
EOF
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/local.orchestra.shop.plist
```

`launchctl kickstart gui/$(id -u)/local.orchestra.shop` starts it at once, to try it; `launchctl bootout gui/$(id -u)/local.orchestra.shop` removes it. Try the job once either way and read its log: a job runs with less than your shell has, and `claude` must be logged in there.

In the morning, in the main checkout:

```
tail -n 5 ~/shop-nightly.log                                              # how the night ended
jq -c 'select(.kind == "end")' .orchestra/run/events.jsonl | tail -n 1   # its exit code
cat ".orchestra/reports/$(ls .orchestra/reports | tail -n 1)"            # the run report
bd show "$(jq -r 'select(.kind == "start" and .spec) | .scope' .orchestra/run/events.jsonl | tail -n 1)"
orchestra answer                                                          # answer the questions workers left for you
```

The run report says what was finished, what was set aside and why, and what needs you. The fourth line shows the spec's root epic: its notes hold the `Assumptions` the breakdown made where the spec left a choice open, each naming the tickets that depend on it. Where one is wrong, change the spec: the next night updates the tickets for the change. Review the branch's merged tickets as a pull request. The exit code says how the night ended ([Exit codes](#exit-codes)): 0 when it ran out of tickets or the spec is built; 8 when the account's usage limit held it longer than `usage_limit_wait`; 3 when a worker waited on you, in its window (`tmux attach -t orchestra-shop`); 2 for setup problems, in the job's log; 5 for uncommitted changes in the main checkout. Whatever stopped it, the next night carries on, the workers it left in their windows included.

### Overnight

`orchestra --overnight` (or `ORCHESTRA_OVERNIGHT=1`) runs the current tickets as `--tickets` does, once a pre-flight has cleared the run to work through the night, so that it doesn't stop at 1am on something you could have settled at 11pm. The pre-flight runs once the startup checks have passed and the run holds its lock, before its start is recorded. Its checks each pass, warn or fail: a failure is what would stop the run, or every ticket's merge, in the night; a warning what would slow the night, cost it tickets or leave something for the morning. It lists them in a checklist, each with its verdict:

```
◆ Overnight pre-flight: 1 failed, 1 passed
  ✓ <what the check found>
  ✗ LIMIT=10 is set: the run would stop after 10 tickets
```

The checklist's first line is the base branch brought up to its upstream, as a run's start [does](#run) without a pre-flight, before the other checks read it: `fast-forwarded main to origin/main (3 commits)`, `main has every commit of origin/main`, or `main follows no upstream: nothing to fetch`. A fetch that fails, or a branch that has diverged, is a warning, the run building on the branch as it is; uncommitted changes in the main checkout, or the checkout off its branch, fail it, as they would stop the run before its first ticket. The setup, the requirements and the check commands (`check_fast`, `check_full`, `check_own`) a fast-forward brings in in `.orchestra/settings.json` are the run's from then on, for the checks after it too, the merge check on the base among them; a file it can't read again leaves them as they were, with a warning (`fast-forwarded main to origin/main (1 commit), but .orchestra/settings.json could not be read again: …; the run keeps the setup, the requirements and the checks it read before`). So is the worker prompt it brings in, for the run's workers; one it can't read again, or without its `TICKET_ID` placeholder, leaves the one the run read, with a warning (`…, but the worker prompt could not be read again: …; the run gives its workers the one it read before`). The run then doesn't fetch again; `--no-fetch` skips it (`main isn't fetched from its upstream (--no-fetch): the run builds on it as it is`).

The checks that fail, each refusing to start the run until it is fixed, in the checklist's order:

- **A ticket limit** (`--limit`, `LIMIT`, with `DONE_SO_FAR`), which would stop the run early: `LIMIT=10 is set: the run would stop after 10 tickets`. Its fix runs without one (`Run without a limit?`).
- **One ticket at a time** (`"concurrent"`, `--concurrent`), where one slow ticket holds up the night. Its fix runs as many at a time as the machine allows, one for each four cores, from 2 to 4, within `--machine-workers` or its default, half the cores (`Run 3 tickets at a time?`), for this run.
- **A permission mode that asks** (`"worker_permission_mode"`, `--worker-permission-mode`): in `default` (`manual`), or Claude Code's own default, a worker waits on a permission prompt and the run stops for it. `auto` and `acceptEdits` pass. Its fix starts the workers in `auto` (`Start workers in auto permission mode?`), for this run.
- **claude not starting or not logged in**, as `claude auth status --json` says: `claude isn't logged in: no worker could start. Log in with 'claude auth login'`.
- **Too little free disk** where the worktrees go, each holding its own dependencies: under 20 GB, or the GB `"overnight_free_disk_gb"` in `settings.json` gives (`0` doesn't check). Where orchestra can't tell, it is a warning.
- **The merge check failing on the base branch** (`"check_fast"`), run once on its head in a worktree of its own, the setup (`"setup"`) first, within `"check_fast_timeout"`, with `Running the merge check on main…` meanwhile: where it fails there, every ticket's merge would fail. The checklist says what failed, and the whole output is in `.orchestra/run/check-base.log`.

The warnings, which never refuse to start the run, among the failures in the checklist (the merge check stays last):

- **The account at its usage limit now**, from the smallest call `claude` answers (one turn, a short system prompt, no tools: a fraction of a cent, at the workers' model): `the account is at its usage limit now ("You've hit your session limit · resets 7pm"): no ticket starts until it resets, at 19:00, in 4h`, and where the run's wait for it runs out before that, that the run would stop. Workers of another agent (`--agent codex`) aren't asked about.
- **A short wait for the usage limit** (`"usage_limit_wait"` under 5h, or `0`), where the session limit, reached in the night, would stop the run. Its fix waits the default 6h (`Wait up to 6h for the usage limit to reset?`), for this run.
- **No ticket limit** (`"ticket_limit"`, `--ticket-limit`), where a hung worker holds its slot all night. Its fix gives each ticket's worker 2h (`Give each ticket's worker 2h?`), for this run.
- **Another orchestra run on the machine**, named by its repository, PID and workers, from the machine's folder of runs: their workers and checks slow each other down.
- **A busy machine**: a 1-minute load past 1.5 per core, or the kernel's memory pressure at warn or worse, naming the three processes that use most CPU, or memory (`the machine is busy, a load of 23.4 on 10 cores, memory pressure normal (most of it cc1plus 390%, …)`).
- **A large virtual machine**, one holding more than 4 GB of memory (Apple's Virtualization framework's, which Docker Desktop, OrbStack, Colima and Podman use, QEMU's, VirtualBox's, VMware's, Parallels'), named with whose it is where orchestra can tell (`a virtual machine holds 8.0 GB of memory (com.apple.Virtualization.VirtualMachine, PID 40); Docker Desktop is running`).
- **The machine on battery**, as `pmset -g batt` says on macOS, the power supplies in `/sys/class/power_supply` on Linux: it would run flat, or sleep, in the night.
- **A worker prompt or verifier older than orchestra's templates**, as a run's start notes it (a run with `--prompt` has none). Its fix brings them up to date as `orchestra init --update` does and commits that on the branch the run works on (`Bring them up to date (orchestra init --update) and commit that?`), as the run won't start on uncommitted changes, and the run's workers then follow the prompt it committed; `git show` reads what changed.
- **How many tickets are ready**, and how many more wait only on open questions, those the pre-flight puts to you next: `2 tickets are ready, and 1 more waits only on questions, to be ready once they are answered`. With none ready it is a warning: the run would end at once.

In a terminal it then offers, one by one, each fix orchestra can make (`Run without a limit?`, yes to start with), makes those you take before the run starts (`◆ Fixed: the run has no ticket limit`), and, while a failed check is left without its fix, asks `Start the run anyway, with 1 check failed?`, no to start with. Esc or Ctrl+C there exits with code 130, with nothing changed but the base branch where the first check fast-forwarded it, which the stop says: `orchestra: stopped before the run started; its pre-flight fast-forwarded main to origin/main (3 commits), nothing else was changed.` A failed check left refuses to start the run, exit code 2, as a setup problem does: `orchestra --overnight cannot start: 1 check failed. Fix what the checklist says, or start anyway with --force-overnight.` `--force-overnight` starts the run with its failed checks left, without asking, and says so: `overnight pre-flight: starting with 1 check failed (--force-overnight)`. Without a terminal (plain output, `--plain`, or stdin or stdout not a terminal), nothing is asked and no fix made: the checklist is printed, plain, after the time (`  failed: LIMIT=10 is set: …`), and a failed check refuses to start the run unless `--force-overnight` is given. The log keeps the checklist and the fixes made, for the morning.

Cleared to start, the pre-flight puts every open question in the run's scope (an issue labelled `human`: with `--ticket`, one that blocks the ticket or one under it, or is under it itself; else every one) to you before the run starts, so that none keeps its tickets waiting all night: in a terminal it opens the [answer talk](dashboard.md#the-answer-talk), a Claude Code session in a pane beside orchestra's (or on orchestra's terminal) that asks each question one by one with its options, the recommended one first and a free-form line, and records your answer with `bd human respond`, which closes the question and frees the tickets it blocked (`◆ Answered 2 questions`). The run starts once the talk is over. A question you leave open (`/exit` in the session), or every one without a terminal, is said in a checklist of its own with the tickets it keeps waiting, and in the log:

```
◆ Overnight pre-flight: 1 question left open
  ! k-9 (Which flag name?): k-5 waits on it. Answer it with 'orchestra answer k-9' (or 'bd human respond k-9')
```

Ctrl+C during the talk exits with code 130 before the run starts, the answers given recorded.

A question a worker asks during the night doesn't open the [answer talk](dashboard.md#the-answer-talk) by itself, whatever `"questions"` says: nobody is there to answer it, and the run's end would wait for the talk's pane to close, holding the run's lock, the machine kept awake, until the morning. The dashboard's hint says it waits (`a to answer 1 question`), as with `"questions": "key"`: **a** opens the talk; else the question waits for `orchestra answer`.

The `START` line says the run is overnight after its scope, `… on main · overnight (done so far: 0, …)`, the dashboard's title line has a small blue `overnight` badge after the version for the whole run (the first thing to give way in a pane too narrow for the line), and the event stream's `start` record has `"overnight": true`. `--overnight` goes with `--ticket` (the ticket and its subtickets, checked the same way) and with `--tickets`, and never asks what to work on; with `--spec` or `--feature` it is a setup problem, as is `--force-overnight` without it.

An overnight run has nobody to answer it until the morning, so it doesn't stop for a ticket that needs you for itself alone: it sets the ticket aside instead, deferred with a note saying why, its worktree and tab left for review, and goes on with the rest. The line says so, `<id>: its worker was blocked, waiting on a dialog, for over 4min -> noted and deferred, the run being an overnight one (BLOCKED); worktree <path> and tab <tab> left for review`, the dashboard's row reads `↷ deferred` (`set aside overnight: BLOCKED`), and the run's report lists the ticket with the others set aside. Its worker stays in its tab, followed there as any worker left in its tab is ([Tickets set aside](#tickets-set-aside)): should it close the ticket, once you answer it say, it merges (`LATE_CLOSE`). Each condition, one by one:

- **Set aside**: a worker idle with its ticket still in progress, or gone from its tab with no session to resume, or gone a second time, or resumed and never taking up carrying on (`PAUSED`); one blocked on a dialog or a permission prompt for 4 minutes (`BLOCKED`); one whose status the terminal can't tell for 5 (`UNKNOWN`); one still going after the [ticket limit](#run) (`TICKET_LIMIT`), which the pre-flight offers for this; and a ticket back from its question whose worker is then gone from its tab with no session to resume.
- **Stop, as in any run**: what carrying on would make unsafe, or would only fail again: git failing in the main checkout (`GIT_FAILED`), uncommitted changes there or the run off its branch (`DIRTY_TREE`), a branch that doesn't fast-forward (`MERGE_FAILED`), the hold for the [environment](#several-tickets-at-once) (`ENVIRONMENT`), a requirement missing (`REQUIREMENTS_MISSING`), the terminal, Beads or a worker's start failing (`TERMINAL_FAILED`, `STATUS_UNREADABLE`, `READY_UNREADABLE`, `START_FAILED`, `TAB_FAILED`, `WORKTREE_FAILED`, `AGENT_BUSY`, `AGENT_NAME_TAKEN`), a `PANIC`, and the [usage limit](#the-usage-limit) held longer than `usage_limit_wait` (`USAGE_LIMIT`), which the pre-flight warns of.

An overnight run keeps the machine from sleeping while it goes, so that no worker is cut off mid-commit in the night: once the pre-flight has cleared the run it starts `caffeinate -i -w <orchestra's PID>` on macOS, or on Linux `systemd-inhibit --what=idle:sleep … tail --pid=<orchestra's PID> -f /dev/null`, and stops it as the run ends, after the organ phase; given orchestra's PID, the command ends by itself however orchestra ends. The checklist says so (`the machine is kept awake while the run goes (caffeinate)`), and warns where the command isn't on the PATH, or the system has none: set the machine not to sleep then. The log says when it started, and when it ended before the run did. Closing a laptop's lid still puts it to sleep.

`"keep_awake": true` in `settings.json` has every run keep the machine awake the same way, not only an overnight one: the command starts as the run starts and stops as it ends, the log saying so, or that nothing keeps the machine awake where the command is missing.

## Several tickets at once

With `concurrent` above 1, up to that many workers run side by side, each in its own worktree and tab. What keeps it safe:

- **No ticket runs twice.** A ticket that's been handed out isn't picked again, even before its worker claims it.
- **Free slots don't wait.** While workers run, `bd ready` is read every 30 seconds: a ticket that becomes ready meanwhile (an answered question, a worker's follow-up, a closed blocker) takes a free slot then, and the dashboard's **In queue** follows.
- **A follow-up waits for the ticket it was filed from.** A ticket a worker files as it works, linked `discovered-from` its own ticket (`bd create --deps discovered-from:<id>`, or `bd dep add <follow-up> <id> --type discovered-from` after it is filed), is ready at once: `bd` doesn't count that link as blocking. But it was written against the code of the ticket it came from, which isn't on the base until that ticket merges, so it waits as it would for a blocker: while its source runs, waits on a question, is closed but not merged, or was [set aside](#tickets-set-aside) with its worker left in its tab, closed or not. The log says once `<id> waits: filed by <source>'s worker; waiting for it to merge`, `… waiting for it to merge (its worker was left in tab <tab>)`, or `… <source> closed but not merged (<why>)`, and it isn't counted in **In queue** meanwhile. Once the source merges (or is closed and on the base already), it starts from a base that has its code. So a follow-up unrelated to its source waits too, usually the few minutes until the source merges, in later runs as well while its source is labelled `unmerged`. A source that is open or deferred and not running holds nothing, as it may never run. With `--ticket`, `SCOPE_OPEN` names such a follow-up `filed by <source>'s worker; <source> is closed but not merged`.
- **A closed blocker has merged only once its branch has.** A ticket closed where the run didn't see it close (by hand, by another tool, by a worker an earlier orchestra left in its tab) went through no merge, though `bd` counts it done. So a closed ticket counts as not merged while git says its work is only on its branch: `wt/<id>` exists, has commits the base doesn't have, and the base doesn't hold its changes (squash-merged by hand). A branch with no commits beyond the base, or no branch at all, holds nothing back. Where git fails to tell, as when a `git` command times out on a loaded machine, the ticket counts as not merged until it can: the tickets it blocks wait, saying `<blocker> closed but not merged (git can't tell whether wt/<blocker> is on <base>: <git's error>)`, and the run asks git again at the next poll. The tickets it blocks, and the follow-ups filed from it, wait for it as for any blocker not merged (`<id> waits: <blocker> closed but not merged (wt/<blocker> is not on <base>)`), and the first time the run holds a ticket for it, it warns once: `CLOSED_UNMERGED: <blocker> is closed, but wt/<blocker> is not on <base>: the tickets it blocks wait until it merges; merge it into <base>, or delete the branch if its work isn't wanted (git branch -D wt/<blocker>)`. The `unmerged` label plays no part: a ticket the run never set aside doesn't carry it, so removing a label frees nothing. Merge the branch into the base, or delete it instead, and the tickets it blocks start at the next poll: the run asks git of a blocker once each time the base moves, and again whenever its branch is on another commit or gone. A worker that started on such a ticket anyway and stops with nothing done goes back in the queue (below), and [nothing to run](#nothing-to-run) counts its dependents among those waiting for their blockers to merge.
- **A ticket that started too early goes back in the queue.** A worker that finds its ticket needs another ticket's work, not merged yet, links that ticket as a blocker (`bd dep add <id> <blocker>`) and stops with the ticket open. When it stops with the ticket open or in progress, no commits beyond the base and a clean worktree, and `bd show` lists a blocker that hasn't merged (running, waiting on a question, open, deferred, or closed but not merged), the ticket started too early, and all it needs is to wait: orchestra reopens it if the worker left it in progress, notes on it `Orchestra: started before <blocker> merged; back in the queue until it does.`, and removes its worktree, branch and tab, which hold nothing. The log says `WAITS_FOR_MERGE: <id> waits for <blocker> to merge; …`, and the dashboard shows the ticket `◷ waiting`. Whether a blocker has merged is the same here, in the holds above and in `DEFERRED_FREE` below: what git and the run know decides, not the `unmerged` label `bd show` lists. A blocker whose label outlived its merge (merged by hand, or merged when `bd` couldn't remove the label, which the log warns of with `LABEL_FAILED`) has merged, and holds nothing. It isn't set aside or triaged, and doesn't count toward the [hold for the environment](#several-tickets-at-once), or toward `LIMIT` until it starts again: the run's `[n/limit]` and its done line count it once. `bd ready` leaves it out until the blocker closes, and the holds above until it merges; then it starts again from a base with the blocker's code. A blocker outside the run that never merges leaves it open and held, as [nothing to run](#nothing-to-run) says. With commits of its own (work to review), or with every blocker closed and merged already, the ticket is deferred for review as any ticket left unfinished; one waiting on a question waits for your answer instead. A ticket deferred before orchestra put such tickets back in the queue, or deferred by hand, stays deferred once its blockers merge, so each run's `START` block lists every deferred ticket in its scope with at least one blocker and every blocker closed and merged (none running, waiting on a question, or closed but not merged): `DEFERRED_FREE: <id>: its blockers have merged (<blockers>); to run it: bd update <id> --status open`. A ticket deferred until a later date (`bd defer --until`, bd's `defer_until`) was deferred on purpose, with a time to look again, and isn't listed until that time has come; once it has passed, the ticket is listed as one with no date. When its worktree (`wt/<id>`) is left with no commits beyond the base, the line goes on `; its worktree has no commits beyond <base>, safe to remove: git worktree remove <path> && git branch -d wt/<id>`. orchestra only lists them, never reopens one itself: a ticket can be deferred for other reasons. It reads them with one `bd list` and a `bd show` for each one with blockers; when `bd` can't say, the log says why and the run goes on without the list.
- **Merges queue, and every merge is checked.** A finished ticket waits for its turn. It frees its slot as it goes to merge, once its worker has settled: the next ready ticket starts while it waits for its turn and merges, or its worker resolves or fixes its branch (below). It keeps everything else a running ticket has: the tickets it blocks and the follow-ups filed from it wait for it to merge, tickets overlapping its footprint wait for it to be done, and its tab and worktree stay until the merge removes them. Up to `concurrent` tickets merge or wait to merge without a slot; beyond that, a finished ticket keeps its slot until a merge ends, so a slow merge check can't let finished tickets pile up without end. The dashboard shows them in Current all along. If other tickets merged while it ran, its branch is rebased onto the current one; either way, the merge check from `settings.json` (`check_fast`, normally `scripts/check-fast.sh`) runs on its branch before it merges, so no ticket reaches the base unchecked: a worker checks its own change, and the merge check tests everything. A branch on top of the base already, as when nothing merged while it ran, is checked as it is (`wt/<id> is on top of <base> already: checking it with '<check>' before it merges`, then `'<check>' passes on wt/<id> on top of <base>`), and a rebased one as rebased (`rebased wt/<id> onto <base>, which moved on while it ran`, then `'<check>' passes on the rebased wt/<id>`). Only a branch whose commits change nothing, taken together, merges without a check: it has nothing to merge (below). As the check runs in the queue, one ticket at a time, it adds its running time to every merge, but for the next ticket's, which is checked beside it (below). A conflict (`MERGE_CONFLICT`) or a failing check (`CHECKS_FAILED`) leaves that ticket for review, once its worker has been asked to resolve or fix it (below), and the run goes on. A worktree with uncommitted changes to files it tracks, as a check that rewrites them (a formatter, `go mod tidy`) leaves, can't be rebased: the ticket is left for review with `DIRTY_WORKTREE`, naming the files, and so is one whose rebase git refuses for another reason without stopping on conflicts (`REBASE_FAILED`, with git's error). A ticket whose worktree has another branch or a detached HEAD checked out, rather than its own, as when its worker switched, is left for review with `OFF_BRANCH`, naming what the worktree has checked out, before anything is rebased or checked. A failing check's whole output is kept in the worktree, in `.orchestra/run/check.log`, which the `CHECKS_FAILED` line names (the log has its last 40 lines). A passing check merges the ticket, and each line of its output starting with `FLAKY:`, which says a test failed and then passed on a rerun, is a warning naming the ticket: `FLAKY: <id>'s check '<check>' passed, but a test failed and then passed on a rerun: <the rest of the line>`. Tickets it blocks wait until it merges, in later runs too: it is labelled `unmerged` until then. Without a check command, tickets merge unchecked, and the log says so of a rebased one. The queue waits on the check, so it is stopped (with everything it started) after 30 minutes, or `"check_timeout"` from `settings.json` (`"5m"`, `"45m"`; `--check-timeout` or `ORCHESTRA_CHECK_TIMEOUT` for one run): the ticket is set aside with `CHECKS_FAILED: … did not finish within 5m`, and the next finished ticket merges. Set it to a few times the check's usual running time.
- **The next merge is checked while the one before it is.** The merge check holding the queue for each merge in turn would bound how many tickets an hour merge, so while a ticket holding the queue is checked, the next one waiting for its turn is rebased onto that ticket's branch as it is checked, in its own worktree, and checked there beside it, outside the queue: `checking wt/<next> ahead of its turn to merge, rebased onto wt/<id> as it is checked`, then `'<check>' passes on wt/<next> ahead of its turn, on top of wt/<id>`. When the ticket ahead merges as it was checked, the next one's branch is on top of the base exactly as it was checked, and it merges in its turn with no second check (`wt/<next> was checked ahead of its turn on top of wt/<id>, which merged as it was checked: merging it with no further check`). When it doesn't (its check failed, it went back to its worker, or the base moved another way), the next one's branch is put back as its worker left it (`wt/<next> was checked ahead of its turn on top of wt/<id>, which did not merge as it was checked: put back as its worker left it`), and rebased onto the base and checked in its turn, as any merge is; so is one whose check failed ahead of its turn (`'<check>' fails on wt/<next> ahead of its turn, on top of wt/<id> (output is in <file>); it is checked again in its turn`), its turn saying so once the ticket ahead merged (`wt/<next> was checked ahead of its turn on top of wt/<id>, which merged as it was checked, but '<check>' fails on wt/<next> on top of it (output is in <file>): put back as its worker left it`): a failure ahead of its turn says nothing of the ticket, and is neither handed back to its worker nor sets it aside. A branch that doesn't rebase cleanly onto the one ahead isn't checked ahead (`wt/<next> is not checked ahead of its turn: it does not rebase cleanly onto wt/<id>`): its turn rebases it onto the base, handing back a conflict as above if it has one. The setup runs first when a dependency file changed, as before any merge check. The ticket's box on the dashboard says, while it waits, how its check ahead goes: rebasing, checked on top of `wt/<id>`, passed or failed ([the dashboard](dashboard.md)). Each check ahead competes with the workers' for the CPU, so only the first ticket in line is checked ahead by default (`"merge_train"` in `settings.json`: how many, each on the branch of the one before it; `0` checks each in its turn alone), none is while the run holds at the machine's cap on workers (`HOLD: MACHINE`, below), and a ticket queueing again after a hand-back to its worker is checked in its turn.
- **Each worker starts with the dependencies installed.** A new worktree has nothing installed in it (no `node_modules`, no virtualenv), so with `"setup"` in `settings.json`, the command that installs the dependencies (`"npm ci"`, `"uv sync"`; see [The checks](setup.md#the-checks)), orchestra runs it in each ticket's new worktree before its worker starts there: `<id>: running 'npm ci' in its new worktree before its worker starts`. It may run as long as the check (`check_fast_timeout`). A worktree an earlier attempt left, taken up again, runs it again when the last setup there failed (`<id>: the last setup in its worktree failed; running 'npm ci' there again before its worker starts`), or didn't finish, cut short by Ctrl+C or the end of orchestra (`<id>: the last setup in its worktree didn't finish; running 'npm ci' there again before its worker starts`; a setup under way leaves `.orchestra/run/setup.started` in the worktree until one works there), or when the commits since its dependencies were last set up (in this run; else since its branch's commit before it was brought up to date with the base) change a file `"setup_files"` names (`<id>: package-lock.json changed since its dependencies were last set up; running 'npm ci' in its worktree before its worker starts`), or git can't say what they change (`<id>: git could not say what changed since its dependencies were last set up; …`), and otherwise not. A worker adopted, told its question is answered, or handed its finished ticket back has its worktree as it left it, and nothing runs for it. The worker's standing rules say so: `This worktree's dependencies are installed with 'npm ci'. Run it again only after changing a file it reads, such as a manifest or a lockfile.` A setup that fails there, or doesn't finish in time, isn't the ticket's fault, so no worker starts and the ticket isn't set aside: `SETUP_FAILED: 'npm ci' fails in <worktree> for <id>; the whole output is in <worktree>/.orchestra/run/setup.log` (`did not finish within 30m` in place of `fails`), the end of its output in the log, and a note on the ticket. The ticket stays open (reopened, if it was claimed), its worktree is kept with the output, and it is left out of the run until a ticket merges, which may bring what the setup needs, or a probe ends a [hold for the environment](#several-tickets-at-once); then it is taken again, its setup first, as taken again at once it would only fail again. A later run takes it again too. A run that ends with such tickets still waiting names them in its last line, each with its output, so that you fix the setup and run again: `READY_EMPTY after 3 tickets; SETUP_WAITS: <id> waits on the setup that failed in its worktree (the whole output is in <worktree>/.orchestra/run/setup.log); fix the setup, then run again` (`LIMIT_REACHED` and `DRAINED` too), and meanwhile the dashboard's **In queue** counts them apart from the tickets held back otherwise (`· 1 setup failed`). It doesn't count toward `LIMIT` until its worker starts, but it does count toward the hold for the environment, as a worker failing at once does, so setups failing ticket after ticket hold the run (below). The setup that works there removes the kept output. The setup is the one `settings.json` gives as the run starts, until a merge changes `"setup"` or `"setup_files"` in the base's `.orchestra/settings.json`, as the [environment setup ticket](#the-breakdown) does: the run takes them from that file as committed, for every worktree, check and full check from then on, and the log says `SETUP: <id>'s merge changed .orchestra/settings.json on <base>: the setup is 'npm ci' from now on` (`none` for a setup removed). A file it can't read or parse leaves the setup as it was, with a warning: `SETTINGS_UNREAD: <id>'s merge changed .orchestra/settings.json on <base>, but it could not be read: <why>; the setup stays 'npm ci'`; so does a merge git can't say changed the file or not: `SETTINGS_UNREAD: git could not say whether <id>'s merge changed .orchestra/settings.json on <base>: <why>; the setup stays 'npm ci', and the requirements as they were`. Other settings a merge changes count from the next run.
- **Dependencies are set up again after a rebase.** A finished ticket's worktree has the dependencies set up for the code its worker started from, and what its worker installed since (`node_modules`, a virtualenv). When a ticket that bumps a dependency merged meanwhile, the rebase brings in the new lockfile, and the check would run the rebased code against the old dependencies and fail on code the ticket never touched. So with `"setup"` in `settings.json`, the command that installs them (`"npm ci"`, `"uv sync"`, `"bundle install"`; see [The checks](setup.md#the-checks)), orchestra runs it in the worktree before the check whenever the commits since the worktree's dependencies were last set up change a file `"setup_files"` names, those the base brought in and the worker's own alike (one set up before its worker started was set up for the commit the worker started from): on a merge, on a `RECHECK` and before checking a worker's resolution of a conflict. The log says `<id>: package-lock.json changed since its dependencies were last set up; running 'npm ci' before the check`; when no such file changed, it doesn't run. It may run as long as the check (`check_fast_timeout`). A setup that fails sets the ticket aside as a failing check does, its whole output kept in the worktree's `.orchestra/run/setup.log`: `CHECKS_FAILED: <id> closed, but the setup 'npm ci', run before the check, fails on wt/<id> rebased onto <base>; … (output is in <worktree>/.orchestra/run/setup.log); checked once more if <base> moves on in this run`, and checked once more, setup first, as below. A setup that fails, or is cut short (by Ctrl+C, the end of orchestra, or the merge train stopping a check ahead of its turn), doesn't leave the dependencies as they were: they may be missing or half installed, as `npm ci` removes `node_modules` first. So the next setup due in that worktree, before a check or a worker, in this run or a later one, runs whatever changed since: `<id>: the last setup in its worktree failed; running 'npm ci' before the check` (`didn't finish` when only `.orchestra/run/setup.started`, which every setup leaves until one works there, says so). A failing setup is handed back to the worker to fix as a failing check is (below), and for a resolution, one it can't fix is a failed resolution. Without `"setup"`, nothing runs before the check; a project can put the install in the check itself instead (`npm ci && npm run check`), at the cost of an install on every check.
- **A conflict goes back to its worker first.** When the rebase stops on conflicts, the worker that did the ticket, still idle in its tab with the whole change in mind, is asked to resolve it: the rebase is left stopped in its worktree, and the worker is told which files conflict, to keep the intent of both sides and finish the rebase, to skip (`git rebase --skip`) a commit whose change `<base>` has already, to run the tests of the code it changed and of the files that conflicted once the rebase has finished until they pass, since the commits that apply cleanly can break them too, folding any fix into the last commit, to leave the whole check to orchestra, which runs it next, and to do nothing else. When the commits since its worktree's dependencies were last set up, which the rebase brings in, change a file `"setup_files"` names, or the last setup in its worktree failed or didn't finish, it is also told to run the setup (`"setup"`) once the rebase has finished and before those tests, so that they don't run on the dependencies installed for the code before the rebase. The log says `RESOLVING: wt/<id> conflicts with <base> in <files>; handed back to its worker in tab <tab>` (adding `; told to run 'npm ci' once the rebase has finished, as the rebase brings in a change to package-lock.json, which the project's setup reads` when it is told to run the setup), and the dashboard shows the ticket as `⟳ resolving`. The merge queue isn't held meanwhile: other finished tickets merge. When the worker is done, orchestra checks the result itself rather than taking its word: the rebase is finished, the worktree clean and on the ticket's branch (the check runs on what the worktree has checked out, and the merge brings in the branch), the branch on top of `<base>` with the ticket's own commits, or those of them the worker didn't skip, and no others, and the check command passes. The check runs once, on the base the ticket merges onto: when more landed on `<base>` while the worker resolved, the branch is rebased onto it first (`<id>'s worker finished the rebase, but <base> moved on meanwhile: rebasing wt/<id> onto it before checking it`), and checked as a rebased branch is (a failure there goes back to the worker to fix, below, or sets the ticket aside with `CHECKS_FAILED`); a new conflict goes back to the worker once more, twice at most. A branch the worker left with no change of its own, every commit skipped, closes with no change to merge, without the check. Then the ticket queues again and merges. If the worker doesn't finish within 20 minutes (`"resolve_timeout"` in `settings.json`), leaves the rebase unfinished or the worktree on another branch or a detached HEAD, makes a commit of its own, or the check fails and isn't fixed (below), its branch is put back as the ticket closed it (left as it is when the worktree isn't on it) and the ticket is set aside with `MERGE_CONFLICT` as before, the line and a note on the ticket saying what was tried and why it failed. The 20 minutes run on the clock, leaving out the time the machine is loaded, as a worker's tests then run several times slower: while the run holds at `--machine-workers` (`HOLD: MACHINE`), or the dashboard's load line has the memory pressure or the CPU red, or swapping under way (plain output reads no load, so there only the hold counts), up to 20 minutes more, the line that ends a hand-back then saying `after 20m (and 7m more for the machine's load)`. A worker still at it then, running its tests say, is looked at in git first: when its rebase has finished, with the branch on top of `<base>` as above, its turn is stopped (Escape) and it is told the branch is taken as it is, which is then checked and merged (`<id>'s worker was still at its hand-back after 20m, but its rebase has finished: wt/<id> is taken as it is`). Otherwise its turn is stopped and it is told, before its branch is put back, that the hand-back is over, the branch put back and the ticket set aside, naming the commit its attempt had got to, which git keeps (`<id>'s worker was stopped and told its hand-back is over`), so that it doesn't work on for a ticket set aside. Without a check command, with the worker gone from its tab or busy, conflicts aren't handed back, and the `MERGE_CONFLICT` line says why. A worker at the account's usage limit isn't passed over: the run holds for the limit, starting no new tickets, and the worker is handed the rebase once the limit resets (Escape first, as a limited worker is told to carry on), or as soon as it goes idle by itself (`<id>'s worker is at the usage limit: it is handed back once the limit lifts`). One that reaches the limit during a hand-back holds the run the same way and is told to carry on after the reset; neither wait counts toward the 20 minutes, nor does the machine's load meanwhile, and a hold that lasts `usage_limit_wait` stops the run with `USAGE_LIMIT`, the hand-back left as Ctrl+C leaves it. `"resolve_conflicts": false` in `settings.json`, or `--resolve-conflicts=false` for one run, turns it off. Ctrl+C during a hand-back leaves the rebase in progress, and the `INTERRUPTED` line says so: once the worker has finished it, run the check and merge the branch by hand.
- **A failing check goes back to its worker too.** A check that fails on the rebased branch, after a clean rebase or once the worker has resolved a conflict, often fails where the ticket's change meets what landed meanwhile: a test another ticket added for the code as it was. One that fails on a branch on top of the base already fails on what the ticket's change breaks that its worker didn't check, and goes back the same way, without a list of what landed (`FIXING: '<check>' fails on wt/<id> on top of <base>; …`; set aside, `CHECKS_FAILED: <id> closed, but '<check>' fails on wt/<id> on top of <base>; …`). The worker, idle in its tab with the change in mind, is handed the failure: where the check's whole output is and the lines of it that say what failed (as the reviewer gets them), what landed on `<base>` since its branch was cut (`git log --oneline`), and the instruction to fix the branch so the check passes, keeping the intent of both sides, running what failed and the tests of the code it changed until they pass, and commit the fix with the ticket's ID in the message, leaving the whole check to orchestra, and nothing else; or, when what failed passes without a change, the failure not coming from the branch, to commit nothing. The log says `FIXING: '<check>' fails on wt/<id> rebased onto <base>; handed back to its worker in tab <tab> to fix (1 of 2, up to 20m)`, and the dashboard shows the ticket as `⟳ fixing`. The merge queue isn't held meanwhile. When the worker is done, orchestra checks what it left rather than taking its word: no rebase in progress, the worktree clean and on the ticket's branch, the branch as the check failed on it with new commits on top, each naming the ticket, or with none; then the setup, if the fix changed a dependency file, and the check run again, once, on the base the ticket merges onto: when more landed on `<base>` while the worker fixed it, the branch is rebased onto it first (`<id>'s worker committed 1 commit, but <base> moved on meanwhile: rebasing wt/<id> onto it before checking it`; a conflict there goes back to the worker to resolve, as above). A check that passes now merges the ticket; one that fails again goes back to the worker again, twice in all by default (`"check_hand_backs"` in `settings.json`; `0` turns it off). A worker that finds nothing to fix (a test that timed out on a loaded machine, say) commits nothing: the check then runs a second time, and a pass merges the ticket (`'<check>' passes on wt/<id> on a second run; its worker committed nothing`), while a second failure sets it aside with no further hand-back, its note saying `its worker committed nothing, and '<check>' fails again (output is in <file>)` and `not handed back again: its worker found nothing to fix`. A fix it can't accept (uncommitted changes, the worktree left on another branch or a detached HEAD, rewritten commits, a commit not naming the ticket, not done within `"resolve_timeout"`) is undone, the branch reset to where the check failed when the worktree is clean and on it, and nothing more is handed back. A worker still at it when `"resolve_timeout"` is up is stopped and told, as for a conflict: a fix it has committed by then is taken as it is and checked, and without one the hand-back is over, the worker told so, and its attempt named, before the branch is reset. When the attempts run out, the ticket is set aside as before: after a clean rebase, `CHECKS_FAILED: <id> closed, but '<check>' fails on wt/<id> rebased onto <base>, after it was handed back to its worker to fix twice (see its notes)`, with a note on the ticket naming each attempt and what came of it; after a resolution, a `MERGE_CONFLICT` whose line and note say the same, the branch put back as the ticket closed it. A check that did not finish within its time limit isn't handed back, nor is anything while the run winds down or holds for a stop, or when the worker is gone from its tab or busy: the `CHECKS_FAILED` line then ends `not handed back to its worker: <why>`. A worker at the usage limit, as it is handed the failure or while it fixes it, waits the limit out as for a conflict. Ctrl+C during a hand-back leaves the worker's fix as it is, and the `INTERRUPTED` line says so: once it has committed it, run the check and merge the branch by hand.
- **A failed check is tried once more.** A check can fail on something the ticket didn't change: a flaky test, or a bug that a later ticket fixes. So a ticket set aside with `CHECKS_FAILED` stays in view for the rest of the run, and once the base has moved on (another ticket merged), it is checked once more: the log says `RECHECK: <id>'s check failed on <base> at <commit>, which has moved on since; rebasing wt/<id> and checking it once more`, its branch is rebased onto the base, and the check runs again, through the merge queue as any merge does. It starts only with a slot free, ahead of any new ticket, and frees the slot again as its merge begins, as any finished ticket does; the dashboard shows it in Current meanwhile. If the check passes, the ticket merges, its `unmerged` label removed, and the tickets it blocks start; if the rebase stops on conflicts, its worker is asked to resolve them, as above; if the check fails again, the ticket stays set aside: `CHECKS_FAILED: <id> closed, but '<check>' fails again on …`. Each ticket is checked again once at most, and none is while the run winds down or holds (see below), or while a `solo` ticket runs or is next. Asked to wind down, the run drops the tickets waiting to be checked again, saying of each `<id> is not checked again in this run, as the run winds down; it stays set aside`, and a ticket set aside after that ends its `CHECKS_FAILED` line `not checked again in this run, as it winds down`; a run that stops says the same of each as it ends, `as the run stopped`. The first `CHECKS_FAILED` line ends `checked once more if <base> moves on in this run`, or says why not when the lines of the check's output that say what failed name a package or a file in a directory the ticket's own commits change, which another ticket won't fix: `not checked again in this run, as it failed in internal/a, which <id>'s own commits change`. A ticket taken up since it was set aside is left as it is rather than rebased under whoever took it up: reopened, its worktree with uncommitted changes or its branch moved, or its worker at work again in its tab. The log then says `<id> is not checked again: <why>; it stays set aside`.
- **Some tickets run alone.** A ticket labelled `solo` (`bd label add <id> solo`), such as one splitting a file every other ticket touches, would conflict with whatever runs beside it. It starts only when no other ticket is running, and nothing new starts while it runs: free slots wait, and the log says once `waiting for solo ticket <id> to finish`. When it is next in priority while others run, nothing new starts behind it, so it isn't starved; the log says `solo ticket <id> is next`, and it starts as soon as the running ones finish. The dashboard's title line shows `solo <id> next` or `solo <id> running`. Holds and questions work as for any ticket, and one whose worker carries on in its tab after its question, adopted while others run, runs alone from then on as well: nothing new starts until it finishes. With one ticket at a time the label only has it wait for the merge before it, and the next ticket for its own, which a slot freed by a merge would otherwise take.
- **Tickets that touch the same code don't run together.** Each ticket has a **footprint**: the files and functions its title, description, design and acceptance criteria name (`internal/dispatch/merge.go:120`, `run.go`, a route of a Next.js or SvelteKit project with its brackets or `+` such as `pages/[id].tsx` or `src/routes/[slug]/+page.svelte`, `Loop.merge`, `refreshBranch()`, a camel-case name in backticks such as `waitSettled`, but not a Go keyword or builtin such as `func()` or `len(x)`, a standard package's function such as `synctest.Wait()`, a test's method such as `t.Run()`, nor a name such as `GitHub` or `iOS`, nor an extension alone such as the `.tsx` of "the `.tsx` files"), its `area:<name>` labels, and the files its `files` metadata lists (`bd update <id> --set-metadata files=a.go,b.go`, or a list: `'files=["a.go","b.go"]'`), where a folder (`internal/dispatch/`) means every file under it, those another ticket adds there included (`internal/dispatch/cart.go`), one that doesn't exist yet (`web/src/`, with its trailing slash) every file under it that another ticket names, and a glob (`*.go`, `internal/**/*_test.go`) every file it matches, those another ticket adds in a folder it matched in included (`internal/dispatch/*.go`, or `dispatch/*.go`, means a new `internal/dispatch/cart.go`, not `internal/dispatch/cart.ts`), one that matches none yet (`web/src/*.ts`) every file or folder another ticket names that it would match, from the repository's root; a part of a glob also means the name written as it is, so a route of a Next.js or SvelteKit project (`pages/[id].tsx`, `src/routes/[slug]/`) means that file or folder, and `[id]` the class matching `i` or `d` besides. A ticket's notes don't count: they say what happened to it (orchestra's notes, its workers', a reopening's), naming files and functions it doesn't change. A ticket with commits on its branch (`wt/<id>`) on top of the base, as one reopened or carried over has, has done its work there, and its text names what it read and what it was told as well: its footprint is the files its branch changes since it forked from the base, those its `files` metadata lists and its `area:<name>` labels, not what its text names, all files it is to change, the check's and a spec among them but not those git merges by union, marked `(from its branch)` in the log (`<id> footprint: test/contract/sdk.test.ts (from its branch)`); orchestra asks git once while the ticket waits, and again after each time it runs. Names are checked against `git ls-files`: a bare file name means every file of that name, `./run.go` and `internal/dispatch/run.go` alike, and a path that isn't there counts only in a folder that is (a file the ticket adds), or in any folder when the `files` metadata lists it (a project built from a spec adds whole folders), and one outside the repository (`../x.go`, `/etc/passwd`) never counts. The files the project's checks name (`check_fast` and `check_full`, such as `scripts/check.sh`), specs under `.orchestra/specs/` and the spec a ticket's `spec` metadata names (one a spec run keeps where it is in the repository, such as `docs/shop-spec.md`, left out of that ticket's footprint alone) are left out, as are predicted ones, unless the `files` metadata lists them: nearly every ticket names the check in "`scripts/check.sh` passes", and every ticket broken down from a spec cites it, without changing them. The files git merges by union (`merge=union` in `.gitattributes`, as `orchestra init` offers for `CHANGELOG.md`; orchestra asks `git check-attr` once a file a run) are left out of every footprint, even when the `files` metadata lists them, and so are workers' edits to them: two tickets' lines in one can't conflict, git keeps both. Two tickets overlap when they share an area label, a function, or a file. A ticket works on the files it names and on those the other names that mention one of its functions (orchestra reads them in the checkout), so a ticket naming `Loop.merge` overlaps one naming `loop.go`; in a file both work on, they are compared by function when both name functions it mentions, and run side by side when none is the same. A file they share keeps them apart only when one of them is to change it, as two tickets that only read a file can't conflict over it: a ticket whose `files` metadata lists files is to change those, and only reads the others its text names; one without is to change the files its text names, but a document (`.md`, `.txt` and the like) only when a sentence asks for a change near it (`Update docs/guide.md`, `Add the result to docs/guide.md`, `docs/guide.md says how`, or the document opening the sentence or a list item), not where the sentence cites it (`per CLAUDE.md`, `as docs/guide.md says`, `Spike 1 (docs/spikes/01-sdk.md, item 4) found …`), and the files mentioning one of its functions, but a document, which mentions functions without holding them. A file a running ticket's worker edited is one it changes. A running ticket's footprint also grows with every file its worker edits (Claude workers report each Edit and Write through their hooks, in `.orchestra/run/edits`, kept when a gone worker's session is resumed), compared file by file. A free slot goes to the highest-priority ready ticket that overlaps no running ticket; one that does is skipped, not waited for, and the log says once `skipping <id>: touches Loop.merge, like running <other>`. If every ready ticket overlaps, the slot stays empty until something finishes. A ticket naming nothing runs beside anything until the [predictor](organs.md#organs) has guessed its files (`<id> footprint predicted: …`), which then count like files it names, marked `(predicted)` in the log; a `solo` ticket waits for every running ticket anyway. The dispatch log shows each ticket's footprint (`<id> footprint: …`). When two running workers edit the same file, the log says once `LIKELY_CONFLICT: <a> and <b> both edit <file>`. `"footprint": false` in `settings.json` turns all of this off.
- **Planning orders tickets that touch the same code.** Keeping overlapping tickets apart at dispatch still lets them run in either order; `orchestra plan` orders them ahead of time. It reads the open tickets (leaving out questions and the `exclude_types`), computes each one's footprint (leaving out the check command's files, specs and the files git merges by union, as above; for a ticket with commits on its branch, `wt/<id>`, the files its branch changes on top of the checked-out branch since their merge base, as at dispatch, rather than what its text names), and proposes a blocks link between two that name the same function, or work on the same file of at most 200 lines (in a larger file they likely work in different places; a file a ticket adds counts as small). They work on files as at dispatch: a ticket works on the files it names and on those the other names that mention one of its functions (orchestra reads them in the checkout), so a ticket naming `Loop.merge` is ordered with one naming a small `merge.go` that mentions it; in a file both work on, they are compared by function when both name functions it mentions, and get no link when none is the same. A file neither of them is to change, as above, links nothing. A function one of them names in passing, which the file doesn't mention, doesn't keep them apart. The higher-priority ticket goes first, then the older one; of two filed in the same second (bd's `created_at` counts whole seconds), the lower subticket number, `e.2` before `e.10`. Area labels and predicted files alone link nothing, and tickets already ordered by blocks links, directly or through others, are left alone; tickets touching one function form a chain rather than each waiting for every other. It prints each link (`k-2 (P3) waits for k-1 (P1): both touch Loop.merge`) and changes nothing; `orchestra plan --apply` adds them with `bd dep add`. Ctrl+C stops it between two links, saying which it added and which not, exit code 130. Run it after filing a batch of tickets, before a run: `bd ready` then holds each second ticket until the first closes, and `orchestra` until it merges.
- **One git writer at a time.** Worktree creation, rebases, merges and cleanup in the main repository take a lock, so workers don't trip over git's lock files.
- **A failing machine holds the run.** Sometimes the environment fails every worker the same way, whichever ticket it has: a safety classifier that is down refuses every command, say, and each worker gives up at once. Setting each ticket aside in turn would burn through the queue, so the run holds for the environment instead when 2 tickets in a row either had workers that went idle for good within 2 minutes of dispatch without claiming the ticket, committing or leaving changes, or had the setup fail in their worktrees before their workers could start (`SETUP_FAILED`, above), or were blamed on the environment with high confidence by [triage](organs.md#organs). The log says once `ENVIRONMENT: the last 2 tickets (<a>, <b>) each settled within 2m of starting without being claimed or changed; check the machine, then restart`, or `ENVIRONMENT: the setup 'npm ci' failed in the worktrees of the last 2 tickets (<a>, <b>); …`, or for a row of both, `ENVIRONMENT: the last 2 tickets (<a>, <b>) each failed at once: the setup 'npm ci' failed in their worktree, or their worker settled within 2m of starting without being claimed or changed; …`: no new tickets start, the running ones finish, and the run ends with exit code 7. Tickets whose setup failed are back in the queue already. Tickets whose workers failed at once did nothing, so they are reopened rather than left deferred, with their notes kept (`<id> reopened: …` in the log, a `reopened` event in the event stream), and no longer count as set aside; tickets triage blamed, whose workers had started on them, stay deferred with the verdict in their notes. One such failure alone changes nothing. Once the running tickets finish, the run probes the machine: the log says `PROBE: the run holds for the environment; in 10m one worker without a ticket runs a command, …`, and 10 minutes later one worker is started in the main checkout, in a tab of its own, and asked to run a single command; a Claude worker starts with `--strict-mcp-config`, without MCP servers, as it needs none. If it does, the machine works again: its tab is closed, the log says `PROBE_OK: …; taking tickets again`, and the run goes on with the reopened tickets and those whose setup failed. If it doesn't within 5 minutes, or stops without running it, the run ends as it would have (`Stopped: ENVIRONMENT`, notified), the `ENVIRONMENT` line adding how the probe failed, and the probe's tab is left open to read. The machine is probed once per run, so a second hold ends it. Press Ctrl+C to end the run during the wait. `"environment_hold": {"count": 3, "window": "90s", "probe": "30m"}` in `settings.json` changes the thresholds and the wait, `{"probe": "0"}` turns the probe off, and `{"count": 0}` turns the hold off.
- **Stopping drains.** Something that stops the run (`PAUSED`, `BLOCKED`, a tool failure) is logged as `HOLD`. No new tickets start, the running ones finish and merge, and then the run ends with that reason. With one ticket at a time, nothing changes. Ctrl+C still stops at once. A worker left running when the run ends (the one that stopped it, or any at Ctrl+C) may still close its ticket after orchestra has gone: the next run carries it over and merges it then (see below). Its ticket is labelled `unmerged` too (`<id> is left running in tab <tab> and labelled 'unmerged'`), so the tickets it blocks wait in later runs until it merges, even if the next run can't carry it over. To wind a run down yourself, press **s** in the dashboard (or send SIGUSR1): see [What you see](dashboard.md#what-you-see).
- **The next run carries on with the workers a run leaves.** As a run ends, however it ends (done, a stop, Ctrl+C, winding down), it writes the workers it leaves in their tabs to `.orchestra/run/state.json` in the main checkout, while it still holds its lock: those on tickets waiting on a question, and those it left running, with what stopped it (`PAUSED`, `BLOCKED`, `TICKET_LIMIT`, `INTERRUPTED`, …); the log says `left for the next run: <id> (asked <question>), <id> (left running: PAUSED)`. The next run reads the file in its `START` block, `carried over from the last run: …`, and takes each up as it does a ticket asked in the run itself: a ticket closed meanwhile is adopted and merged (rebased and checked if the base moved on, its `unmerged` label removed), and the tickets it blocks start once it has; one whose worker is at work on it again is adopted and watched, rather than stopping the run with `AGENT_BUSY`; one whose question was answered comes back through `bd ready` to its earlier worker, told the answer is in (or, gone from its tab, its session resumed), rather than to a new one that starts over. One still waiting on its question, or left running with its worker idle (waiting for you, as when the run stopped), is left as it is and saved again. One deferred meanwhile shows as deferred. Each is checked first: one whose worktree is gone, or whose ticket is closed with its branch on the base already (merged by hand, with a commit of its own naming the ticket: one since its branch was cut from the base, which the file notes for each worker), is dropped, as the log says; one whose ticket was deleted from `bd` since is dropped too (`<id>, carried over from the last run, is dropped: bd has no such ticket`); one it can't check, as `bd` can't show its ticket (after three tries) or `git` can't list the worktrees, isn't taken for gone: it is kept for the next run and saved again as it was, as the log says (`<id>, carried over from the last run, is kept for the next run: bd can't show it: …`); one in progress whose worker has gone from its tab has the worker's session resumed in a new tab ([`RESUMED`](workers.md#worker-prompt)), or, without a session to resume, is warned about once (`WORKER_GONE: <id> is in progress after …, but its worker is gone from tab <tab> (worktree <path>)`), noted on the ticket and dropped, and the run goes on. In Herdr, a worker the last run launched just before Ctrl+C, which Herdr hadn't yet seen to give it the name orchestra knows it by, comes up unnamed: the next run, finding no worker under that name, looks in the pane it was started in, which the file holds too, and names the worker there (`<id>'s worker was without its name in tab <tab>; named it <name> again`), but only while Herdr still has the tab labelled with the ticket's ID, for the reason below. Merging a carried-over ticket closes its worker's tab only while the terminal still has the tab labelled with the ticket's ID (in tmux, the window named with it): Herdr numbers its tabs afresh when it starts without restoring its last session, and tmux its windows when its server starts again, so after such a restart the tab ID the last run recorded may be another tab, yours included. Then the `closed` line ends `worktree and branch removed; tab <tab> left open: the terminal has it labelled '<label>' now, …`, or `its tab <tab> was closed already` if there is no such tab; this holds for any merged ticket. A run scoped with `--ticket` keeps the workers on other tickets for a later run. Ctrl+C while the run is still reading the last run's state (in its `START` block) ends it `INTERRUPTED` at once and leaves the file as it was, so the next run carries every worker over; a check cut short drops none. A file that can't be read carries nothing over, and the log says why. An asked ticket its worker closed before the run could merge it (`ASKED_UNMERGED`, or `LEFT_UNMERGED` for one the last run left running) is carried over and merged by the next run, as one closed between runs is; a ticket left for review (`MERGE_CONFLICT`, `CHECKS_FAILED`, …) isn't carried over, nor one whose rebase Ctrl+C left in progress during a hand-back; the `unmerged` labels still hold what they block. A quit at once (a second Ctrl+C) saves the workers as the run would have as it ended, but for one that comes while the run still reads the last run's state, which leaves the file as it was.

What `orchestra` can't make safe for you:

- **Checks that collide.** Every worker runs the project's checks. Tests that share one named simulator, a port or a database can fail when two run at once.
- **Files every ticket touches.** If most tickets add to the same spot, like a CHANGELOG's `[Unreleased]` list, the end of a test file or the end of a struct, rebases conflict: each side only added lines, but git can't order them. The worker prompt asks workers to put new tests in a new file named after the feature and new fields and helpers next to the code they belong to. For the changelog, `orchestra init` offers a `.gitattributes` line, `CHANGELOG.md merge=union`, which keeps both sides' lines; a line both sides add identically (a `### Fixed` heading, say) is kept once. The same works for other list-like files.

Start at 1, and raise it once the checks run cleanly side by side.

## Runs that share a machine

Runs in different repositories can go at once on one machine, each with its own workers, and their checks slow each other down: a check that takes 97 seconds alone took 166 beside one other and 317 beside three, and a test suite with a time limit per test (bun's 5 seconds) can fail for it. So each run registers itself while it runs, a small file in `runs/` in orchestra's folder in your cache folder (`~/Library/Caches/orchestra/runs` on macOS, `$XDG_CACHE_HOME/orchestra/runs` or `~/.cache/orchestra/runs` on Linux; `ORCHESTRA_RUNS_DIR` names another, `ORCHESTRA_RUNS_DIR=off` none), with its PID, repository, `concurrent`, when it started and how many of its workers are running, and removes it as it ends. A file whose process is gone, a run killed or quit at once, is ignored and removed, and so is one whose PID a process started since has taken (as after a reboot): a run compares the file's start time with the process's. A folder that can't be read counts no other run, and one removed under the runs, by a cache cleaner say, is made again as each next writes its file.

A run that starts beside another, or sees one start (it looks as it polls, every 30 seconds), says so once for each, `SHARED_MACHINE: another orchestra run is going in <repository> with <n> workers; their checks slow each other down`, and once it has ended, `  the other orchestra run in <repository> has ended`. The dashboard's title line says `· shared with 1 run` (or `2 runs`) meanwhile.

Each Claude worker starts with its share of the machine's cores in its environment: the cores divided among the run's `concurrent` workers and those running in the other runs as it last looked (no more workers than `--machine-workers`, half the cores by default), at least one. `ORCHESTRA_CORES` gives it, for a project's check scripts to keep to (a test runner's workers, a linter's jobs), and `GOFLAGS` gets `-p=<share>` after the flags it has, unless those set `-p` already, so that `go test ./...` runs no more packages at once than that; the rules' note on checks tells the worker so. Left alone, Go runs as many packages at once as there are cores, each with as many threads, so four workers' checks on ten cores pushed the load past 30 and timed tests out in code no ticket touched. The share is taken as the worker starts and kept: one started before another run began keeps its larger share. It goes in the worker's settings (`hooks.json`), so a worker without its hooks gets none. The same settings set Claude Code's `BASH_DEFAULT_TIMEOUT_MS` to the merge check's limit (`check_fast_timeout`, 30 minutes when unset), and `BASH_MAX_TIMEOUT_MS` to that or 10 minutes, whichever is longer: Bash then waits on a check in the foreground as long as the merge check may take without the worker passing a timeout, and so does the verifier, a subagent in the worker's process. Bash otherwise waits 2 minutes, then moves the command to the background, where the worker looks idle while it waits.

`--machine-workers N` (or `ORCHESTRA_MACHINE_WORKERS=N`) caps the workers running across the machine's runs, this one's included: by default at half the machine's cores, at least 2 (5 on 10 cores), as workers mostly wait on the model but their checks are CPU-heavy, and runs slowed sharply past about 4 checks at once on 10 cores; `0` for no cap. To change it, set it in your shell's profile, as it is about the machine rather than a project, and every run you start keeps to it. The START line says the cap and what gave it, `machine workers: 5 (default: half of 10 cores)` (or `--machine-workers`, `ORCHESTRA_MACHINE_WORKERS`, `none` for no cap), and a run whose own `concurrent` is above the cap says so once under it: it is held at the cap as below. A worker counts while it takes a slot of its run's `concurrent`: from its dispatch until its worker settles and its ticket goes to merge, which frees its slot ([several tickets at once](#several-tickets-at-once)), so a ticket waiting for its turn, merging, or handed back to its worker to resolve or fix its branch doesn't count, unless more than `concurrent` of them wait at once. With a slot free and a ticket ready, a run at the cap starts nothing: it says once `HOLD: MACHINE: the machine's orchestra runs have <n> workers running, <m> of them this run's, at the cap of <N> (ORCHESTRA_MACHINE_WORKERS); the next ticket starts once one of them finishes`, and its title line says `· machine full`. It starts the ticket once one of them finishes, in either run, within 2 seconds, as it looks every 2 seconds while it holds; a run that has stopped taking tickets meanwhile (winding down, at its ticket limit or the usage limit) clears `· machine full` as it next looks (within 30 seconds). A run never holds with no ticket of its own at work or waiting to merge, so a run started beside another at the cap still gets one worker going, and each run keeps to its own `concurrent` too. Two runs that look at the same moment can both start a ticket, going one over the cap until one finishes. Without the cap (`0`), nothing waits for the other runs. A run with a cap counts the workers of every registered run, whether or not those have a cap of their own.

## Tickets set aside

A ticket whose worker settles without closing it is set aside: deferred, with a note saying why, and handed to [triage](organs.md#organs). Its worker deferred it (`<id> deferred by worker`), left it open or in progress (`<id> still open -> noted and deferred`), or never started on its prompt (`PROMPT_FAILED`); a worker that stopped because a blocker hasn't merged has its ticket go back in the queue instead (`WAITS_FOR_MERGE`, [above](#several-tickets-at-once)). What becomes of the worker depends on what it left:

- **Nothing done**: no commits beyond the base and a clean worktree. Nothing there is left to review, so once triage has gathered its evidence the worker's worktree, branch and tab are removed, as the line says: `<id> deferred by worker; nothing done, so its worktree, branch and tab are removed` (`<id> still open -> noted and deferred; nothing done, …`).
- **Work of its own**, commits or uncommitted changes, or a prompt it never took: the worker is left in its tab, with its worktree, for you to review (`…; worktree <path> and tab <tab> left open`). So is one that deferred its ticket in its tab while it waited on your answer to a question.

A worker left in its tab may carry on there and close its ticket: Claude Code continues a worker by itself once the account's [usage limit](#the-usage-limit) resets, say, or you answer it in its tab. `bd` would then count the ticket done though nothing merged it, so the run follows it:

- **Its ticket is read at each poll**, with one `bd list` for all such tickets. Once `bd` shows it closed and its worker has settled (idle or done, or gone from its tab; never while it works), the run merges it, whatever the free slots: `LATE_CLOSE: <id> was closed in tab <tab> after it was set aside; merging it now`. It is rebased, checked and merged as any closed ticket ([Several tickets at once](#several-tickets-at-once)), its worktree, branch and tab removed, and no longer counts as set aside; a conflict or a failing check leaves it for review as usual (`MERGE_CONFLICT`, `CHECKS_FAILED`, …).
- **What waits on it waits**, closed or not: the tickets it blocks, and the follow-ups filed from it, are held until it merges (`<dep> waits: <id> closed but not merged (its worker was left in tab <tab>)`).
- **It is labelled `unmerged`** as it is first left, its fork noted (`unmerged_fork`), as a ticket left running is ([After a run stops](#after-a-run-stops)). The label holds nothing while the ticket isn't closed. A ticket closed once the run has ended, or once something stopped it (a stopped run follows its left workers no more), isn't merged by any run: the tickets it blocks wait, in later runs too, until `wt/<id>` is merged into the base by hand, and the next run then removes the label. The run doesn't wait for these workers before it ends.
- **It is no longer followed** once it merges, once its worker is gone from its tab with the ticket not closed, once `bd` no longer has the ticket, or when the ticket is dispatched again.

A ticket closed but not merged, set aside in this run (`CHECKS_FAILED`, `MERGE_CONFLICT`, …) or left `unmerged` by an earlier one, may be merged by hand while the run goes on. Each time the base moves on, the run asks git of each such ticket's branch, as it does of an earlier run's as it starts ([After a run stops](#after-a-run-stops)): one on the base now is taken as merged, `<id>, set aside in this run, is on <base> now (<commit>): merged by hand, so no longer set aside; its 'unmerged' label is removed`. It counts among the tickets the run closed, not those it set aside, in the end line and for the reviewer, the tickets it blocks start, and it isn't checked again. Its worktree, branch and tab are left as they are.

A ticket set aside and reopened (`bd update <id> --status open`) is dispatched again to a new worker in the same worktree, told what the earlier attempt left on its branch ([Worker prompt](workers.md#worker-prompt)). The earlier worker, idle or done in its tab, has that tab closed rather than kept beside the new one, and the log says where its session's transcript is: `<id>'s earlier worker was idle in tab <tab>; its tab is closed, as the new worker takes up its worktree; its session's transcript is <path>`. The tab is closed only while the terminal has it labelled with the ticket's ID, as a merged ticket's is; one whose tab the run doesn't know, or that it can't close, is renamed instead, for the new worker to have its name, and its tab left open. An earlier worker at work in its tab stops the run (`AGENT_BUSY`) rather than have a second worker start beside it. One waiting on the account's [usage limit](#the-usage-limit) there is adopted instead, found under the ticket's name when the run has no record of it (`<id>'s earlier worker is still limited in tab <tab>; adopting it rather than starting another`): the run holds for the limit and tells it to carry on after the reset, as it does its own limited workers, where a second worker would start beside one that Claude Code may continue by itself.

## The usage limit

On a subscription, a long run of several workers reaches the account's usage limit, its five-hour session limit or its weekly one, which all the workers share: Claude Code refuses every request until it resets, whichever worker makes it. A worker whose turn ends on it is `limited` ([the hooks](workers.md#worker-prompt) say so, with when it resets), and the run holds for it rather than end, logging once per hold `USAGE_LIMIT: <id>'s worker reached the usage limit; it resets at 14:05. No new tickets start until then, for up to 6h`, or, when Claude Code doesn't say when, `…; when it resets is not known. No new tickets start, and one limited worker is told to carry on every 15m, for up to 6h`.

- **Claude Code may let a turn run a little past the limit**, telling the worker so ("a short grace allowance remains"): the worker wraps up and ends its turn normally, and Claude Code says it will continue by itself once the limit resets. That worker is `limited` too, its transcript saying so (`Usage limit reached · continuing automatically at 5:30am`), with when it resets. One that closed its ticket first is done with it, and merges as usual. One that deferred its ticket as it stopped has it brought back in progress, with a note, for it to carry on after the reset (`<id>'s worker deferred its ticket as it stopped at the usage limit; brought back in progress, for it to carry on after the reset`). The workers' standing rules say to commit what they have and stop at the limit, without deferring or closing the ticket for it.
- **No new ticket starts**, as its worker would only reach the limit too; the workers not limited go on. A limited worker isn't told to continue into the limit or settled, doesn't count toward the [hold for the environment](#several-tickets-at-once) or `PAUSED`'s idle grace, and the time it waits doesn't count toward its [ticket limit](#run). A worker handed its finished ticket back, to resolve conflicts or fix a failing check, waits the same way ([Several tickets at once](#several-tickets-at-once)).
- **A minute after the reset** (Claude Code gives it to the minute), each worker still limited is sent Escape, which dismisses Claude Code's own question about the limit or cancels its automatic continue, and told to carry on with its ticket (`<id>'s worker was told to carry on after the usage limit`), and tickets start again; a worker Claude Code has already continued by itself is at work, and is neither sent Escape nor told again: `USAGE_LIMIT lifted: the limit reset at 14:05; telling the workers still limited to carry on, and taking tickets again`.
- **With the reset unknown**, one limited worker is told to carry on every 15 minutes, to try the limit (`  USAGE_LIMIT: telling <id>'s worker to carry on, to see whether the limit has lifted`, then, refused again, `  USAGE_LIMIT: <id>'s worker reached the usage limit again; the next try is at 14:20`). A worker that goes on past the limit for a minute, or settles once it went on, shows that it has lifted: `USAGE_LIMIT lifted: <id>'s worker went on past the limit; telling the workers still limited to carry on, and taking tickets again`.
- **With nothing running**, the limited workers gone from their tabs say, the run waits for the reset itself; Ctrl+C, or winding the run down (**s** in the dashboard, or SIGUSR1), ends the wait. A worker whose limit has reset already, as one carried over from the last run may find, is told to carry on at once, without a hold. A limit reached again after a hold lifts starts another hold, which never acts sooner than 15 minutes after the last one lifted.
- **The wait has an end.** `"usage_limit_wait"` in `settings.json` (default `"6h"`; `"0"` doesn't wait at all) is how long a hold may last. Past it, the run stops with exit code 8, `USAGE_LIMIT: <id>'s worker reached the usage limit (it resets at Tue Oct 20 14:05), still waiting after 6h; stopping, with its tab <tab> and worktree <path> left as they are` (or `USAGE_LIMIT: the run held for the usage limit for 6h (…), with nothing running; stopping`), the worker noted on its ticket and left for the next run, which carries it over and tells it to carry on once its limit has reset. A reset on another day than today is given with its day.

The dashboard's title line says `usage limit · resets 14:05` (or `usage limit`), in yellow, while the run holds; a notification says `Usage limit reached · resets 14:05` (or `· the run waits`) once per hold, and `Stopped: USAGE_LIMIT on <id>` should the run stop for it. The [event stream](events.md) records `usage_limit` and `usage_limit_lifted`. The organs skip a call the limit refuses, rather than fail, and one refused during the run starts the hold when the run has none, as the workers share the account (`USAGE_LIMIT: triage of <id> was refused for the usage limit; it resets at 14:05. …`): `  triage of <id> skipped: claude is at the account's usage limit (…)`, `  <id> footprint not predicted: skipped, as claude is at the account's usage limit (…)`, `REVIEW_SKIPPED: claude is at the account's usage limit (…)`; the environment probe's worker fails with `it reached the account's usage limit without running its command`.

## The full check

A run that ends by itself (`READY_EMPTY`, `LIMIT_REACHED` or `DRAINED`) having merged at least one ticket runs the project's full check once, after its last merge and before triage finishes and the run report: `check_full` from `settings.json`, normally `scripts/check-full.sh`, which runs `scripts/check-fast.sh` and then the suites too slow or too demanding to run on every merge ([The checks](setup.md#the-checks)). It doesn't run after a stop or a hold, after Ctrl+C, after a run that merged nothing, or without `check_full` (a project set up before it had one: `orchestra init` adds it).

It runs on the head of the branch the run merged into, in a worktree of its own, `<WT_ROOT>/check-full-<random>`, on no branch, which is removed afterwards with whatever the check left in it: the main checkout stays as it is. It may run for 60 minutes, or `check_full_timeout` from `settings.json` (`--check-full-timeout` or `ORCHESTRA_CHECK_FULL_TIMEOUT` for one run), and is then stopped with everything it started. Nothing is installed in that new worktree, so with `"setup"` in `settings.json` (such as `"npm ci"`; see [The checks](setup.md#the-checks)), or as a merge in the run [set it](#several-tickets-at-once), orchestra runs it there first, always, within the same time limit. The log says `FULL_CHECK: running '<check>' on <base> at <commit> in <worktree> (time limit 60m)`, or `running '<setup>', then '<check>', on …` with a setup; on a terminal a line spins meanwhile, `Running the full check… (Ctrl+C skips)`. Ctrl+C stops it (`FULL_CHECK_SKIPPED`) and skips triage and the run report, as it does during them.

- **Passing**: `FULL_CHECK passed: '<check>' on <base> at <commit> (12m3s)`. Each `FLAKY:` line of its output is a warning, as for the merge check.
- **Failing**: `FULL_CHECK_FAILED: '<check>' fails on <base> at <commit>, in the suite <suite>; the whole output is in <repo>/.orchestra/run/check-full.log; filed <id>`, with a notification, `Full check failed · <suite>`. One that runs out of time says `did not finish within 60m` instead of `fails`. The suite is the one its output names last: the runners print `SUITE: <name>` as each suite starts (its name, or else its command), and a check of your own can print the same; without such a line, the suite is the check itself. The whole output is kept in the main checkout's `.orchestra/run/check-full.log` until the next full check fails; the log has its last 40 lines, and so does the run report, after the reviewer's text (the reviewer is told how the full check went, too). orchestra files a P2 bug titled `Full check fails: <suite>` and labelled `check-full`, with the lines of the output that say what failed, for a worker to fix in a later run. While a ticket with that title and label is open, the next failure in the same suite files no other: it is noted on that ticket, and the line ends `<id> is open for it already`.
- **Failing in the setup**: `FULL_CHECK_FAILED: the setup '<setup>', run before '<check>', fails on <base> at <commit>; the whole output is in <repo>/.orchestra/run/check-full.log; no ticket filed: it is not a suite's failure`, with a notification, `Full check failed · setup`. The check doesn't run; the output is kept, and its end goes to the log, the reviewer and the report, as for a failing check, but no ticket is filed: a setup fails for want of a network or a registry as often as for the code.

The [event stream](events.md) records it as a `full_check` record.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | nothing left in `bd ready`, the limit was reached, or it stopped after the running tickets as asked (`DRAINED`); also a run with [nothing to run](#nothing-to-run) from the start (`✓ All done` or `Nothing ready to run`); with `--ticket`, the last line says whether the ticket's scope is finished (`SCOPE_DONE` or `SCOPE_OPEN`); with a feature (`--feature` or **New feature**), also a session that filed none; with `--spec`, also a spec that is built (`✓ <path> is built`), or a refinement that filed nothing |
| 2 | setup problem found before starting (all problems are listed), or another run going in the same repository; an [overnight](#overnight) run's failed pre-flight check left; a [requirement](setup.md#the-machines-requirements) still missing before the first ticket, or after a merge changed the list (`REQUIREMENTS_MISSING`); with a feature (`--feature` or **New feature**), also no `claude` to talk it through with, no terminal to talk it through on, or an epic handed back that orchestra won't run; with `--spec`, also a breakdown that failed, ran out of time or named no root epic it could run, a refinement left with tickets filed, `--refine` with no terminal, or the setup of a repository `init` hadn't set up failing other than in bd or git; with a spec chosen at the start, one git ignores |
| 3 | a worker stayed blocked for more than 4 minutes or unknown for more than 5, went idle with its ticket still `in_progress`, or was still going after the ticket limit; an [overnight](#overnight) run sets such a ticket aside instead, and goes on |
| 4 | a terminal (Herdr, tmux or cmux), Beads or git failure, or orchestra panicked while working on a ticket (`PANIC`); with `--spec`, also git failing to commit the spec, or bd failing to list its issues or to set the repository up |
| 5 | uncommitted changes in the main checkout, or it left the branch it started on |
| 6 | a finished ticket's branch does not fast-forward (it should have been rebased first) |
| 7 | workers kept failing at once, or the setup in their new worktrees, whichever ticket they had: the environment, not the tickets (`ENVIRONMENT`) |
| 8 | the account's [usage limit](#the-usage-limit) held the run longer than `usage_limit_wait` (`USAGE_LIMIT`); the limited workers keep their tabs and worktrees, for the next run to carry on with |
| 130 | stopped with Ctrl+C, SIGTERM or SIGHUP, or quit at once by a second one while the stopped run wound down (`INTERRUPTED: quit at once …`); the running workers keep their tabs and worktrees |

## After a run stops

After an 8, there is nothing to do but run again, once the limit has reset or before: the next run carries the limited workers over, tells each to carry on once its limit has reset, and holds for the limit again if it hasn't. A spec run's next night does this by itself.

After a 3, answer the worker in its tab, then resume with `DONE_SO_FAR=<n>`: the next run carries over the workers this one left running (see [Several tickets at once](#several-tickets-at-once)), so it merges a ticket the worker closed meanwhile, and adopts a worker still at work on its ticket. A ticket whose worker was left running (after a 3, 4 or 130, say) is also labelled `unmerged`: the tickets it blocks wait until its branch (`wt/<id>`) is merged, by the next run or by hand, and the next run removes the label once the branch is on the base with a commit naming the ticket that it made since it was cut, or once the base holds the branch's changes, squash-merged by hand, and a commit on it that the branch doesn't have names the ticket: orchestra notes where it was cut (the merge-base) in the ticket's metadata, `unmerged_fork`, as it labels it, so that an older commit naming the ticket, or a branch with no commits of its own, doesn't count. A quit at once labels nothing, though it saves the workers for the next run: label each ticket it names yourself (`bd label add <id> unmerged`), merge one its worker closes by hand, and run `git status` before the next run if it abandoned a merge.
