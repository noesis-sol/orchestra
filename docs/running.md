# Running

Starting a run and its options, several tickets at once, and what happens when a run stops. Back to the [README](../README.md).

## Run

From the main checkout (not a worktree), in a Herdr pane or, with tmux installed, any terminal, on the branch finished tickets should land on:

```
git switch -c batch/$(date +%F)
orchestra
```

`orchestra` checks its setup first and lists every problem at once, with exit code 2. In a repository [`orchestra init`](setup.md#set-up-a-project) hasn't set up (no `.orchestra/worker-prompt.md` or `.orchestra/settings.json`, nor a `.claude/worker-prompt.md` from before `init`), it says so first, `orchestra isn't set up in this repository yet. Run this first: orchestra init`, rather than list the worker prompt and Beads database `init` provides; problems `init` doesn't fix, such as a detached HEAD or no terminal for the workers, follow under `Also fix before a run:`. `orchestra --feature …` stops the same way before screening. A project with settings but no worker prompt is told `Worker prompt not found: .orchestra/worker-prompt.md. Recreate it with: orchestra init`.

One run at a time works on a repository: a second would race the first for the same tickets, worktrees and branch. Once its startup checks pass, a run holds a lock, `orchestra.lock` in the repository's git directory (`.git/orchestra.lock` in the main checkout; `git rev-parse --git-common-dir` names that directory from any worktree), until it exits after the run report. Nothing that empties `.orchestra/run/`, such as `git clean -fdX` or `-fdx`, removes it: `git clean` never touches the git directory. A second run in the same repository stops before changing anything, and a `--feature` request before it is screened, with exit code 2: `orchestra is already running in <repo> (pid 44497, since 08:31, main, pane w2B:p60)`. The lock is an `flock`, which the system releases when orchestra exits however it exits, `kill -9` included, so there is never a stale lock to remove. The file says which run holds it, or held it last: its PID, start time, version, branch, `ticket` or `feature` (a feature described at the question too, once it is typed) and `pane`, the Herdr or tmux pane, or cmux terminal, it runs in (`HERDR_PANE_ID`, `TMUX_PANE`, `CMUX_SURFACE_ID`; empty when it runs in none). `lsof .git/orchestra.lock` shows whether a run holds it. Runs in different repositories don't block each other. `orchestra init` holds the lock too while it changes the project, writing `"init": true` and its PID alone, so a run started meanwhile is refused (`orchestra is already running in <repo> (orchestra init, pid 44497)`). `orchestra plan --apply` warns when a run is going: a ticket the run has started keeps going whatever it now waits for.

In a terminal (its input and output both), `orchestra` then asks what the run should work on, once the startup checks have passed and it holds the lock, so that an answer is never followed by `orchestra cannot start`:

- **Current tickets**, selected to start with, runs the backlog as this page describes. The option says what there is to run: `Current tickets: N ready`, N what the run's own `bd ready` query finds (`0 ready` when the last run left workers to carry on with); with [nothing to run](#nothing-to-run), none ready (or every ready ticket held back) and none carried over, `Current tickets: none, all done` or `Current tickets: none ready (N open)`, N the tickets not closed, leaving out the `exclude_types`. It says only `Current tickets` when `bd` can't say. Picked with nothing to run, it shows why, as [below](#nothing-to-run).
- **New feature** opens a field for the feature's description. Alt+Enter or Ctrl+J starts a new line, and Enter goes on; an empty description isn't taken. orchestra prints the description, then opens Claude Code in a pane to the right of its own to [talk it through](#talked-through) with you and file its tickets.

Esc or Ctrl+C at the question (Ctrl+D, the end of input, with `TERM=dumb`, where it asks with plain lines) exits with code 130, with nothing changed and no run recorded in `.orchestra/run/events.jsonl`. `--tickets` (or `ORCHESTRA_TICKETS=1`) skips the question and runs the current tickets; `--ticket`, `--feature` and `-plain` skip it too, and a run without a terminal, or with `DONE_SO_FAR` at `LIMIT`, never asks. Scripts and agents that start `orchestra` in a terminal, such as a Herdr pane or a tmux window, pass `--tickets`, or `--feature` or `--ticket`: the bare command would wait at the question.

### Herdr, tmux or cmux

Workers run in [Herdr](https://herdr.dev) tabs, [tmux](https://github.com/tmux/tmux) windows or [cmux](https://cmux.com) workspaces. `--terminal herdr`, `--terminal tmux`, `--terminal cmux` or `--terminal auto` (or `ORCHESTRA_TERMINAL`) chooses for a run, over `"terminal"` in `settings.json`, which chooses for the project; without either it is `auto`: the terminal `orchestra` runs in, the innermost first (Herdr in a Herdr pane, `HERDR_ENV=1`; tmux in tmux, `$TMUX`; cmux in a cmux terminal, `CMUX_WORKSPACE_ID`), else tmux when `tmux` is on the `PATH`. A terminal started from a pane of another copies that one's variables into its own panes, as tmux started from a Herdr pane has `HERDR_ENV=1` and `HERDR_PANE_ID` in its panes, even once that pane is closed: with Herdr's variables beside `$TMUX` or `CMUX_WORKSPACE_ID`, orchestra picks Herdr only when Herdr says `HERDR_PANE_ID` is the pane it runs in (orchestra's process group is the one in that pane's foreground, `herdr pane process-info`), and else tmux, or cmux. With none of these, the run doesn't start: `No terminal for the workers: run orchestra from a Herdr pane or a cmux terminal, or install tmux (brew install tmux, apt install tmux) to run it anywhere.` A choice of Herdr outside a Herdr pane, of tmux without `tmux` installed, or of cmux outside a cmux terminal, is a setup problem that says so. The `START` line names the choice, `terminal: Herdr, workspace: w2B`, `terminal: tmux, session: orchestra-kinieta` or `terminal: cmux, workspaces: one per ticket`.

- **Herdr.** Each worker gets a tab in the Herdr workspace `orchestra` runs in, or in the one `--workspace ID` names (`herdr workspace list` lists them). Herdr reads from each worker's screen whether it is idle, working or blocked, for any agent kind it can start (`--agent`).
- **tmux.** Each worker gets a window named with its ticket's ID, which keeps that name whatever Claude Code writes to its title (tmux 3.7, which refuses `.` and `:` in a window name, gets them as `_`, so a child ticket's window there is named `proj-abc_1`); notes and logs give its window and pane by tmux's IDs (`@3`, `%7`). Run inside tmux, `orchestra` opens the windows in its own session, beside its own window, and the dashboard's number keys go to them. Run outside tmux, it opens them in a detached session, `orchestra-<repository folder>` (with `.` and `:` made `_`, which tmux before 3.8 doesn't keep in a session name), starting the session, and the tmux server if none runs, when it opens the first window. `--workspace <session>` names another session, made the same way if tmux has none; tmux before 3.8 names one asked for with `.` or `:` with `_` in their place (3.2 to 3.6), or refuses the name (3.0, 3.1 and 3.7), and orchestra then uses the session so named. A `:` in `--workspace` is made `_` on every tmux, 3.8 included, since tmux reads `foo:bar` as session `foo`, window `bar`, and couldn't be told to attach to a session so named; only the session `orchestra` runs in keeps a `:`. A session's name may hold `.` or `#`, whether orchestra makes the session or runs in it; one with `.` is attached to as `tmux attach -t foo.bar:`, since tmux reads `foo.bar` as window `foo`, pane `bar`. When the windows aren't in the session `orchestra` runs in, the `START` block says how to see them, `to see the workers' tabs: tmux attach -t orchestra-kinieta` (`tmux switch-client -t …` from inside tmux), the dashboard says it above its hint, and a run that leaves workers in their windows says it again as it ends. A worker's window stays open when Claude Code exits, its screen there to read, until orchestra closes it.
- **cmux.** Each worker gets a workspace of its own in orchestra's window, named with its ticket's ID, which the sidebar lists with its branch; start `orchestra` from a cmux terminal. See [Workers in cmux](#workers-in-cmux).
- **Workers in tmux and cmux are Claude Code.** Neither can say what a program in a window is doing: the worker's [hooks](workers.md#workers-in-tmux-and-cmux) tell orchestra, and only Claude Code has them. `--agent` (or `AGENT_KIND`) other than `claude` with tmux or cmux is a setup problem: `Workers in tmux must be Claude Code …` (`Workers in cmux …`). The environment probe's worker and the feature interview report through hooks too.

`.orchestra/run/state.json` records which terminal each worker the last run left runs in. A run in another terminal can't reach those workers: it leaves them in the file for a run in theirs, and its `START` block says so, `kept for a run in Herdr, as this run in tmux can't reach their workers: <id> (left running: PAUSED)`. It doesn't start their tickets either, even once bd ready lists one again, as when the question its worker asked is answered: their workers may still be at work in those worktrees. The tickets they block wait as they would for a running one. A file written before workers could run in tmux names no terminal: its workers are Herdr's.

### Workers in cmux

[cmux](https://cmux.com), a macOS terminal for coding agents, can hold the workers: `"terminal": "cmux"` in `.orchestra/settings.json`, `--terminal cmux` or `ORCHESTRA_TERMINAL=cmux`, or left to `auto` from a cmux terminal (a Herdr pane, or tmux, inside it comes first). Start orchestra from a cmux terminal: cmux answers only programs started in its own terminals, so outside one choosing cmux is a setup problem saying so. orchestra finds the `cmux` command on the `PATH`, as in a cmux terminal, or else in `/Applications/cmux.app`.

Each worker gets a workspace of its own in orchestra's window, named with its ticket's ID and opened without taking the focus, so the sidebar lists the workers with their branches; `--workspace` has no use there and is a setup problem. The dashboard's 1–9 keys select a worker's workspace, and [the feature interview](#talked-through) opens claude in a split to the right of orchestra's terminal. As under tmux, workers must be Claude Code: cmux can't say what an agent is doing, so a worker's hooks do, and a session killed or crashed without a word is gone once no `claude` process is left in its terminal; a dialog Claude Code shows before its session starts, such as whether to trust the folder, is read from the screen. From cmux 0.65.0 a prompt is pasted into the worker's input box with `cmux paste`, bracketed, so its lines arrive together; an older cmux types what it is given, with no bracketed paste, so there a prompt of several lines is written to `.orchestra/run/cmux-prompt-<terminal>.md` in the worker's worktree, and the worker is pointed at it with `@`. cmux 0.65.0 also refuses to type over a draft in an agent's prompt or into a dialog it has open, so orchestra passes `--force` with what it types and the keys it presses in its workers' terminals, as a key answering Claude Code's dialogs has to go through; it reads the version with `cmux version`. cmux's own hooks for Claude Code (its sidebar's notices) are off in the workers' terminals, where orchestra's hooks report instead. The adapter was written against cmux 0.64.22 and 0.65.0.

orchestra addresses cmux's workspaces and terminals by their UUIDs, never by short refs such as `workspace:2`, which older cmux numbered afresh on each start, and keeps those it opened in `.orchestra/run/cmux.json`. It closes only a workspace it opened that still has its ticket's name, never its own, and checks afterwards that cmux closed the right one. Quitting or restarting cmux ends the workers (cmux restores its layout, not the programs that ran in it): the next run finds their workspaces gone, or holding no claude, and resumes them from their sessions in new ones, as after a Herdr restart.

### Nothing to run

A run with nothing to run says so and exits 0, rather than open the dashboard only to end at once: no dashboard, no triage, no run report and no notification. It has nothing to run when its own `bd ready` query (in its scope, without questions and the `exclude_types`) finds nothing the run would start and `.orchestra/run/state.json` carries no worker over from the last run (with `--ticket`, none on a ticket in the scope); a worker to carry on with is something to run, and the run goes ahead. A ticket `bd ready` lists that the run would hold back is none to start: a parent whose subtickets aren't all closed and merged, which runs after them, or a ticket blocked by one closed but not merged, which waits for it to merge (`bd ready` counts a closed blocker as done), or a follow-up filed from one (`discovered-from`), which waits likewise (see [Several tickets at once](#several-tickets-at-once)). When `bd` can't show such a ticket's blockers, the run goes ahead. A run that asks checks once **Current tickets** is picked; the others (`--tickets`, `--ticket`, `-plain`, no terminal) check once the startup checks have passed and they hold the lock, and a feature run once its epic is filed. On a terminal the message is a box, otherwise the same lines, plain, after the time:

- `✓ All done`: no ticket is left but those of the `exclude_types` (epics, never run), and none is closed but not merged. `Still open: <ids> (bd close <ids>)` follows when epics are still open: their subtickets merged before this run, which closes an epic only as it merges the last of them.
- `○ Nothing ready to run`: tickets are left, but none can start. A line for each of what holds them: `N questions wait for your answer: bd human list`, `N tickets wait on other tickets: bd blocked`, `N tickets wait for their subtickets to merge`, `N tickets wait for their blockers to merge`, `N follow-ups wait for the tickets they were filed from to merge`, `N in progress · N deferred`, `N closed but not merged: bd list --label unmerged`. A ticket labelled `unmerged` whose branch is on the base already, merged by hand with a commit of its own naming the ticket, counts as merged, as the run itself would find it; the next run that gets as far as its loop removes the label.

With nothing ready, in either form, a deferred ticket whose blockers have all merged gets a line of its own, `Deferred: <id>: its blockers have merged (<blockers>); to run it: bd update <id> --status open`, followed by `its worktree has no commits of its own, safe to remove: git worktree remove <path> && git branch -d wt/<id>` when its worktree holds nothing, as the [`DEFERRED_FREE`](#several-tickets-at-once) line in a run's `START` block does; one deferred until a later date (`bd defer --until`) isn't listed until that date has come. When `bd` can't say which they are, the box goes without them and the log says why.

The [event stream](events.md) records the run's start, its done line, `READY_EMPTY after 0 tickets: everything is done` or `READY_EMPTY after 0 tickets: nothing ready`, and its end with code 0; the log has the done line too. When `bd` can't say, the run goes ahead, and the loop reports what it can't read (`READY_UNREADABLE`). A run whose `DONE_SO_FAR` has reached `LIMIT` ends `LIMIT_REACHED`, as before.

`--concurrent N` (or `-c N`, or `ORCHESTRA_CONCURRENT=N`) sets how many tickets run at the same time for this run, from 1 to 16, overriding `settings.json` (0 is a setup problem, not "unset"); see [Several tickets at once](#several-tickets-at-once). `--terminal` chooses Herdr, tmux or cmux, and `--workspace` the Herdr workspace or tmux session for the worker tabs (cmux has none: each worker gets a workspace): see [Herdr, tmux or cmux](#herdr-tmux-or-cmux). `orchestra -h` lists the flags. Most default to the environment variable `orchestrate.sh` used: `LIMIT` (40), `DONE_SO_FAR`, `AGENT_KIND` (claude), `WORKER_PROMPT` (`.orchestra/worker-prompt.md`), `NOTIFY`, and `WT_ROOT` (`<repo>-worktrees`); a relative `WORKER_PROMPT` or `WT_ROOT`, or their flags, is relative to the repository. The organs add `TRIAGE`, `REVIEW`, `ORGAN_MODEL` and `ORGAN_EFFORT`, and `PROMPT_AT_LAUNCH` controls how workers get their prompt.

The on-or-off variables, `NOTIFY`, `TRIAGE`, `REVIEW`, `PROMPT_AT_LAUNCH`, `ORCHESTRA_TICKETS` and `ORCHESTRA_NO_UPDATE_CHECK`, all read their value the same way: `1`, `true`, `yes` or `on` turns the feature on, `0`, `false`, `no` or `off` turns it off, in any case, and unset leaves its default (on for the first four, off for the last two). Anything else is a setup problem (exit code 2) naming the variable, unless its flag, such as `-triage=false`, is given too.

`--worker-effort medium` (or `WORKER_EFFORT=medium`, or `"worker_effort": "medium"` in `settings.json`) starts Claude workers with `--effort medium`; any of `low`, `medium`, `high`, `xhigh` and `max` will do. Without it they run at Claude Code's own default, and `orchestra init` says so. There is no recommended level yet: it waits on measuring `high` against `medium` on real tickets (time to close, tokens, the check passing first time).

`--ticket-limit 2h` (or `TICKET_LIMIT=2h`, or `"ticket_limit": "2h"` in `settings.json`) stops the run, like `PAUSED`, when a worker is still going that long after its ticket was dispatched: a hung command or a stuck worker would otherwise hold its slot for good. The worker's prompt says how long it has, as agents pace themselves to a stated budget. The ticket gets a note, and its tab and worktree are left open. `0` turns a limit from `settings.json` off for a run. Without a limit, a worker still going after 2 hours is logged once (`LONG_RUNNING`), and the run keeps waiting. Whatever the limit, a worker whose status the terminal can't tell (`unknown`) for 5 minutes stops the run (`UNKNOWN >5min`), as one blocked on a dialog for 4 does. A project not yet set up with `orchestra init` keeps working from `.claude/worker-prompt.md`, `.claude/orchestrate.log` and `.claude/orchestrate-reports/`.

Every `bd`, `git`, `herdr`, `tmux` and `cmux` command orchestra runs has a time limit: 30 seconds for a read or a Herdr, tmux or cmux call, 2 minutes for a git write (worktree, rebase, merge, branch) or a `bd` update; Herdr's own waits keep their timeouts, with 30 seconds to spare. A command still running then is stopped and fails with `<command>: timed out after 30s`, reported like any failure of it (`STATUS_UNREADABLE`, `TERMINAL_FAILED`, `GIT_FAILED`, …). Ctrl+C stops the commands in flight too, and the run ends once its workers have returned; a merge already under way, and the notes after it, finish first, so one Ctrl+C never leaves the repository half merged.

Pressing Ctrl+C again meanwhile quits rather than wait, so that a shutdown that hangs can be left without `kill -9`. With nothing under way that Ctrl+C doesn't cut short, orchestra quits at once with exit code 130, logging and printing `INTERRUPTED: quit at once with Ctrl+C, leaving <id> (tab <tab>) running with its tab and worktree open`, without triage or the report. With a merge or a worktree setup under way, the second Ctrl+C says so, `<id>'s merge is under way; press Ctrl+C again to abandon it (the repository may be left half merged)`, and skips triage and the report, as it always did; a third quits, the line adding `abandoned <id>'s merge: git may still finish it, so check git status before starting another run`. The commands under way run in their own process groups, so they carry on after orchestra has gone: a `git` command may still finish, or hold git's lock files for a while, though a new run can take orchestra's own lock at once. The workers left running aren't labelled `unmerged` as they are after a stop, which would wait on `bd`, but they are saved for the next run to carry on with, as after a stop: those at work as left running, `INTERRUPTED` (see [Exit codes](#exit-codes)). SIGTERM and SIGHUP (closing the terminal or pane) count as Ctrl+C does, so a supervisor's second SIGTERM quits too. During triage and the report, Ctrl+C skips them, and the one after it quits.

Epics are never dispatched: their children are the work. `"exclude_types"` in `settings.json` lists the issue types a run leaves out of `bd ready`, for a project with other container or non-work types, for example `["epic", "decision", "milestone"]`; without it, only `epic` is left out, and `[]` dispatches every type.

Parents run last. A ticket with subtickets (`bd create --parent <id>`) that aren't all closed and merged waits for them, logged once as `<id> waits: its subtickets are not all closed and merged`: its worker couldn't close it before they are, and its work builds on theirs. An epic is never dispatched, so orchestra closes it itself once a run merges the last of its subtickets: when none is left open, running, or closed but not merged (labelled `unmerged`), it runs `bd close <id>` with the reason `All 3 subtickets are merged; closed by orchestra after <last id>`, and logs `closed epic <id>: all 3 subtickets are merged`. An epic that was itself the last open subticket of another epic closes that one too, and so on up. Should `bd close` fail, the log carries `bd`'s error and `all 3 subtickets are merged, but bd could not close <id>: <error>; close it with: bd close <id>`, and the run goes on. An epic whose subtickets were all merged before the run started isn't closed, as orchestra didn't see the last one merge: [nothing to run](#nothing-to-run) lists it under `Still open`.

### One ticket and its subtickets

```
orchestra --ticket CalendarView-bl0
```

`--ticket <id>` (or `ORCHESTRA_TICKET=<id>`) runs that ticket and its descendants (children, grandchildren, …) and nothing else: the queue is `bd ready --parent <id>` plus the ticket itself, with the usual filters, holds and priority order, each parent after its children. A ticket without subtickets is a run of one. An unknown ticket, a closed one or a question (label `human`) is a setup problem. The START line and the dashboard's title line show the scope (`· ticket <id>`), and so does the run report.

Workers are told to file follow-ups that belong to the work as children of `<id>`, and those join the run; anything filed otherwise waits for a later run, and the log and the run report list it. `--limit`, `--concurrent` and the rest apply as usual. The run ends as any other, with `READY_EMPTY`, `LIMIT_REACHED` or `DRAINED`, followed by whether the scope is finished:

- `SCOPE_DONE: <id> and its 3 subtickets are merged`, or for an epic, which the run closes as its last subticket merges, `SCOPE_DONE: <id>'s 3 subtickets are merged; orchestra closed <id>` (`…; close it with: bd close <id>` should `bd close` have failed);
- `SCOPE_OPEN: <id>: 2 of its 5 subtickets not done: <id>.2 (blocked by other-7 outside the scope), <id>.4 (waiting on your answer to <question>)`, naming why each isn't: set aside in this run, deferred, closed but not merged, waiting for its own subtickets, not started.

Both exit with 0.

With nothing under `<id>` ready from the start (or only tickets the run would hold back), and no worker carried over on a ticket in the scope, the run has [nothing to run](#nothing-to-run): it shows `○ Nothing under <id> is ready to run`, then each ticket not done with why, as `SCOPE_OPEN` gives it, and its done line ends with the `SCOPE_OPEN` part (`READY_EMPTY after 0 tickets: nothing ready; SCOPE_OPEN: …`). An epic whose subtickets are all merged is `✓ All done`, with `Still open: <id> (bd close <id>)`.

### A feature from one request

A feature goes from a request to a finished run in one of two ways:

- **Talked through**, typed at the start: run `orchestra` in a terminal and choose **New feature** ([Run](#run)). Claude Code interviews you about the feature and files the tickets you agree on.
- **Planned by the organs**, for scripts and agents: `orchestra --feature "<request>"`. The screen and plan organs turn the request into tickets, and orchestra asks only whether to file them, which `--yes` answers in advance.

Either way the feature is filed in Beads as an epic and its tickets, and run as `--ticket <epic>` would run it. Both start after the usual startup checks (repository, `bd`, the terminal, settings, MCP servers, and a clean main checkout), so that nothing is filed for a run that couldn't start.

#### Talked through

Once you have described the feature, orchestra splits its pane, Herdr's or tmux's, or its cmux terminal, and starts an interactive Claude Code session in the new pane, to the right of orchestra's, in the main checkout, with the keyboard focus: `claude --append-system-prompt-file .orchestra/run/interview-prompt.md -- "Here is the feature I'd like to talk through: @.orchestra/run/feature-request.md"`. Herdr types the command into the pane's shell, which takes no argument with line breaks, so the description, every line of it, goes in `.orchestra/run/feature-request.md`, which the `@` attaches to Claude's first message; tmux runs the same command, with Claude's hooks added, and cmux too, its split taking the keyboard focus. The file holds the description between an opening and a closing `<pasted_content id="<random>">` tag, the ID drawn afresh for each interview: a description is often pasted from an issue or a web page, and the interview's instructions say that text inside the tags may carry instructions you didn't write, which Claude follows only where your own message asks it to. orchestra's pane stays in view, saying `Talking the feature through with claude in the pane on the right, which closes once the feature is filed. Type /exit there to leave without filing; Ctrl+C here stops.`, and waits for the interview to end. A line under it, updated in place each second as Herdr reports Claude (in tmux, as Claude's hooks report it, to `.orchestra/run/interview-session/`), says whether Claude is working, waiting for you or waiting for a permission answer (a permission prompt, or the question whether to trust the folder), and how long the interview has run; once the feature is filed it names the epic: `Filed <epic>: <title> (N tickets)`. The line is gone before the tickets and the question are shown. The instructions, appended to Claude Code's own system prompt so that its tools and sub-agents work, adapt Matt Pocock's [grilling skill](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md) (MIT License; see [the notices](../THIRD_PARTY_NOTICES.md)). It is your own session, not a worker or an organ: your Claude Code setup applies, the project's `CLAUDE.md` and your MCP servers included.

1. Claude reads the README and `CLAUDE.md` (or `AGENTS.md`), then interviews you in rounds. A round asks every question that can be asked yet, numbered, each with Claude's recommended answer; a question that depends on an answer still open waits for a later round. Claude looks facts up in the repository itself, with a sub-agent only for a wide search, rather than ask you; the decisions are yours. When nothing is left open, it sums up what you agreed and waits for you to confirm it.
2. It proposes an epic and its child tickets, each one worker's session of work, with a description, acceptance criteria, a type, a priority, the files it changes, the tickets it waits for, and the `solo` label where one restructures code most tickets touch. Titles are at most 60 characters; no ticket duplicates an open one or asks you a question. Nothing is filed until you agree.
3. It files them with `bd`: the epic, each ticket as its child with its files as `files` metadata (which [footprints](#several-tickets-at-once) read), and `bd dep add` for each link. Last, it writes the epic's ID to `.orchestra/run/feature.json` and tells you that the feature is filed and that orchestra shows the tickets next.
4. Once `feature.json` names the epic and Claude's turn is over (Herdr, or in tmux its hooks, report it idle, or done), orchestra closes Claude's pane, which ends Claude Code, and its own pane has the keyboard focus again: you don't type `/exit`. A `feature.json` written while Claude is still working, or waiting on a permission answer, leaves the pane open until that turn ends. There the epic and its tickets are shown as `--feature` shows a plan (type, priority, files, `after:`), followed by `Start the run on <epic> (N tickets)? [y/N]`. On `y` the run is that of `--ticket <epic>`, as in step 5 below, with the description as the request. Otherwise orchestra says `Start it later with: orchestra --ticket <epic>` and exits with 0.

To end the interview without filing, type `/exit` in Claude's pane, or close the pane: orchestra closes it if it is still open, and says that nothing was filed (below).

Claude only reads and files tickets: it doesn't edit files, commit or push. Ctrl+C in Claude's pane is Claude Code's, which interrupts or clears with it. Ctrl+C in orchestra's pane, SIGTERM or SIGHUP close the interview's pane, which ends Claude Code, and stop orchestra (exit code 130), naming the epic if one was filed.

When Herdr, tmux or cmux can't split the pane or start Claude Code in it, or Claude Code doesn't show in the new pane within a minute, orchestra closes any pane it made, says why in one line (`orchestra couldn't open the interview in a pane beside its own, so claude takes this terminal: <why>`), and hands its own terminal to the session instead, as `claude --append-system-prompt-file .orchestra/run/interview-prompt.md -- "Here is the feature I'd like to talk through: <description>"`, the description in its `pasted_content` tags, waiting for it to end. orchestra can't end that session by itself, so it adds to the instructions there that Claude, once the feature is filed, tells you to type `/exit` to come back. There Ctrl+C is Claude Code's, not orchestra's; SIGTERM and SIGHUP still stop orchestra (exit code 130), the session with it. Ctrl+Z suspends orchestra with the session, as the shell suspends any program, and `fg` brings both back. orchestra run outside tmux, its workers in a detached session, has no pane of its own to split: the session gets its terminal this way from the start, without that line.

orchestra removes an earlier `.orchestra/run/feature.json` before the session. When the session leaves none, or it names no epic `bd` knows, orchestra says `No feature was filed; nothing to run.` and exits with 0. Without `claude` on the `PATH`, or with workers of another agent (`--agent`), there is no interview: orchestra says why and plans the feature with the organs, as below.

#### Planned by the organs

```
orchestra --feature "Add a --json flag to the list command"
```

`--feature "<request>"` takes a request from idea to a finished run, asking nothing but whether to file the plan:

1. The [screen organ](organs.md#organs) judges the request. A request it rejects or finds unclear stops with its reason (exit code 2), as does a screen that fails: an unscreened request isn't planned.
2. The [plan organ](organs.md#organs) plans it as an epic and its tickets. When it needs answers first, orchestra prints its questions and stops (exit code 2); run it again with the answers in the request.
3. orchestra shows the plan: the epic, then each ticket with its type, priority, files and the tickets it waits for (`after:`), and any file dropped when the plan was checked. It asks `File these N tickets and start the run? [y/N]`. `--yes` files it without asking; without a terminal to ask on (input and output both: the plan and the question go to standard output, so `> run.log` counts as none), and without `--yes`, nothing is filed (exit code 2).
4. orchestra files the plan with `bd`: the epic, each ticket as its child with its description, acceptance criteria, type, priority and `files` metadata (which [footprints](#several-tickets-at-once) read), then a `blocks` link for each ticket it waits for. If a `bd` command fails, orchestra stops (exit code 4) and lists what it filed, each ticket by ID and plan key, with the `bd delete … --force` command that removes it and the `orchestra --ticket <epic>` command that carries on with it; when a link fails, it first gives a `bd dep add <blocked> <blocker>` for every link not added, that one included, so the tickets still run in order. It says nothing was filed only when `bd` exited with an error of its own: a `bd` that was stopped, was killed, or gave output orchestra couldn't read may have filed what it was filing, and orchestra says how to check with `bd list`.
5. The run is that of `--ticket <epic>`, with the other flags as given (`-c`, `--plain`, the effort flags, …). The START line and the dashboard's title show `· feature <epic>`, the log names the request, and the run report gets the request as evidence.

On a terminal, the screen and the plan each show a spinner while Claude works, with the time so far: `⣾ Planning the feature with Claude… 1:12 (this can take a few minutes; Ctrl+C stops it)`. When the step ends, its line becomes its outcome and how long it took: `◆ Request screened (8s)`, `◆ Feature planned (2m31s)`, `◆ Planning needs answers`, `◆ Request not screened` or `◆ Feature not planned` before the error, or `◆ Screening stopped` and `◆ Planning stopped` after Ctrl+C. With `--plain`, or when output isn't a terminal, each step is one line as it begins: `screening the request with claude…`.

Nothing is filed before you confirm the plan, and Ctrl+C stops the checks, the screen, the plan or the question with nothing filed (exit code 130). `--organ-model` and `--organ-effort` apply to both organs. `--feature` with `--ticket` (or `ORCHESTRA_TICKET`) or `--tickets`, an empty request, and `DONE_SO_FAR` at or above `LIMIT`, which would file a plan and start none of it, are setup problems.

## Several tickets at once

With `concurrent` above 1, up to that many workers run side by side, each in its own worktree and tab. What keeps it safe:

- **No ticket runs twice.** A ticket that's been handed out isn't picked again, even before its worker claims it.
- **Free slots don't wait.** While workers run, `bd ready` is read every 30 seconds: a ticket that becomes ready meanwhile (an answered question, a worker's follow-up, a closed blocker) takes a free slot then, and the dashboard's **In queue** follows.
- **A follow-up waits for the ticket it was filed from.** A ticket a worker files as it works, linked `discovered-from` its own ticket (`bd create --deps discovered-from:<id>`, or `bd dep add <follow-up> <id> --type discovered-from` after it is filed), is ready at once: `bd` doesn't count that link as blocking. But it was written against the code of the ticket it came from, which isn't on the base until that ticket merges, so it waits as it would for a blocker: while its source runs, waits on a question, or is closed but not merged. The log says once `<id> waits: filed by <source>'s worker; waiting for it to merge`, or `… <source> closed but not merged (<why>)`, and it isn't counted in **In queue** meanwhile. Once the source merges (or is closed and on the base already), it starts from a base that has its code. So a follow-up unrelated to its source waits too, usually the few minutes until the source merges, in later runs as well while its source is labelled `unmerged`. A source that is open or deferred and not running holds nothing, as it may never run. With `--ticket`, `SCOPE_OPEN` names such a follow-up `filed by <source>'s worker; <source> is closed but not merged`.
- **A ticket that started too early goes back in the queue.** A worker that finds its ticket needs another ticket's work, not merged yet, links that ticket as a blocker (`bd dep add <id> <blocker>`) and stops with the ticket open. When it stops with the ticket open or in progress, no commits beyond the base and a clean worktree, and `bd show` lists a blocker that hasn't merged (running, waiting on a question, open, deferred, or closed but not merged), the ticket started too early, and all it needs is to wait: orchestra reopens it if the worker left it in progress, notes on it `Orchestra: started before <blocker> merged; back in the queue until it does.`, and removes its worktree, branch and tab, which hold nothing. The log says `WAITS_FOR_MERGE: <id> waits for <blocker> to merge; …`, and the dashboard shows the ticket `◷ waiting`. Whether a blocker has merged is the same here, in the holds above and in `DEFERRED_FREE` below: what git and the run know decides, not the `unmerged` label `bd show` lists. A blocker whose label outlived its merge (merged by hand, or merged when `bd` couldn't remove the label, which the log warns of with `LABEL_FAILED`) has merged, and holds nothing. It isn't set aside or triaged, and doesn't count toward the [hold for the environment](#several-tickets-at-once), or toward `LIMIT` until it starts again: the run's `[n/limit]` and its done line count it once. `bd ready` leaves it out until the blocker closes, and the holds above until it merges; then it starts again from a base with the blocker's code. A blocker outside the run that never merges leaves it open and held, as [nothing to run](#nothing-to-run) says. With commits of its own (work to review), or with every blocker closed and merged already, the ticket is deferred for review as any ticket left unfinished; one waiting on a question waits for your answer instead. A ticket deferred before orchestra put such tickets back in the queue, or deferred by hand, stays deferred once its blockers merge, so each run's `START` block lists every deferred ticket in its scope with at least one blocker and every blocker closed and merged (none running, waiting on a question, or closed but not merged): `DEFERRED_FREE: <id>: its blockers have merged (<blockers>); to run it: bd update <id> --status open`. A ticket deferred until a later date (`bd defer --until`, bd's `defer_until`) was deferred on purpose, with a time to look again, and isn't listed until that time has come; once it has passed, the ticket is listed as one with no date. When its worktree (`wt/<id>`) is left with no commits beyond the base, the line goes on `; its worktree has no commits beyond <base>, safe to remove: git worktree remove <path> && git branch -d wt/<id>`. orchestra only lists them, never reopens one itself: a ticket can be deferred for other reasons. It reads them with one `bd list` and a `bd show` for each one with blockers; when `bd` can't say, the log says why and the run goes on without the list.
- **Merges queue.** A finished ticket waits for its turn. If other tickets merged while it ran, its branch is rebased onto the current one, and the merge check from `settings.json` (`check_fast`, normally `scripts/check-fast.sh`) runs again on the rebased code before it merges. A conflict (`MERGE_CONFLICT`) or a failing check (`CHECKS_FAILED`) leaves that ticket for review, once its worker has been asked to resolve or fix it (below), and the run goes on. A worktree with uncommitted changes to files it tracks, as a check that rewrites them (a formatter, `go mod tidy`) leaves, can't be rebased: the ticket is left for review with `DIRTY_WORKTREE`, naming the files, and so is one whose rebase git refuses for another reason without stopping on conflicts (`REBASE_FAILED`, with git's error). A ticket whose worktree has another branch or a detached HEAD checked out, rather than its own, as when its worker switched, is left for review with `OFF_BRANCH`, naming what the worktree has checked out, before anything is rebased or checked. A failing check's whole output is kept in the worktree, in `.orchestra/run/check.log`, which the `CHECKS_FAILED` line names (the log has its last 40 lines). A passing check merges the ticket, and each line of its output starting with `FLAKY:`, which says a test failed and then passed on a rerun, is a warning naming the ticket: `FLAKY: <id>'s check '<check>' passed, but a test failed and then passed on a rerun: <the rest of the line>`. Tickets it blocks wait until it merges, in later runs too: it is labelled `unmerged` until then. Without a check command, a rebased ticket merges unchecked, and the log says so. The queue waits on the check, so it is stopped (with everything it started) after 30 minutes, or `"check_timeout"` from `settings.json` (`"5m"`, `"45m"`; `--check-timeout` or `ORCHESTRA_CHECK_TIMEOUT` for one run): the ticket is set aside with `CHECKS_FAILED: … did not finish within 5m`, and the next finished ticket merges. Set it to a few times the check's usual running time.
- **Dependencies are set up again after a rebase.** A finished ticket's worktree has the dependencies its worker installed (`node_modules`, a virtualenv) for the code as it closed the ticket. When a ticket that bumps a dependency merged meanwhile, the rebase brings in the new lockfile, and the check would run the rebased code against the old dependencies and fail on code the ticket never touched. So with `"setup"` in `settings.json`, the command that installs them (`"npm ci"`, `"uv sync"`, `"bundle install"`; see [The checks](setup.md#the-checks)), orchestra runs it in the worktree before the check whenever the commits since the worktree's dependencies were last set up change a file `"setup_files"` names: on a merge, on a `RECHECK` and before checking a worker's resolution of a conflict. The log says `<id>: package-lock.json changed in the rebase; running 'npm ci' before the check`; when no such file changed, it doesn't run. It may run as long as the check (`check_fast_timeout`). A setup that fails sets the ticket aside as a failing check does, its whole output kept in the worktree's `.orchestra/run/setup.log`: `CHECKS_FAILED: <id> closed, but the setup 'npm ci', run before the check, fails on wt/<id> rebased onto <base>; … (output is in <worktree>/.orchestra/run/setup.log); checked once more if <base> moves on in this run`, and checked once more, setup first, as below (the dependencies are still those from before the lockfile changed). A failing setup is handed back to the worker to fix as a failing check is (below), and for a resolution, one it can't fix is a failed resolution. Without `"setup"`, nothing runs before the check; a project can put the install in the check itself instead (`npm ci && npm run check`), at the cost of an install on every check.
- **A conflict goes back to its worker first.** When the rebase stops on conflicts, the worker that did the ticket, still idle in its tab with the whole change in mind, is asked to resolve it: the rebase is left stopped in its worktree, and the worker is told which files conflict, to keep the intent of both sides and finish the rebase, to skip (`git rebase --skip`) a commit whose change `<base>` has already, to run the check command once the rebase has finished until it passes, since the commits that apply cleanly can break it too, folding any fix into the last commit, and to do nothing else. The log says `RESOLVING: wt/<id> conflicts with <base> in <files>; handed back to its worker in tab <tab>`, and the dashboard shows the ticket as `⟳ resolving`. The merge queue isn't held meanwhile: other finished tickets merge. When the worker is done, orchestra checks the result itself rather than taking its word: the rebase is finished, the worktree clean and on the ticket's branch (the check runs on what the worktree has checked out, and the merge brings in the branch), the branch on top of `<base>` with the ticket's own commits, or those of them the worker didn't skip, and no others, and the check command passes. A branch the worker left with no change of its own, every commit skipped, closes with no change to merge, without the check. Then the ticket queues again and merges (rebased again, and re-checked, if more landed meanwhile; a new conflict goes back to the worker once more, twice at most). If the worker doesn't finish within 20 minutes (`"resolve_timeout"` in `settings.json`), leaves the rebase unfinished or the worktree on another branch or a detached HEAD, makes a commit of its own, or the check fails and isn't fixed (below), its branch is put back as the ticket closed it (left as it is when the worktree isn't on it) and the ticket is set aside with `MERGE_CONFLICT` as before, the line and a note on the ticket saying what was tried and why it failed. Without a check command, with the worker gone from its tab or busy, conflicts aren't handed back, and the `MERGE_CONFLICT` line says why. A worker at the account's usage limit isn't passed over: the run holds for the limit, starting no new tickets, and the worker is handed the rebase once the limit resets (Escape first, as a limited worker is told to carry on), or as soon as it goes idle by itself (`<id>'s worker is at the usage limit: it is handed back once the limit lifts`). One that reaches the limit during a hand-back holds the run the same way and is told to carry on after the reset; neither wait counts toward the 20 minutes, and a hold that lasts `usage_limit_wait` stops the run with `USAGE_LIMIT`, the hand-back left as Ctrl+C leaves it. `"resolve_conflicts": false` in `settings.json`, or `--resolve-conflicts=false` for one run, turns it off. Ctrl+C during a hand-back leaves the rebase in progress, and the `INTERRUPTED` line says so: once the worker has finished it, run the check and merge the branch by hand.
- **A failing check goes back to its worker too.** A check that fails on the rebased branch, after a clean rebase or once the worker has resolved a conflict, often fails where the ticket's change meets what landed meanwhile: a test another ticket added for the code as it was. The worker, idle in its tab with the change in mind, is handed the failure: where the check's whole output is and the lines of it that say what failed (as the reviewer gets them), what landed on `<base>` since its branch was cut (`git log --oneline`), and the instruction to fix the branch so the check passes, keeping the intent of both sides, and commit the fix with the ticket's ID in the message, and nothing else. The log says `FIXING: '<check>' fails on wt/<id> rebased onto <base>; handed back to its worker in tab <tab> to fix (1 of 2, up to 20m)`, and the dashboard shows the ticket as `⟳ fixing`. The merge queue isn't held meanwhile. When the worker is done, orchestra checks what it left rather than taking its word: no rebase in progress, the worktree clean and on the ticket's branch, the branch as the check failed on it with new commits on top, each naming the ticket; then the setup, if the fix changed a dependency file, and the check run again. A check that passes now merges the ticket (rebased and checked again if more landed meanwhile); one that fails again goes back to the worker again, twice in all by default (`"check_hand_backs"` in `settings.json`; `0` turns it off). A fix it can't accept (uncommitted changes, the worktree left on another branch or a detached HEAD, rewritten commits, a commit not naming the ticket, nothing committed, not done within `"resolve_timeout"`) is undone, the branch reset to where the check failed when the worktree is clean and on it, and nothing more is handed back. When the attempts run out, the ticket is set aside as before: after a clean rebase, `CHECKS_FAILED: <id> closed, but '<check>' fails on wt/<id> rebased onto <base>, after it was handed back to its worker to fix twice (see its notes)`, with a note on the ticket naming each attempt and what came of it; after a resolution, a `MERGE_CONFLICT` whose line and note say the same, the branch put back as the ticket closed it. A check that did not finish within its time limit isn't handed back, nor is anything while the run winds down or holds for a stop, or when the worker is gone from its tab or busy: the `CHECKS_FAILED` line then ends `not handed back to its worker: <why>`. A worker at the usage limit, as it is handed the failure or while it fixes it, waits the limit out as for a conflict. Ctrl+C during a hand-back leaves the worker's fix as it is, and the `INTERRUPTED` line says so: once it has committed it, run the check and merge the branch by hand.
- **A failed check is tried once more.** A check can fail on something the ticket didn't change: a flaky test, or a bug that a later ticket fixes. So a ticket set aside with `CHECKS_FAILED` stays in view for the rest of the run, and once the base has moved on (another ticket merged), it is checked once more: the log says `RECHECK: <id>'s check failed on <base> at <commit>, which has moved on since; rebasing wt/<id> and checking it once more`, its branch is rebased onto the base, and the check runs again, through the merge queue as any merge does. It takes one of the run's slots, as a running ticket does, before any new ticket starts, and the dashboard shows it in Current meanwhile. If the check passes, the ticket merges, its `unmerged` label removed, and the tickets it blocks start; if the rebase stops on conflicts, its worker is asked to resolve them, as above; if the check fails again, the ticket stays set aside: `CHECKS_FAILED: <id> closed, but '<check>' fails again on …`. Each ticket is checked again once at most, and none is while the run winds down or holds (see below), or while a `solo` ticket runs or is next. The first `CHECKS_FAILED` line ends `checked once more if <base> moves on in this run`, or says why not when the lines of the check's output that say what failed name a package or a file in a directory the ticket's own commits change, which another ticket won't fix: `not checked again in this run, as it failed in internal/a, which <id>'s own commits change`. A ticket taken up since it was set aside is left as it is rather than rebased under whoever took it up: reopened, its worktree with uncommitted changes or its branch moved, or its worker at work again in its tab. The log then says `<id> is not checked again: <why>; it stays set aside`.
- **Some tickets run alone.** A ticket labelled `solo` (`bd label add <id> solo`), such as one splitting a file every other ticket touches, would conflict with whatever runs beside it. It starts only when no other ticket is running, and nothing new starts while it runs: free slots wait, and the log says once `waiting for solo ticket <id> to finish`. When it is next in priority while others run, nothing new starts behind it, so it isn't starved; the log says `solo ticket <id> is next`, and it starts as soon as the running ones finish. The dashboard's title line shows `solo <id> next` or `solo <id> running`. Holds and questions work as for any ticket, and one whose worker carries on in its tab after its question, adopted while others run, runs alone from then on as well: nothing new starts until it finishes. With one ticket at a time the label changes nothing.
- **Tickets that touch the same code don't run together.** Each ticket has a **footprint**: the files and functions its title, description, design, acceptance criteria and notes name (`internal/dispatch/merge.go:120`, `run.go`, a route of a Next.js or SvelteKit project with its brackets or `+` such as `pages/[id].tsx` or `src/routes/[slug]/+page.svelte`, `Loop.merge`, `refreshBranch()`, a camel-case name in backticks such as `waitSettled`, but not a Go keyword or builtin such as `func()` or `len(x)`, a standard package's function such as `synctest.Wait()`, a test's method such as `t.Run()`, nor a name such as `GitHub` or `iOS`, nor an extension alone such as the `.tsx` of "the `.tsx` files"), its `area:<name>` labels, and the files its `files` metadata lists (`bd update <id> --set-metadata files=a.go,b.go`, or a list: `'files=["a.go","b.go"]'`), where a folder (`internal/dispatch/`) means every file under it, those another ticket adds there included (`internal/dispatch/cart.go`), one that doesn't exist yet (`web/src/`, with its trailing slash) every file under it that another ticket names, and a glob (`*.go`, `internal/**/*_test.go`) every file it matches, one that matches none yet (`web/src/*.ts`) every file or folder another ticket names that it would match, from the repository's root; a part of a glob also means the name written as it is, so a route of a Next.js or SvelteKit project (`pages/[id].tsx`, `src/routes/[slug]/`) means that file or folder, and `[id]` the class matching `i` or `d` besides. Names are checked against `git ls-files`: a bare file name means every file of that name, `./run.go` and `internal/dispatch/run.go` alike, and a path that isn't there counts only in a folder that is (a file the ticket adds), or in any folder when the `files` metadata lists it (a project built from a spec adds whole folders), and one outside the repository (`../x.go`, `/etc/passwd`) never counts. The files the project's check command names (`scripts/check.sh`), specs under `.orchestra/specs/` and the spec a ticket's `spec` metadata names (one a spec run keeps where it is in the repository, such as `docs/shop-spec.md`, left out of that ticket's footprint alone) are left out, as are predicted ones, unless the `files` metadata lists them: nearly every ticket names the check in "`scripts/check.sh` passes", and every ticket broken down from a spec cites it, without changing them. Two tickets overlap when they share an area label, a function, or a file. A ticket works on the files it names and on those the other names that mention one of its functions (orchestra reads them in the checkout), so a ticket naming `Loop.merge` overlaps one naming `loop.go`; in a file both work on, they are compared by function when both name functions it mentions, and run side by side when none is the same. A running ticket's footprint also grows with every file its worker edits (Claude workers report each Edit and Write through their hooks, in `.orchestra/run/edits`, kept when a gone worker's session is resumed), compared file by file. A free slot goes to the highest-priority ready ticket that overlaps no running ticket; one that does is skipped, not waited for, and the log says once `skipping <id>: touches Loop.merge, like running <other>`. If every ready ticket overlaps, the slot stays empty until something finishes. A ticket naming nothing runs beside anything until the [predictor](organs.md#organs) has guessed its files (`<id> footprint predicted: …`), which then count like files it names, marked `(predicted)` in the log; a `solo` ticket waits for every running ticket anyway. The dispatch log shows each ticket's footprint (`<id> footprint: …`). When two running workers edit the same file, the log says once `LIKELY_CONFLICT: <a> and <b> both edit <file>`. `"footprint": false` in `settings.json` turns all of this off.
- **Planning orders tickets that touch the same code.** Keeping overlapping tickets apart at dispatch still lets them run in either order; `orchestra plan` orders them ahead of time. It reads the open tickets (leaving out questions and the `exclude_types`), computes each one's footprint (leaving out the check command's files and specs, as above), and proposes a blocks link between two that name the same function, or work on the same file of at most 200 lines (in a larger file they likely work in different places; a file a ticket adds counts as small). They work on files as at dispatch: a ticket works on the files it names and on those the other names that mention one of its functions (orchestra reads them in the checkout), so a ticket naming `Loop.merge` is ordered with one naming a small `merge.go` that mentions it; in a file both work on, they are compared by function when both name functions it mentions, and get no link when none is the same. A function one of them names in passing, which the file doesn't mention, doesn't keep them apart. The higher-priority ticket goes first, then the older one; of two filed in the same second (bd's `created_at` counts whole seconds), the lower subticket number, `e.2` before `e.10`. Area labels and predicted files alone link nothing, and tickets already ordered by blocks links, directly or through others, are left alone; tickets touching one function form a chain rather than each waiting for every other. It prints each link (`k-2 (P3) waits for k-1 (P1): both touch Loop.merge`) and changes nothing; `orchestra plan --apply` adds them with `bd dep add`. Run it after filing a batch of tickets, before a run: `bd ready` then holds each second ticket until the first closes, and `orchestra` until it merges.
- **One git writer at a time.** Worktree creation, rebases, merges and cleanup in the main repository take a lock, so workers don't trip over git's lock files.
- **A failing machine holds the run.** Sometimes the environment fails every worker the same way, whichever ticket it has: a safety classifier that is down refuses every command, say, and each worker gives up at once. Setting each ticket aside in turn would burn through the queue, so the run holds for the environment instead when 2 tickets in a row either had workers that went idle for good within 2 minutes of dispatch without claiming the ticket, committing or leaving changes, or were blamed on the environment with high confidence by [triage](organs.md#organs). The log says once `ENVIRONMENT: the last 2 tickets (<a>, <b>) each settled within 2m of starting without being claimed or changed; check the machine, then restart`: no new tickets start, the running ones finish, and the run ends with exit code 7. Tickets whose workers failed at once did nothing, so they are reopened rather than left deferred, with their notes kept (`<id> reopened: …` in the log, a `reopened` event in the event stream), and no longer count as set aside; tickets triage blamed, whose workers had started on them, stay deferred with the verdict in their notes. One such failure alone changes nothing. Once the running tickets finish, the run probes the machine: the log says `PROBE: the run holds for the environment; in 10m one worker without a ticket runs a command, …`, and 10 minutes later one worker is started in the main checkout, in a tab of its own, and asked to run a single command; a Claude worker starts with `--strict-mcp-config`, without MCP servers, as it needs none. If it does, the machine works again: its tab is closed, the log says `PROBE_OK: …; taking tickets again`, and the run goes on with the reopened tickets. If it doesn't within 5 minutes, or stops without running it, the run ends as it would have (`Stopped: ENVIRONMENT`, notified), the `ENVIRONMENT` line adding how the probe failed, and the probe's tab is left open to read. The machine is probed once per run, so a second hold ends it. Press Ctrl+C to end the run during the wait. `"environment_hold": {"count": 3, "window": "90s", "probe": "30m"}` in `settings.json` changes the thresholds and the wait, `{"probe": "0"}` turns the probe off, and `{"count": 0}` turns the hold off.
- **Stopping drains.** Something that stops the run (`PAUSED`, `BLOCKED`, a tool failure) is logged as `HOLD`. No new tickets start, the running ones finish and merge, and then the run ends with that reason. With one ticket at a time, nothing changes. Ctrl+C still stops at once. A worker left running when the run ends (the one that stopped it, or any at Ctrl+C) may still close its ticket after orchestra has gone: the next run carries it over and merges it then (see below). Its ticket is labelled `unmerged` too (`<id> is left running in tab <tab> and labelled 'unmerged'`), so the tickets it blocks wait in later runs until it merges, even if the next run can't carry it over. To wind a run down yourself, press **s** in the dashboard (or send SIGUSR1): see [What you see](dashboard.md#what-you-see).
- **The next run carries on with the workers a run leaves.** As a run ends, however it ends (done, a stop, Ctrl+C, winding down), it writes the workers it leaves in their tabs to `.orchestra/run/state.json` in the main checkout, while it still holds its lock: those on tickets waiting on a question, and those it left running, with what stopped it (`PAUSED`, `BLOCKED`, `TICKET_LIMIT`, `INTERRUPTED`, …); the log says `left for the next run: <id> (asked <question>), <id> (left running: PAUSED)`. The next run reads the file in its `START` block, `carried over from the last run: …`, and takes each up as it does a ticket asked in the run itself: a ticket closed meanwhile is adopted and merged (rebased and checked if the base moved on, its `unmerged` label removed), and the tickets it blocks start once it has; one whose worker is at work on it again is adopted and watched, rather than stopping the run with `AGENT_BUSY`; one whose question was answered comes back through `bd ready` to its earlier worker, told the answer is in (or, gone from its tab, its session resumed), rather than to a new one that starts over. One still waiting on its question, or left running with its worker idle (waiting for you, as when the run stopped), is left as it is and saved again. One deferred meanwhile shows as deferred. Each is checked first: one whose worktree is gone, or whose ticket is closed with its branch on the base already (merged by hand, with a commit of its own naming the ticket: one since its branch was cut from the base, which the file notes for each worker), is dropped, as the log says; one whose ticket was deleted from `bd` since is dropped too (`<id>, carried over from the last run, is dropped: bd has no such ticket`); one it can't check, as `bd` can't show its ticket (after three tries) or `git` can't list the worktrees, isn't taken for gone: it is kept for the next run and saved again as it was, as the log says (`<id>, carried over from the last run, is kept for the next run: bd can't show it: …`); one in progress whose worker has gone from its tab has the worker's session resumed in a new tab ([`RESUMED`](workers.md#worker-prompt)), or, without a session to resume, is warned about once (`WORKER_GONE: <id> is in progress after …, but its worker is gone from tab <tab> (worktree <path>)`), noted on the ticket and dropped, and the run goes on. In Herdr, a worker the last run launched just before Ctrl+C, which Herdr hadn't yet seen to give it the name orchestra knows it by, comes up unnamed: the next run, finding no worker under that name, looks in the pane it was started in, which the file holds too, and names the worker there (`<id>'s worker in tab <tab> came up without its name; named it <name>`), but only while Herdr still has the tab labelled with the ticket's ID, for the reason below. Merging a carried-over ticket closes its worker's tab only while the terminal still has the tab labelled with the ticket's ID (in tmux, the window named with it): Herdr numbers its tabs afresh when it starts without restoring its last session, and tmux its windows when its server starts again, so after such a restart the tab ID the last run recorded may be another tab, yours included. Then the `closed` line ends `worktree and branch removed; tab <tab> left open: the terminal has it labelled '<label>' now, …`, or `its tab <tab> was closed already` if there is no such tab; this holds for any merged ticket. A run scoped with `--ticket` keeps the workers on other tickets for a later run. Ctrl+C while the run is still reading the last run's state (in its `START` block) ends it `INTERRUPTED` at once and leaves the file as it was, so the next run carries every worker over; a check cut short drops none. A file that can't be read carries nothing over, and the log says why. An asked ticket its worker closed before the run could merge it (`ASKED_UNMERGED`, or `LEFT_UNMERGED` for one the last run left running) is carried over and merged by the next run, as one closed between runs is; a ticket left for review (`MERGE_CONFLICT`, `CHECKS_FAILED`, …) isn't carried over, nor one whose rebase Ctrl+C left in progress during a hand-back; the `unmerged` labels still hold what they block. A quit at once (a second Ctrl+C) saves the workers as the run would have as it ended, but for one that comes while the run still reads the last run's state, which leaves the file as it was.

What `orchestra` can't make safe for you:

- **Checks that collide.** Every worker runs the project's checks. Tests that share one named simulator, a port or a database can fail when two run at once.
- **Files every ticket touches.** If most tickets add to the same spot, like a CHANGELOG's `[Unreleased]` list, the end of a test file or the end of a struct, rebases conflict: each side only added lines, but git can't order them. The worker prompt asks workers to put new tests in a new file named after the feature and new fields and helpers next to the code they belong to. For the changelog, `orchestra init` offers a `.gitattributes` line, `CHANGELOG.md merge=union`, which keeps both sides' lines; a line both sides add identically (a `### Fixed` heading, say) is kept once. The same works for other list-like files.

Start at 1, and raise it once the checks run cleanly side by side.

## The full check

A run that ends by itself (`READY_EMPTY`, `LIMIT_REACHED` or `DRAINED`) having merged at least one ticket runs the project's full check once, after its last merge and before triage finishes and the run report: `check_full` from `settings.json`, normally `scripts/check-full.sh`, which runs `scripts/check-fast.sh` and then the suites too slow or too demanding to run on every merge ([The checks](setup.md#the-checks)). It doesn't run after a stop or a hold, after Ctrl+C, after a run that merged nothing, or without `check_full` (a project set up before it had one: `orchestra init` adds it).

It runs on the head of the branch the run merged into, in a worktree of its own, `<WT_ROOT>/check-full-<random>`, on no branch, which is removed afterwards with whatever the check left in it: the main checkout stays as it is. It may run for 60 minutes, or `check_full_timeout` from `settings.json` (`--check-full-timeout` or `ORCHESTRA_CHECK_FULL_TIMEOUT` for one run), and is then stopped with everything it started. Nothing is installed in that new worktree, so with `"setup"` in `settings.json` (such as `"npm ci"`; see [The checks](setup.md#the-checks)), orchestra runs it there first, always, within the same time limit. The log says `FULL_CHECK: running '<check>' on <base> at <commit> in <worktree> (time limit 60m)`, or `running '<setup>', then '<check>', on …` with a setup; on a terminal a line spins meanwhile, `Running the full check… (Ctrl+C skips)`. Ctrl+C stops it (`FULL_CHECK_SKIPPED`) and skips triage and the run report, as it does during them.

- **Passing**: `FULL_CHECK passed: '<check>' on <base> at <commit> (12m3s)`. Each `FLAKY:` line of its output is a warning, as for the merge check.
- **Failing**: `FULL_CHECK_FAILED: '<check>' fails on <base> at <commit>, in the suite <suite>; the whole output is in <repo>/.orchestra/run/check-full.log; filed <id>`, with a notification, `Full check failed · <suite>`. One that runs out of time says `did not finish within 60m` instead of `fails`. The suite is the one its output names last: the runners print `SUITE: <name>` as each suite starts (its name, or else its command), and a check of your own can print the same; without such a line, the suite is the check itself. The whole output is kept in the main checkout's `.orchestra/run/check-full.log` until the next full check fails; the log has its last 40 lines, and so does the run report, after the reviewer's text (the reviewer is told how the full check went, too). orchestra files a P2 bug titled `Full check fails: <suite>` and labelled `check-full`, with the lines of the output that say what failed, for a worker to fix in a later run. While a ticket with that title and label is open, the next failure in the same suite files no other: it is noted on that ticket, and the line ends `<id> is open for it already`.
- **Failing in the setup**: `FULL_CHECK_FAILED: the setup '<setup>', run before '<check>', fails on <base> at <commit>; the whole output is in <repo>/.orchestra/run/check-full.log; no ticket filed: it is not a suite's failure`, with a notification, `Full check failed · setup`. The check doesn't run; the output is kept, and its end goes to the log, the reviewer and the report, as for a failing check, but no ticket is filed: a setup fails for want of a network or a registry as often as for the code.

The [event stream](events.md) records it as a `full_check` record.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | nothing left in `bd ready`, the limit was reached, or it stopped after the running tickets as asked (`DRAINED`); also a run with [nothing to run](#nothing-to-run) from the start (`✓ All done` or `Nothing ready to run`); with `--ticket`, the last line says whether the ticket's scope is finished (`SCOPE_DONE` or `SCOPE_OPEN`); with `--feature`, also a plan you declined; with **New feature**, also an epic you didn't start, or an interview that filed none |
| 2 | setup problem found before starting (all problems are listed), or another run going in the same repository; with `--feature`, also a request the screen turned down or couldn't judge, a plan that failed or has questions, or no terminal to confirm on without `--yes` |
| 3 | a worker stayed blocked for more than 4 minutes or unknown for more than 5, went idle with its ticket still `in_progress`, or was still going after the ticket limit |
| 4 | a terminal (Herdr, tmux or cmux), Beads or git failure, or orchestra panicked while working on a ticket (`PANIC`) |
| 5 | uncommitted changes in the main checkout, or it left the branch it started on |
| 6 | a finished ticket's branch does not fast-forward (it should have been rebased first) |
| 7 | workers kept failing at once, whichever ticket they had: the environment, not the tickets (`ENVIRONMENT`) |
| 130 | stopped with Ctrl+C, SIGTERM or SIGHUP, or quit at once by a second one while the stopped run wound down (`INTERRUPTED: quit at once …`); the running workers keep their tabs and worktrees |

## After a run stops

After a 3, answer the worker in its tab, then resume with `DONE_SO_FAR=<n>`: the next run carries over the workers this one left running (see [Several tickets at once](#several-tickets-at-once)), so it merges a ticket the worker closed meanwhile, and adopts a worker still at work on its ticket. A ticket whose worker was left running (after a 3, 4 or 130, say) is also labelled `unmerged`: the tickets it blocks wait until its branch (`wt/<id>`) is merged, by the next run or by hand, and the next run removes the label once the branch is on the base with a commit naming the ticket that it made since it was cut, or once the base holds the branch's changes, squash-merged by hand, and a commit on it that the branch doesn't have names the ticket: orchestra notes where it was cut (the merge-base) in the ticket's metadata, `unmerged_fork`, as it labels it, so that an older commit naming the ticket, or a branch with no commits of its own, doesn't count. A quit at once labels nothing, though it saves the workers for the next run: label each ticket it names yourself (`bd label add <id> unmerged`), merge one its worker closes by hand, and run `git status` before the next run if it abandoned a merge.
